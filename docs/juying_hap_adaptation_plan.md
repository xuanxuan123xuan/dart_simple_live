# 借鉴聚映播放器的落地顺序

这是一份不改现有代码的实现规划，先用于评估工作量。

## 第一阶段：先把播放稳定性做出来

- 统一播放器状态：准备、缓冲、播放、首帧、渲染、错误、停止。
- Surface 创建/销毁/尺寸变化单独处理。
- 播放成功和真正渲染分开。
- 保留封面直到收到渲染确认。
- 加入 Surface 重新绑定和播放器释放保护。

## 第二阶段：加入硬解降级

- 默认尝试鸿蒙硬解。
- 记录当前硬解模式和失败次数。
- 直出失败时切换 copy 模式。
- copy 仍失败时锁定软件解码。
- 切换过程避免循环重试。

## 第三阶段：抽离平台适配器

- 定义统一房间、清晰度、播放地址、弹幕消息模型。
- 每个平台单独实现解析、签名、Cookie 和 WebSocket。
- 所有平台结果进入统一归一化层。
- 页面只依赖统一接口。

## 第四阶段：弹幕性能

- 使用单一 Canvas 或原生绘制层。
- 用轨道占用表避免弹幕重叠。
- 限制最大活跃条数。
- 可选重复合并和屏蔽词。
- 画布尚未准备好时缓存少量消息。

## 第五阶段：数据和生命周期

- 数据库迁移版本化。
- 收藏、历史、标签分表。
- 事务失败可回滚。
- 备份先预览，应用后校验。
- 后台播放、画中画、投屏、屏幕常亮各自持有生命周期对象。

## 不建议直接照搬的部分

- 不直接复制原 HAP 的 ArkTS 字节码或 `.so`。
- 不把平台 Cookie、签名算法和页面抓取逻辑写进通用播放器。
- 不让页面直接持有 native handle。
- 不把所有平台的失败重试写成一个固定策略。

最小可行目标是先完成“统一播放器状态 + Surface 生命周期 + 首帧封面策略”，这三项最可能直接改善播放体验。
