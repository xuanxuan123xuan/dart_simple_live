# 跨平台聚合搜索设计

> 状态：**已实施（路线 A）**。后续编号章节保留实施前基线，下方“实施状态”记录当前实现、治理措施和验收结果。

Roadmap 原文：**一个搜索框同时搜五大平台，结果按平台分区聚合展示。**标注「工程量较大」。

## 实施状态（2026-08-06）

已完成一个搜索框的五平台并发聚合搜索：聚合页只取每个平台第一页，按平台独立展示加载、成功、空结果和错误；“查看更多”进入单站搜索页，单站页保留完整分页。主 App、TV 房间搜索和主播搜索均接入同一套 core 搜索协议。

- 在 `simple_live_core` 增加不暴露 Dio 的 `CoreCancellation`、`CoreCancellationToken` 和 `CoreCancelledError`。新关键词、模式切换、清空、超时、页面销毁和 TV 切站都会取消旧请求。

## 1. 一句话结论

**Roadmap 那句「工程量较大」是准确的，但大在意想不到的地方 —— 不是并发难写，而是五个平台的搜索契约根本不可比。**

UI 层已经是「五平台 TabBar」结构，改成聚合展示不难。真正的成本在数据层：返回模型不带平台标识、`hasMore` 有五种互不兼容的语义且上层根本不读、每页条数差 4 倍、一个平台的主播搜索是伪实现、一个平台永不抛异常。

**这个功能的实际形态取决于一个前置决策：是「五路并发一次性展示」还是「保留分页」。** 选前者能绕开大半障碍，选后者要先做一轮抽象层重构。

## 2. 抽象层现状（已核实）

`simple_live_core/lib/src/interface/live_site.dart:15` —— 基类是 `class LiveSite`，**不是 abstract、不是 interface**，所有方法都有默认空实现。

```dart
// :31
Future<LiveSearchRoomResult> searchRooms(String keyword, {int page = 1}) {
  return Future.value(LiveSearchRoomResult(hasMore: false, items: <LiveRoomItem>[]));
}
// :38
Future<LiveSearchAnchorResult> searchAnchors(String keyword, {int page = 1}) { ... }
```

三个事实：
- 参数只有 `keyword` + `page`（默认 1）。**没有 pageSize** —— 每页条数由各站点内部硬编码。
- **没有 `CancelToken`** —— 抽象层不透传取消能力（见 §7）。
- 站点身份 `id`(:17) / `name`(:20) 是可变 `String` 字段而非 getter。

### 返回模型的致命缺口

`simple_live_core/lib/src/model/live_search_result.dart`：
- `LiveSearchRoomResult`(:4)：`bool hasMore` + `List<LiveRoomItem> items`
- `LiveSearchAnchorResult`(:13)：`bool hasMore` + `List<LiveAnchorItem> items`

**两者都不带 siteId，也不带 total/numFound。** 聚合展示最基本的「这条结果属于哪个平台」在数据层不存在，必须由调用方外挂。

元素模型字段还不重叠：
- `LiveRoomItem`(`live_room_item.dart:3`)：`roomId` / `title` / `cover` / `userName` / `online`
- `LiveAnchorItem`(`live_anchor_item.dart:3`)：`roomId` / `avatar` / `userName` / `liveStatus`

**无公共基类、无公共接口** —— 房间结果和主播结果在类型层面完全分家。

## 3. 五个平台的实现差异（这是主要成本）

| 平台 | searchRooms | searchAnchors | 文件 |
|---|---|---|---|
| B站 | :420 | :457 | `bilibili_site.dart` |
| 斗鱼 | :265 | :329 | `douyu_site.dart` |
| 虎牙 | :588 | :633 | `huya_site.dart` |
| 抖音 | :1078 | :1211 | `douyin_site.dart` |
| 快手 | :371 | :434 | `kuaishou_site.dart` |

### 3.1 抖音的 searchAnchors 是伪实现

`douyin_site.dart:1211-1240` 直接复用搜房间结果：

```dart
final result = await searchRooms(keyword, page: page);   // ← 搜的是房间
...
items: rooms.map((room) => LiveAnchorItem(
  roomId: room.roomId,
  userName: room.userName,
  avatar: room.cover,        // ← 用房间封面冒充头像
  liveStatus: true,          // ← 硬编码
)).toList(),
```

其余四家都有独立主播搜索端点（B站 `search_type=live_user`、斗鱼 `japi/search/api/searchUser`、虎牙 `response["1"]`、快手 `live_api/search/author`）。

**后果：主播模式的聚合结果里，抖音分区的数据质量与其他四家不可比**（头像是封面、直播状态恒真）。

### 3.2 快手永不抛异常

`kuaishou_site.dart:371-461` 是「双通道 + 静默兜底」结构：

```dart
try {
  var result = await _searchLiveStreams(keyword, page: page);   // 通道1
  if (result.items.isNotEmpty || page > 1) return result;
} catch (_) {}                                                  // ← 吞
if (page > 1) return LiveSearchRoomResult(hasMore: false, items: []);
try {
  return await _searchRoomsByOverview(keyword);                 // 通道2，仅第一页
} catch (_) {
  return LiveSearchRoomResult(hasMore: false, items: []);       // ← 吞
}
```

**「快手挂了」和「快手没搜到」在调用方看来完全一样。** 其他四家失败都会抛（B站/虎牙让 `CoreError` 冒泡，斗鱼/抖音显式 `throw Exception`）。

聚合时的直接影响：快手永远不会触发错误分支，永远显示「无结果」。

### 3.3 分页机制五种写法

| 平台 | page 语义 | pageSize | hasMore 判定 |
|---|---|---|---|
| B站 | 直传 | 无参数，服务端默认 | `items.length >= 40`（魔数 40 与未声明的页大小耦合） |
| 斗鱼 | 直传 | 显式 20 | `relateShow.isNotEmpty` —— **非空即 true，永不自然终止** |
| 虎牙 | `start: (page-1)*20` | `rows: 20` | `numFound > page*20` —— **唯一有真实总数的平台** |
| 抖音 | `offset: (page-1)*10` | `count: "10"` | `items.length >= 10` |
| 快手 | 房间直传 / 主播 +`count:15` | 房间未知 / 主播 15 | 通道1 非空；**通道2 恒 false** |

三个要点：
- page 起点统一（都从 1 起），但换算三种：直传 / `(page-1)*20` / `(page-1)*10`
- 每页条数 ~40 / 20 / 20 / 10 / 15 —— **同一个「第 N 页」拿到的条数差 4 倍**
- `hasMore` 语义不可比：虎牙是真分页信息，斗鱼是「非空恒 true」，快手 overview 通道恒 false

### 3.4 上层根本不读 hasMore

`SearchListController.getData`（`search_list_controller.dart:24-36`）只 `return result.items`，**`hasMore` 字段被丢弃**。

`BasePageController.loadData()`（`base_controller.dart:80-114`）判断的是 `result.isNotEmpty`（:98-107）。

而且 `BasePageController.pageSize = 24`（:61）传给 `getData(page, pageSize)`，但 `SearchListController` **把 pageSize 参数完全丢弃** —— **24 这个值在搜索路径上是死值**。

### 3.5 凭证/反爬差异

| 平台 | 凭证需求 | 冷启动 HTTP 轮次 |
|---|---|---|
| 虎牙 | **零凭证**（不带任何 header/cookie/UA） | **1** |
| 斗鱼 | 现场生成 32 位随机 hex 作 `dy_did`/`acf_did`（不联网） | **1** |
| B站 | `buvid3`/`buvid4` cookie，**搜索不走 wbi 签名** | **1 或 2**（`buvid3` 空时先 `getBuvid()`） |
| 抖音 | ttwid + `__ac_nonce` + ~30 个伪造指纹参数 | **2 串行，不可跳过** |
| 快手 | `_headersWithCookie` + 动态 referer | **1 或 2 串行** |

**抖音是最重的一家。** `douyin_site.dart:1078-1200` 单次 `searchRooms` 是两次串行 HTTP：先 `HEAD https://live.douyin.com` 抓 cookie（:1133-1156），再发带 ~30 个伪造浏览器指纹参数的搜索 GET（:1084-1129）。

反爬检测两处（:1180-1186）：
```dart
if (result == "" || result == 'blocked') throw Exception("抖音直播搜索被限制，请稍后再试");
if (result is Map && result["status_code"] == 2483) throw Exception("抖音搜索需要登录，...");
```

`:1131` 有一行被注释掉的 `//var requlestUrl = await getAbogusUrl(...)` —— **搜索路径当前没有 a_bogus 签名**，而房间详情等路径有。`CoreError` 里还专门为抖音留了 444 文案（`core_error.dart:28-29`）「抖音访问过于频繁或触发风控限制(444)」—— **抖音风控在这个代码库里是既成事实**。

木桶效应就在这里：抖音固定 2 轮串行 + 风控概率，且**串行发生在方法内部**，无法从外部拆解并行。

值得注意：`douyin_site.dart` 内部有大量 `_logElapsed` 耗时埋点（:51-54），说明抖音的慢被开发者关注过，但 **`searchRooms` 本身没有埋点** —— 搜索路径无耗时观测。

## 6. 并发先例（已核实 7 处 `Future.wait`，0 处 `Future.any`）

三种风格并存：

**(a) 无隔离，一败俱败。** `huya_site.dart:124`：
```dart
final subCategories = await Future.wait(categories.map((item) => getSubCategores(item.id)));
```
任一失败整个 `getCategores()` 抛出。**这是最接近聚合搜索场景的先例，而它恰好是最脆弱的写法。**

**(b) 加总预算超时。** `network_diagnose_service.dart:124-135`：
```dart

} on TimeoutException {

```
`totalBudget` 默认 1800ms(:113)。**库里唯一的「并发 + 总时间预算 + 降级」范式。**

**(c) worker 池 + 分组限流。** `follow_service.dart:869-895`：
```dart
final douyinTargets = orderedTargets.where((item) => item.siteId == Constant.kDouyin).toList();

for (final group in [douyinTargets, otherTargets]) {
  final workerCount = isDouyinQueue ? 1 : group.length.clamp(1, 2).toInt();
  ...
```

**这段已经在实践中承认「抖音必须单并发，其他平台最多 2 并发」。** 另有专门的 `douyin_follow_refresh_limiter.dart`（内容未核实）。

**没有一个先例完全对口。** (c) 的分组限流思想最贴合，但它是「串行队列 + 有序进度回调」模型，不是「五路并发、各自成功各自渲染、失败只标该分区」。(b) 提供了超时预算写法。**「单平台失败不拖垮整体」在搜索场景下没有先例可抄。**

## 7. 网络层与取消

`simple_live_core/lib/src/common/http_client.dart`：
- **dio 单例**(:9-12)
- **统一 20 秒 × 3 超时**(:16-22)：`connectTimeout` / `receiveTimeout` / `sendTimeout` 全 20s，**无 per-request 覆盖能力**
- 唯一拦截器 `CustomInterceptor`(:23) **只做日志**，配 `HttpLogSanitizer` 脱敏 —— **没有统一 UA/header 注入**，每站点各自手写

**五路并发聚合，最坏用户等 20 秒；抖音因两轮串行可达 40 秒。**

### CancelToken：能力存在但断在抽象层

`HttpClient` 四个方法 `getText`/`getJson`/`postJson`/`head` 都有 `CancelToken? cancel` 形参并透传给 dio。

**但 `LiveSite.searchRooms`/`searchAnchors` 签名里没有 CancelToken**，五个站点实现调 `HttpClient` 时也都不传。

已核实全库 `CancelToken` 命中仅 15 处，**全部是形参声明本身，零处实际构造或传入实例**。

**后果：「用户改关键词时取消上一轮」当前不可能实现。** 需要改抽象层签名 + 五个站点实现 + 三个 app 调用链。这对聚合搜索比对单平台搜索重要得多 —— 五路并发时用户改词，五个请求全都在跑。

## 8. 节流与错误处理

**搜索路径上零节流零重试零去抖**（已核实）。

其他路径有成熟先例（`bilibili_site.dart`）：
- `_getRoomPlayInfo`(:254-299) —— 429 退避重试，`retryDelays = [800ms, 1600ms]`
- `_throttlePlayInfoRequest`(:290-303) —— **static 队列 + 最小间隔 450ms 串行化**

唯一作用于搜索的是 UI 层 2 秒刷新冷却（`base_controller.dart:55`），且是 **toast 拒绝式而非排队式，且只拦 `refreshData` 不拦 `loadData`**。

错误抛出**三种类型不一致**：`CoreError`（extends **`Error` 而非 `Exception`**，`core_error.dart:1`）/ `Exception` / 不抛。上层 `handleError` 只能做字符串清洗（`base_controller.dart:46-48`）：
```dart
exception.toString().replaceAll("Exception:", "")
```

另一个并发隐患：B站 `getHeader()` 内部 `if (buvid3.isEmpty)` 会触发 `getBuvid()` 网络请求，**这个初始化没有并发保护** —— 五路并发首次搜索时可能同时打。

## 10. 设计方向：两条路线

### 路线 A：一次性并发聚合（推荐）

放弃分页，五路并发各取第一页，按平台分区展示，「查看更多」跳转到该平台的单平台 tab（复用现有 UI）。

绕开的障碍：
- ✅ `hasMore` 五种语义 —— 不用了
- ✅ 每页条数差 4 倍 —— 分区展示，条数不齐可接受（甚至可以截到统一条数）
- ✅ `BasePageController` 的 pageSize 死值 —— 不走它

必须处理的：
- 平台标识外挂（返回模型不带 siteId）
- 错误分区化（每个分区独立的空/错/载态）
- 总时间预算（照抄 `network_diagnose_service.dart:124` 的 `.timeout(totalBudget)`）
- 抖音降级策略（它 2 轮串行，大概率最后返回）

成本主要在 UI（分区容器 + 每区独立状态）和一个聚合 service。

### 路线 B：保留分页的完整聚合

需要先做抽象层重构：`hasMore` 语义统一、pageSize 进签名、`CancelToken` 透传、错误类型统一。

**这是一轮跨 `simple_live_core` + 五个站点 + 三个 app 的重构**，且改的是所有搜索路径（不只是聚合），回归面很大。

**倾向路线 A。** 理由：它把 §3.3/§3.4 的全部不兼容问题从「必须解决」变成「不相关」，而用户对聚合搜索的核心诉求（一次看到五个平台有什么）在路线 A 下已经完全满足。分页需求可以通过「跳转到单平台 tab」满足 —— 那条路径现在就能用。

---

## 11. 无论哪条路线都要处理的

1. **平台标识** —— 返回模型不带 siteId，聚合层必须外挂（包装类或 `Map<String, Result>`）
2. **抖音单独限速** —— `follow_service.dart` 已经承认它必须 workerCount=1；聚合时五路齐发会加剧风控（444 / 2483 / blocked 三种）
3. **快手的静默失败** —— 它永不抛，「挂了」和「没结果」不可分。要么改快手实现（动 core），要么接受它永远显示无结果
4. **总时间预算 + 部分结果渲染** —— 20s 统一超时下，不能等最慢的
5. **B站 `getBuvid()` 并发保护** —— 首次搜索时五路可能同时打
6. **CancelToken**（路线 A 下也需要）—— 用户改词时五个请求都在跑，不取消是明显的浪费和风控风险
7. **TV 端要不要覆盖** —— 两套 UI 零复用，覆盖等于两倍工作量

## 13. 一句话总结

UI 骨架现成（已经是五平台 TabBar），并发范式有先例（虽然最贴近的那个写法最脆弱），**真正的成本在五个平台搜索契约的不可比性**。选「一次性并发聚合，分页交给单平台 tab」能把大半不兼容问题变成不相关问题 —— 这是把这个功能从「较大工程」压回「中等工程」的关键决策。
