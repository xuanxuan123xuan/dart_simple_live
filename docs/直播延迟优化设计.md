# 直播延迟优化设计

> 状态：设计草案，未动任何代码
> 分支范围：dev
> 撰写日期：2026-08-04
> 观测到的现象：相比各平台官方 App，延迟高出约 5–10s

---

## 1. 目标与非目标

**目标**

- 把稳态延迟差距从 5–10s 压到 1–3s 残差
- 消除「延迟随观看时长单调增长」的漂移
- 消除「一次偶发切线导致该站点永久高延迟」的固化

**非目标（明确不追求）**

- 追平官方 App。官方持有私有低延迟协议（如抖音 RTM 类）、按 App 签名放行的低延迟流变体、深度定制原生播放器，这三样本项目都拿不到。
- 精确显示「绝对延迟秒数」。flv 流通常不带挂钟时间戳（HLS 才有 `EXT-X-PROGRAM-DATE-TIME`），无服务端时间基准时只能测量「缓冲/漂移」，测不出绝对延迟。这会限制「修好了」能被验证到什么程度，需在设计阶段就接受。

---

## 2. 诊断结论摘要

延迟不是单点 bug，是四层叠加，每层都缺一道「直播意识」。全项目 grep 确认：**没有任何一处代码显式偏好 flv 或排除 hls**。

| 层 | 问题 | 归属 |
|---|---|---|
| L1 选流 | 各站点 urls 顺序由 API 返回顺序或写入顺序决定，无延迟等级概念 | 本项目逻辑 |
| L2 选线 | 默认线路按 TCP 握手 RTT 选，协议盲 | 本项目逻辑 |
| L3 记忆 | 线路记忆按站点（非按房间）固化，自动切线也会写入 | 本项目逻辑 |
| L4 播放器 | 三平台均跑各自播放器的点播出厂默认，零低延迟调优 | 「没做」而非「做错」 |

L1/L2/L3 是本项目自己造成的，L4 是缺失。

---

## 3. 5–10s 这个量级的诊断含义（决定动手顺序）

这个数字排除了最坏假设，但没排除次坏的：

- **排除**「经典 HLS」——10s 分片 × 3 缓冲，差距会是 20–30s
- **两个都吻合**：
  - (a) 已在放 flv，纯粹播放器没调优
  - (b) 在放短分片 HLS/fMP4（2s 分片 × 3 ≈ 6s）

**(a) 与 (b) 的药方完全不同**：(a) 要调播放器属性（L4），(b) 要改选流逻辑（L1/L2）。

因此**第 0 阶段观测是强制前置**。没有它就动手，等于拿延迟换卡顿，且没有任何指标能判断换亏还是换赚。

## 阶段 0：先观测，不改行为（强制前置）

**目的**：分清病因是 (a) 还是 (b)，并为后续每一步建立可比基线。

**改动位置**

| 位置 | 改动方向 |
|---|---|
| `simple_live_app/lib/modules/live_room/live_room_controller.dart` `initPlaylist` 附近 | 已有 `Log.i("准备打开播放器：…")` 打了 URL。扩展为记录**协议等级判定结果**（flv / hls / fmp4 / rtmp / unknown），而非只记 URL 原文 |
| `simple_live_app/lib/modules/multi_room/multi_room_player_controller.dart` `sampleTelemetry` | 已在读 `cache-speed`。**追加 `demuxer-cache-duration` 采样**，这是漂移的直接观测量 |
| 单开页同等位置 | 单开页目前无对应遥测，需补一份最小版本 |

**为什么是这两个属性**

- `demuxer-cache-duration` 直接反映「本地已缓冲多少秒」，即客户端侧延迟贡献
- 它随时间的**曲线形状**比绝对值更重要：单调上升 = 漂移累积，平稳 = 只有起播偏移

**观测产出与分支决策**

| 观测结果 | 判定 | 优先动 |
|---|---|---|
| 实际协议是 flv，且 cache-duration 起播即偏高 | (a) | 阶段 1（播放器调优） |
| 实际协议是 hls/fmp4 | (b) | 阶段 3（选流排序） |
| cache-duration 随时长单调上升 | 漂移 | 阶段 2（追帧环），与 (a)/(b) 无关，必做 |

**成本**：低。**风险**：无，纯只读观测。

## 阶段 1：播放器低延迟调优（L4）

### 1.1 mpv 侧（桌面 / Android media_kit 路径）

**现状（已核实）**

media_kit 从 pub cache 消费 1.2.6（`third_party/` 只 vendored 了 `media_kit_video`）。初始化实际下发的属性见 `media_kit-1.2.6/lib/src/player/native/player/real.dart:2389-2438`：

```
demuxer-max-bytes = 32MB     demuxer-max-back-bytes = 32MB
cache = yes                  cache-on-disk = yes
keep-open = yes              hr-seek = yes            network-timeout = 5
```

而 `cache-secs`、`demuxer-readahead-secs`、`profile=low-latency`、`untimed`、`audio-buffer`、`cache-pause*`、`stream-buffer-size` **一个都没设**，全走 libmpv 自身默认。

App 侧 `PlayerConfiguration` 只传 `title` + `logLevel`，`bufferSize` 未传 → 吃 32MB 默认。

**改动位置（单点，这是本设计最好的一个性质）**

`simple_live_app/lib/services/mpv_options_service.dart`

现有三档 profile（`performance` / `balanced` / `balancedDesktop` / `quality`）**全是画质键**（`scale` / `cscale` / `dscale` / `deband` / `correct-downscaling` / `sigmoid-upscaling`），grep `cache|buffer|demuxer|latency` 零命中。

方向：**新增一个与画质档位正交的「直播延迟档」维度**，经由已有的 `applyToPlayer(Player)` 单点注入。不要塞进现有画质 profile —— 两者语义无关，混在一起会让「高画质」隐含「高延迟」。

**关键设计考量：`profile=low-latency` 是双刃剑**

它不只是调小缓冲，会一并带上：

- `vd-lavc-threads=1` —— 弱设备放 1080p60 会掉帧
- `stream-buffer-size=4k` —— 抖动大的网络更容易卡
- `fflags=+nobuffer`、`analyzeduration` 压到极小 —— 关掉 libavformat 探测缓冲，这是它对**起播时间**贡献最大的部分
- `cache-pause=no`、`audio-buffer=0`

因此不建议无条件全量套用。建议**拆成可分级的档位**，而不是一个开关：

| 档 | 含义 | 适用 |
|---|---|---|
| 关 | 现状行为 | 弱网 / 弱设备 / 出问题时的回退位 |
| 温和 | 只压探测与音频缓冲，不动解码线程与 stream-buffer | 默认建议值 |
| 激进 | 接近完整 `low-latency` | 强网 + 强设备 + 用户明确选择 |

**`demuxer-max-bytes` 是红鲱鱼**

大家最先想动的旋钮，但它是**上限不是目标值**。改小它不降稳态延迟，只是给漂移设个天花板（防止一次长卡顿后偏移无界增长）。可以顺手调，但不要指望它带来收益。

**顺带发现：`cache-on-disk=yes` 对直播无意义**

media_kit 默认开启（`real.dart:2401`）。对一条无限长的直播流把数据往磁盘写，纯属 IO 开销，长时间观看还有磁盘占用问题。**建议单独查证实际影响后关掉**，但需注意这是覆盖上游默认值，要确认不会影响 seek/回放等其他功能。

**平台例外（已存在，必须保留）**

`applyToPlayer` 目前在 iOS 上直接 return（注释：libmpv vo + gpu 系选项会破坏色彩管线 → 偏绿/偏紫）。新增的延迟选项若与 vo 无关，理论上 iOS 可以放行，但**需单独验证**，不要顺手把 iOS 的早退去掉。

### 1.2 Android ExoPlayer 侧（`video_player` 路径）

**现状（已核实）**

`video_player` 是 git 依赖（不在 `packages/`，实际在 pub git cache），Android 侧就一行裸构建：

`video_player_android/.../VideoPlayer.java:79`

```java
ExoPlayer exoPlayer = new ExoPlayer.Builder(context).build();
```

**没有 `setLoadControl`、没有 `MediaItem.LiveConfiguration`、没有 `targetOffsetMs`**，跑 ExoPlayer 2.18.7 的 `DefaultLoadControl` 出厂值。HLS live target offset 完全由 manifest 决定，客户端零覆盖。

**改动方向**

- 注入 `DefaultLoadControl`，调小 `bufferForPlaybackMs` / `minBufferMs`
- 设置 `MediaItem.LiveConfiguration` 的 `targetOffsetMs`

**这条是三个平台里最好调的** —— ExoPlayer 自带 `DefaultLivePlaybackSpeedControl`，追帧机制是现成的，不需要像 mpv 那样自己写（见阶段 2）。

**但有前置问题**：需先确认该路径在当前版本**是否真的被使用**（OHOS 走 `video_player`，Android 主路径走 media_kit）。若 Android 不走这条，收益仅限 OHOS 之外的验证价值，优先级应下调。改动落在 fork 仓库而非本仓库，发布链路更长。

### 1.3 OHOS AVPlayer 侧

**现状（已核实）**

`simple_live_app/third_party/video_player_ohos/ohos/src/main/ets/components/videoplayer/VideoPlayer.ets:103`

`PlaybackStrategy` 是**空字面量 `{}`**，`preferredBufferDuration` 等字段一个没填。

**两个改动点，顺序有依赖**

1. **结构先修**：该分支**只在 `headers` 非空时才走** `setMediaSource`。无 header 时直接赋 `avPlayer.url`，连 `PlaybackStrategy` 都不经过。要先让两条路径都能带策略，否则填了字段也可能不生效。
2. **再填策略**：`preferredBufferDuration` 设 1–2s。

**注意**：需核对项目 OHOS SDK 版本。较新 API 提供 `preferredBufferDurationForPlaying`、`showFirstFrameOnPrepare` 等更细的字段，可用性随版本变化，不要照抄文档。

### 1.4 TV app 的现成坑

`simple_live_tv_app/lib/modules/live_room/player/player_controller.dart:24` 唯一那处 `bufferSize` 尝试是**被注释掉的**（引用 media-kit issue #549）。

## 阶段 2：追帧环（最重要，且与 (a)/(b) 病因无关，必做）

### 2.1 为什么单调 buffer 参数不够

这一节是整份设计里最容易被忽略、但常常是主因的部分。

多数直播 CDN 在客户端连上的瞬间会先吐一段**服务端缓存的历史帧**（通常一个完整 GOP 到几秒），好让客户端能立刻出画。mpv 会老老实实以 1x 速度把这段历史播完 —— **然后永远保持这个偏移**。

同样的机制让 mpv 在一次卡顿之后永久落后：缓冲涨上去就再也不会掉下来，而直播流不可 seek，没法跳到边缘。

**结论：只调 buffer 参数，最好情况也只能减少起播那一次的偏移，不能修复运行中的漂移累积。**

### 2.2 mpv 没有内置追帧

ExoPlayer 有 `DefaultLivePlaybackSpeedControl`，**mpv 没有对应物**。需要在 app 层自己实现。

### 2.3 设计方向

一个基于观测量的闭环：

```
监听 demuxer-cache-duration
  ├─ 超上阈值 → speed = 1.05 ~ 1.10（悄悄追）
  ├─ 回到目标区间 → speed = 1.0
  └─ 低于下阈值 → 维持 1.0（不要减速，减速等于主动加延迟）
```

**基础设施已经齐了**：`NativePlayer.setProperty` 已在用（`MpvOptionsService.applyToPlayer`），属性采样代码已在用（多开页 `sampleTelemetry`）。这是几十行的事。

**改动位置**

| 位置 | 角色 |
|---|---|
| 新增一个 service（建议 `simple_live_app/lib/services/` 下，与 `MpvOptionsService` 平级） | 追帧环本体，输入 cache-duration，输出 speed |
| `player_controller.dart` / `multi_room_player_controller.dart` | 起停挂载点，与 `initializePlayer` 生命周期对齐 |

### 2.4 风险与调参考量

| 风险 | 说明 |
|---|---|
| 音调变化可感知 | 1.10 已接近人耳可察阈值。建议上限 1.05–1.08，宁可追得慢 |
| 与音频重采样交互 | 需确认是否要配合 `audio-pitch-correction`（mpv 默认开启）|
| 阈值抖动导致 speed 反复切换 | 必须做**滞回**（上下阈值分离）+ 最小驻留时间，否则会听到速度来回变 |
| 多开页 N 路各自追帧 | N 个独立环，需确认 CPU 开销与相互干扰 |
| 弱网误判 | 网络抖动造成的 cache 堆积与「服务端历史帧偏移」难以区分，追帧可能加剧卡顿。需要下限保护 |

### 2.5 若 Android 走 ExoPlayer 路径

直接启用 `DefaultLivePlaybackSpeedControl` 即可，不要自己实现。仅 mpv 路径需要手写环。

## 阶段 3：选流按延迟等级排序（L1）

### 3.1 现状（已核实）

| 站点 | urls 顺序由什么决定 | 线路1 可能是 |
|---|---|---|
| 抖音 | 硬编码写入顺序 flv→hls（`douyin_site.dart:1029`、`:997` 两个分支一致） | flv ✅ |
| 虎牙 | 无条件拼 `.flv`，hls 分支全被注释（`huya_site.dart:310`） | flv ✅ |
| B站 | 请求 `protocol:"0,1"` + `format:"0,2"`，flv 与 fmp4 混在同一 list，**唯一排序是 mcdn 置后**（`bilibili_site.dart:214`） | fmp4/hls ❌ |
| 快手 | JSON 递归遍历顺序，过滤条件只有 scheme（`kuaishou_site.dart:189`） | 不确定 ❌ |
| 斗鱼 | 服务端 CDN 列表顺序（`douyu_site.dart:148`） | 服务端决定 ❌ |

虎牙是唯一延迟正确的站点 —— 因为它物理上只能出 flv。

顺带一个细节：虎牙把 `sHlsAntiCode` 解析进了 `HuyaLineModel`（`huya_site.dart:442`）但活代码从不读，那是「未使用」不是「主动排除」。

### 3.2 改动方向

**新增一个共享的「延迟等级判定」工具**，建议放 `simple_live_core/lib/src/common/` 下（与 `network_diagnose_service.dart` 平级，因为阶段 4 也要用它）。

输入 URL，输出等级：

```
flv / rtmp        → 低延迟档
fmp4 / hls(短分片) → 中
hls(未知分片)      → 高
unknown           → 中（保守）
```

判定依据是 URL 路径/扩展名/查询参数，无法从 URL 判断分片时长，所以 hls 只能保守归高。

各站点 `getPlayUrls` 返回前按等级**稳定排序**（等级内保持原有顺序，以免破坏 mcdn 置后、scdn 置后这些既有规则）。

### 3.3 关键约束：B站必须「排序」不能「过滤」

**部分清晰度 / HEVC 编码只有 fmp4 形态。硬过滤掉非 flv 会直接丢线路，导致某些清晰度无法播放。**

同理不建议把请求参数改成 `protocol:"0"` + `format:"0"` —— 那是服务端过滤，会让部分清晰度直接拿不到地址。宁可全都要回来，本地排序。

### 3.4 UI 侧配套

当前 UI 只显示「线路1 / 线路2」，纯索引，用户无从判断协议。

方向：**线路名带上协议/延迟标注**（如「线路1 · 低延迟」）。这不减延迟，但让用户可以自救，也让问题反馈可诊断。改动位置在线路选择器（`live_room_controller.dart` 的 `currentLineInfo` 与 `player_controls.dart` 的线路面板）。

## 阶段 4：选线与记忆（L2 / L3，「防止变坏」）

这一阶段基本不直接降延迟，但它决定前面三阶段的收益**能不能保持住**。

### 4.1 测速协议盲（L2）

**现状（已核实）** `simple_live_core/lib/src/common/network_diagnose_service.dart:95` `findFastestLine`：

- **纯 TCP connect 测速** —— 唯一网络操作是 `Socket.connect(host, port)` 然后立刻 `close()`（`:58`），不发 HTTP 请求，不拉一个字节码流
- **完全不看 URL 路径**，只取 `uri.host` / `uri.port`。`.flv` 和 `.m3u8` 在它眼里没有区别
- **按 host 去重**，同 host 多条线路塌缩成一次探测，且只保留该 host 的**第一个**索引
- 超时：单连接 800ms，总预算 1800ms，`samples = 1`
- 所有失败路径都返回 `0`
- `autoSelectFastestLine` **默认开启**（`app_settings_controller.dart:2595`）

**后果**：一个握手 RTT 更低的 HLS 边缘节点会稳赢 RTT 稍高的 flv 节点，App 把 20s 延迟的线路标为「最快」。**握手快 ≠ 流延迟低**，这两个量在直播里几乎无关。

**改动方向**：改成**先按延迟等级分桶，桶内再比 RTT**。复用阶段 3 的等级判定工具。即「最快」的语义从「握手最快」变成「在最低延迟档里握手最快」。

**附带问题**：host 去重逻辑在分桶后需要重新审视 —— 同一 host 上的 flv 与 hls 现在属于不同桶，不应再塌缩成一条。

### 4.2 记忆固化（L3）

**现状（已核实）**

- 记忆粒度是**按站点**，不是按房间（`live_room_controller.dart:383`，`data[site.id]`）。存储键 `kRoomQualityMemory` 名字有误导性 —— B站所有房间共用同一个 `line` 索引
- 记忆**优先级高于测速**：有记忆时 `findFastestLine` 根本不会被调用（`:2075`）
- `changePlayLine` 只有 6 行，**每次调用都立刻写记忆**（`:2129`），包括两处失败自动切线 `changePlayLine(currentLineIndex + 1)`（`:2333`、`:2382`）
- 记忆的是**裸整数索引**，不绑定 host 或格式

**失效链条**

```
flv 线路瞬时抽风
  → mediaEnd() 重试 2 次失败
  → 自动跳线路2（可能是 HLS）
  → 立刻写进「按站点」的记忆
  → 该站点所有房间从此默认 HLS，永久多延迟，且不再测速
```

用户唯一自救方式是手动切回去 —— 但 UI 上看不出协议（见 3.4）。

**改动方向（三条，可独立实施）**

1. **区分「用户主动选择」与「自动故障切换」** —— 只有前者写记忆。这是最小、收益最高的一条。
2. **记忆存签名而非裸索引** —— 存 host + 格式等级，恢复时按签名匹配。裸索引在 urls 列表长度/顺序变化后本身就会指错。
3. **记忆加时效或降级** —— 让记忆不再无条件压过测速，比如记忆命中但等级低于当前可得最优档时重新评估。

### 4.3 起播串行请求（仅影响首帧，不影响稳态）

| 位置 | 问题 |
|---|---|
| `douyu_site.dart:148` | **逐个 CDN 串行 await POST**，N 个 CDN 就是 N 次串行往返才能开始播 |
| `bilibili_site.dart` `_getRoomPlayInfo` | 节流 + 重试退避 `[800ms, 1600ms]` |
| `findFastestLine` | 本身是 awaited，最坏再加 1.8s（`totalBudget`）|

**方向**：斗鱼改并发。B站退避策略与节流需评估是否可放宽（注意这些可能是为规避风控加的，改动前需查提交历史确认意图）。测速可考虑不阻塞首帧 —— 先起播默认线路，测速结果后到再决定是否切。

## 5. 性价比汇总

| 措施 | 阶段 | 预期收益 | 成本 | 风险 |
|---|---|---|---|---|
| 协议 + cache-duration 观测 | 0 | 0（但解锁其余全部） | 低 | 无 |
| mpv 低延迟档（`MpvOptionsService` 单点注入） | 1 | 2–4s，含起播 | 很低 | **中**：弱设备掉帧、弱网更易卡 |
| app 层追帧环 | 2 | 消除漂移累积，长时间观看收益最大 | 低 | 低，阈值调不好有音调变化 |
| URL 按延迟等级排序 + UI 标注协议 | 3 | 命中 (b) 时 5–15s | 低 | 低（B站须排序不得过滤） |
| `findFastestLine` 分协议桶 | 4 | 消除「把 HLS 标成最快」 | 低 | 低 |
| 记忆存签名 + 自动切线不写记忆 | 4 | 不减延迟，防止悄悄变差 | 中 | 低 |
| OHOS `preferredBufferDuration` | 1 | OHOS 端可能 2–4s | 低 | 需核对 SDK；须先修无 header 分支 |
| ExoPlayer `LoadControl` + `LiveConfiguration` | 1 | 仅当该路径真在用 | 低 | 低，自带追帧最好调 |
| 斗鱼起播并发化 | 4 | 仅首帧 1–3s | 低 | 低 |
| `cache-on-disk=no` | 1 | 未知，需查证 | 低 | 低，但覆盖上游默认需验证副作用 |
| TV app `playerBufferSize` 接上或撤掉 | 1 | 0（修误导） | 低 | 低 |

**`demuxer-max-bytes` 刻意未列入收益项** —— 上限不是目标值，改小它不降稳态延迟，只是给漂移设天花板。这是最容易被误当成主旋钮的红鲱鱼。

## 6. 建议推进顺序（顺序本身很重要）

```
阶段 0 观测          ← 强制前置，不改行为
   ↓
   ├─ 测出 (a) → 阶段 1 mpv 低延迟档（温和档起步）
   └─ 测出 (b) → 阶段 3 协议排序
   ↓
阶段 2 追帧环        ← 前两步都不解决漂移，必做
   ↓
阶段 4 选线/记忆/UI  ← 收尾，锁住前面的收益
```

**为什么不能先做阶段 1**：没有阶段 0，动阶段 1 等于拿延迟换卡顿，而且没有任何指标能告诉你换亏了还是换赚了。

**为什么阶段 2 不能省**：阶段 1 只能减少起播那一次的偏移。不做追帧环，用户看半小时之后延迟会回到原点，会得到「修了没用」的结论。

**为什么阶段 4 排最后**：它不产生可感知收益，但如果不做，阶段 1–3 的收益会被一次偶发切线永久抹掉。

## 7. 验证方案

**每阶段必须同时记录三个量，不能只看延迟**：

| 指标 | 观测方式 | 作用 |
|---|---|---|
| `demuxer-cache-duration` 曲线 | 阶段 0 建立的遥测 | 主指标：延迟与漂移 |
| 卡顿次数 / 缓冲事件频率 | mpv 事件 / ExoPlayer 回调 | 防止「拿卡顿换延迟」 |
| 掉帧率（`estimated-vf-fps` 或 drop 计数） | 多开页已有 fps 采样可扩展 | 防止 low-latency 档在弱设备上掉帧 |

**测试矩阵维度**

- 站点：五个全覆盖（虎牙作为 flv 对照组，B站作为 fmp4 主场景）
- 平台：Windows / Android / OHOS / iOS / TV（各自播放器路径不同，结论不可平移）
- 网络：良好 / 抖动 / 弱网（low-latency 档的风险只在后两者显现）
- 设备档位：至少一台弱设备跑 1080p60

**基线要求**：改动前后同一房间、同一清晰度、同一网络下对比。**绝对延迟测不准（见非目标），所以基线比的是相对差值与曲线形状，不是秒数。**

## 8. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| low-latency 档在弱网/弱设备上恶化体验 | 高 | 分级档位 + 保留「关」作为回退位；不设为强制默认 |
| 追帧环音调变化被用户察觉 | 中 | speed 上限压到 1.05–1.08；滞回 + 最小驻留 |
| B站硬过滤非 flv 导致部分清晰度不可播 | 高 | 只排序不过滤；请求参数不动 |
| 记忆改签名后与旧数据不兼容 | 中 | 需设计迁移或容错读取，旧裸索引数据要能优雅失效 |
| 改 `video_player` fork 发布链路长 | 中 | 先确认该路径是否真被使用，再决定投入 |
| B站节流/退避可能是风控规避措施 | 中 | 改动前查提交历史确认原始意图 |
| 覆盖 media_kit 上游默认（`cache-on-disk`）| 低 | 单独验证 seek/回放等功能无回归 |
| iOS 早退逻辑被误删 | 中 | 明确：新增延迟选项不得顺手移除 iOS 的 `applyToPlayer` 早退 |

## 10. 一句话结论

**能修，位置很集中**：mpv 侧几乎全在 `MpvOptionsService` 单点，选流/选线全在 `simple_live_core` 与 `live_room_controller` 两处。

但**不要指望单靠调 buffer 解决** —— 服务端历史帧偏移与运行时漂移需要追帧环，那是本设计里最容易漏、又最影响长时间观看体感的一块。

现实目标：**5–10s 压到 1–3s 残差，且不再随时间漂移。**
