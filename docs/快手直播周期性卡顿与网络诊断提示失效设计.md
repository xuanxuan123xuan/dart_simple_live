## 0. 背景与实施状态

- 三份快手/诊断方案按合并实施计划落地于提交 `96b7c74`，核心治理（协调器、Cookie 会话、错误分类、轮询治理、诊断会话）均已实施并通过自动化测试。

- 本文不重复三份方案的设计，只做回归根因分析，并把"诊断提示失效"与"周期性卡顿"两条线合到一起：它们不是两个独立问题，而是**同一组改动里两处副作用**。

- 实施时修正了文档中的一个数据归属假设：快手签名 URL 实际保存在 `LivePlayQuality.data`，因此恢复链必须原子刷新 room detail 与 quality snapshot，不能只更新 `detail.value`。

## 1. 一句话结论

网络正常却周期性转圈、提示又不弹，是两个改动叠加的回归：

1. **诊断触发条件被改得过严**：`LiveRoomAutoQualityBufferTracker` 的 8 秒稳定清零 + 8 秒 warmup，使"间隔型转圈"（每次转圈相隔超过 8 秒）永远累计不到 3 次阈值，自动网络诊断与自动降画质**双双失效**，左上角提示自然永不弹出。
2. **播放 URL 过期后没有刷新路径**：S2-T1 在"稳定播放"时完全停止快手详情轮询，而快手又不在媒体错误重试的 URL 刷新白名单里，重试与切线路都用旧 URL。快手播放 URL 带服务端签名会过期，过期后播放器只能"缓冲几秒、撞运气重试、再缓冲"，形成周期性转圈。

**顺带修正一个前提**：转圈不是"网络波动"，而是"播放 URL 过期 + 客户端无自愈路径"。这也解释了为什么网络正常、诊断测不出问题——因为卡顿的根因在链路层，不在连通性层。

## 2. 根因摘要

| 层 | 已核实问题 | 结果 |
|---|---|---|
| R1 诊断触发失效 | `LiveRoomAutoQualityBufferTracker` 8s 稳定清零 + 8s warmup 反复重置 | 间隔 >8s 的转圈永不达到 3 次阈值，诊断不触发、提示不弹 |
| R2 URL 过期无刷新 | 快手稳定播放期停轮询（`_isStablyPlaying` 恒真）+ 快手不在 URL 刷新白名单 | 播放 URL 过期后无任何刷新来源，周期性转圈无法自愈 |
| R3 降画质同效失效 | 自动降画质与诊断共用同构 tracker（同样 8s 清零） | 卡顿无法通过自动降档缓解，放大 R2 |
| R4 冷却误触发 | `_getCookie` 403/挑战页触发 2 分钟全局冷却 | 冷却期后台恢复请求被拒，恢复变慢（需日志确认，非主因） |

**主因优先级：R1 + R2 必须一起修**。只修 R1 会恢复提示但转圈依旧；只修 R2 会停止转圈但下次卡顿时提示还是不弹。

## 3. 根因一：诊断 tracker 触发条件过严，间隔型转圈永不触发

### 3.1 改动前：累计 2 次即触发，无窗口无清零

改动前（`96b7c74` 之前）`player_controller.dart` 的缓冲监听逻辑是：

- 每个 `buffering=true` 事件，只要距上一次间隔超过 300ms 就 `_bufferingCount += 1`。
- `_bufferingCount >= 2` 即触发 `_runAutoNetworkDiagnose()`。
- 计数从不归零（这正是《直播间网络波动自动检测修复设计》指出的"计数单调增加"缺陷），但也正因如此，**任何累计两次转圈都必触发**。

### 3.2 改动后：3 次阈值 + 30s 窗口 + 8s 稳定清零 + 8s warmup

改动后（`player_controller.dart:1913-1919`）自动网络诊断改用独立 tracker：

```dart
final LiveRoomAutoQualityBufferTracker _autoDiagnosisTracker =
    LiveRoomAutoQualityBufferTracker(
  requiredBufferStarts: 3,
  bufferingWindow: const Duration(seconds: 30),
  stableResetAfter: const Duration(seconds: 8),
  warmupDuration: const Duration(seconds: 8),
);
```

`LiveRoomAutoQualityBufferTracker.update()`（`simple_live_app/lib/modules/live_room/live_room_auto_quality_buffer_tracker.dart:44-84`）在每次新的 `buffering=true` 边沿到来时执行：

```dart
if ((stableSince != null &&
        now.difference(stableSince) >= stableResetAfter) ||
    (lastStartedAt != null &&
        now.difference(lastStartedAt) > bufferingWindow)) {
  _bufferingStarts = 0;   // 稳定超过 8s 或窗口超过 30s，清零重来
  _lastBufferingStartedAt = null;
}
```

其中 `_stableSince` 在每次 `buffering=false` 时记录（`:46-49`）。

### 3.3 为什么"转几秒、恢复、隔一会再转"永远不触发

用户观察到的转圈节奏是：每次转圈几秒后恢复，**间隔一段时间再转下一次**。若两次转圈的间隔（上一次 `false` 到下一次 `true`）超过 8 秒：

| 事件序列 | 时间 | `_bufferingStarts` |
|---|---|---|
| 第一次 `true`（转圈） | t=0s | 1 |
| `false`（恢复） | t=3s | `_stableSince = t=3s` |
| 第二次 `true`（再转） | t=15s | `now - stableSince = 12s ≥ 8s` → **清零**，计数仍为 1 |
| 第三次 `true` | t=28s | 同样先清零，计数仍为 1 |

**计数永远停在 1，永远到不了 3**，诊断永不触发，`networkHint` 保持空字符串，左上角提示永不弹出。8 秒稳定清零的语义是"网络恢复 8 秒后视为风平浪静"，但对这种周期性短暂卡顿恰好是"每次都在计数前被清零"。

### 3.4 warmup 反复重置是第二个放大器

`markStreamOpening()`（`player_controller.dart:1952-1955`）在每次 `player.open()` 前调用 `_autoDiagnosisTracker.beginWarmup(DateTime.now())`，而 `beginWarmup` 会**先 `reset()` 清零全部计数，再开启 8 秒 warmup**（`live_room_auto_quality_buffer_tracker.dart:28-31`），warmup 内的缓冲事件一律不计（`:59-62`）。

调用点 `live_room_controller.dart:2447` 位于 `setPlayer` 的 `player.open()` 之前。这意味着**每次媒体错误重试、切线路、降画质重开流，都会把诊断计数清零并进入 8 秒忽略期**。若转圈触发了重开流，则"转圈 → 重开 → warmup 忽略 → 再转圈 → 再重开"循环里，诊断计数几乎永远在 warmup 内或被清零。

### 3.5 结论

诊断触发条件从"累计 2 次必触发"修正为"3 次独立缓冲开始 + 30s 窗口 + 8s 稳定清零 + 8s warmup"，方向上修复了"计数单调增加"，但参数过严，**与间隔型转圈（>8s 一次）不兼容**。提示不弹出是预期内的副作用，不是 bug，是"阈值配错了"。

## 4. 根因二：播放 URL 过期后无刷新路径

### 4.1 快手播放 URL 来自进房时的详情解析，且带服务端签名

快手 `getPlayUrls` 只从 `LiveRoomDetail.data`（进房时解析的 `playUrls`）提取，不做任何网络请求（`simple_live_core/lib/src/kuaishou_site.dart:1524-1529`）：

```dart
@override
Future<LivePlayUrl> getPlayUrls({
  required LiveRoomDetail detail,
  required LivePlayQuality quality,
}) async {
  return LivePlayUrl(urls: extractPlayableUrls(quality.data));
}
```

`data` 来自详情页 `window.__INITIAL_STATE__` 解析（`kuaishou_site.dart:1263,1331`）。这类直播流地址带服务端签名，**存在有效期**（《三份修复方案合并实施计划》待核实项 4 已列为"房间页面播放 URL 有效期"）。URL 过期后必须重新 `getRoomDetail` 才能拿到新 URL。

### 4.2 S2-T1：稳定播放期完全停止详情轮询

`live_room_controller.dart:1359-1379` 的 `_restartOnlineRefreshTimer`：

```dart
if (site.id == Constant.kKuaishou && _isStablyPlaying()) {
  Log.d("[ks-poll] skip online refresh timer (stably playing) ...");
  return;
}
```

而 `_isStablyPlaying()`（`:1387-1400`）非 OHOS 分支等价于 `_hasActivePlaybackSession || player.state.playing`。`_hasActivePlaybackSession` 在播放器打开成功后置 `true`（`:2460`），**在 mediaError/mediaEnd/换房之前一直为 `true`**。

关键点：**URL 过期导致播放器缓冲转圈时，并不一定触发 mediaError**（播放器在缓冲等待期间 `_hasActivePlaybackSession` 仍为 true）。于是：

- 转圈期间轮询被 `_isStablyPlaying()` 跳过 → 详情不刷新 → 播放 URL 不刷新 → 无法自愈。
- 这正是 S2-T1 注释里"播放状态作为主信号"假设失效的地方：**播放器"还在 playing"不等于"流是健康的"**。

### 4.3 媒体错误重试与切线路都不刷新 URL

`_shouldRefreshUrlsOnPlaybackRetry`（`live_room_controller.dart:2618-2619`）：

```dart
bool get _shouldRefreshUrlsOnPlaybackRetry =>
    Utils.isOhos || site.id == Constant.kHuya || site.id == Constant.kDouyu;
```

**不含快手**。因此：

- `mediaEnd`（`:2622-2637`）/ `mediaError`（`:2680-2695`）重试时调用 `setPlayer(refreshUrls: false)` → 用旧 URL 重开；
- 全部线路失败后 `changePlayLine(currentLineIndex + 1, persist: false)`（`:2672,2723`）→ `changePlayLine` 内部 `setPlayer()`（`:2308`）默认 `refreshUrls: false` → 依旧旧 URL；
- `_reloadPlayUrls` 唯一刷新入口（`:2208-2269`）依赖 `detail.value` + `getPlayUrls`，而 `detail.value` 只有在 `getRoomDetail` 成功时才更新（`:1434`）——轮询停了，`detail.value` 也陈旧。

### 4.4 完整链条：解释"看几分钟后开始、转几秒恢复"

1. 进房拿到带签名的播放 URL，正常播放。
2. 数分钟后 URL 过期（签名有效期到）。
3. 播放器拉新分片失败 → 缓冲转圈几秒。
4. 播放器内部重试/服务端对近期 URL 短暂容忍 → 恢复播放几秒到几十秒。
5. URL 再次过期 → 再转圈；若触发 mediaError，重试仍用旧 URL，多数继续失败，偶尔撞运气成功。
6. 循环往复，形成"转几秒、恢复、隔一会再转"。

**与本地网络无关**：URL 过期是服务端签名语义，不是连通性故障，所以用户网络正常、诊断也测不出问题（前提是诊断能触发——它又不能，见根因一）。

## 5. 根因三：自动降画质同构失效，卡顿无法降档缓解

自动降画质 tracker（`live_room_controller.dart:626`）与诊断 tracker 使用**同一套算法的独立实例、相同默认参数**（3 次 / 30s 窗口 / 8s 稳定清零 / 8s warmup）：

```dart
LiveRoomAutoQualityBufferTracker _autoQualityBufferTracker =
    LiveRoomAutoQualityBufferTracker();
```

`_setupAutoQualityAdjust`（`:630-664`）在 3 次缓冲开始后自动降一档。与根因一相同，间隔 >8s 的转圈**同样永远到不了 3 次**，自动降画质永不触发。

后果：在 R2 造成的周期性卡顿里，即使降低清晰度能缓解，客户端也不会降，卡顿持续。R1 与 R3 是同一次参数改动在两条消费链路上的重复失效。

## 6. 次级风险：协调器冷却误触发可能放大恢复延迟

`KuaishouSite` 现在把以下响应视为限流并触发全局冷却（`kuaishou_site.dart`）：

| 触发 | 位置 | 冷却时长 |
|---|---|---|
| 429 | `:1195` | 5 分钟 |
| 403（`_getCookie` 一律按 `hasCookie: true` 处理） | `:1203` | 2 分钟 |
| 200 安全验证页（`looksLikeChallengePage`，`:1161`） | `:1178`（`_challengePageError`） | 2 分钟 |

冷却期内，除用户主动进房外的后台请求（房间状态轮询、弹幕凭证、关注刷新，`kuaishou_request_coordinator.dart:201-212`）直接以 `KuaishouCooldownError` 失败。

风险点：

- `_getCookie` 对房间页面 403 无条件触发冷却——**未登录/匿名访问的 403 与风控 403 被同等对待**；
- `looksLikeChallengePage` 依赖 `captcha / 安全验证 / 访问过于频繁 / 风控` 等关键词（`:1161-1174`），正常页面若偶发包含这些词，会误判为挑战页并冷却 2 分钟；
- 冷却期正好处于"URL 过期转圈 → 播放恢复需要重新取详情"的阶段时，恢复请求被拒，转圈时间被拉长。

此项需要运行时日志确认是否为用户环境的高频路径，但防护成本低，建议随 R1/R2 一并处理。

## 7. 修复方向

### 7.1 修复诊断 tracker 触发条件（根因一，P0）

- **去掉或大幅放宽 8 秒稳定清零**：`stableResetAfter` 建议改为与 `bufferingWindow` 同级（30s）或更长（60s）。语义从"恢复 8 秒就清零"改为"只要两次转圈落在统计窗口内就继续累计"，让间隔型转圈也能达到阈值。
- **阈值由 3 改回 2 或保持 3 由实测定**：`requiredBufferStarts` 先改回 2（与用户旧认知一致），真机统计转圈间隔分布后再定稿。
- **warmup 仅限真正起播**：`markStreamOpening` 只在**首次** `player.open()` 前调用；mediaError/mediaEnd 重试、切线路、降画质重开流不再清零诊断计数、不进入新的 8s warmup（或只给极短 warmup，如 2s）。起播预缓冲过滤只对"新流首次打开"保留。
- 降画质 tracker（根因三）与诊断 tracker 同步放宽清零；两者仍保持独立实例。

### 7.2 恢复播放中 URL/详情刷新（根因二，P0）

- **"稳定播放"改为低频复核而非完全停轮询**：快手播放中保留低频详情复核（初值 120–180s + 随机抖动，最终按 URL 实测有效期定稿），复核仍走协调器 `roomStatus` 优先级与同房合并。若担心复核命中 15s 详情缓存导致状态发现延迟，可为 `roomStatus` 单独保留短缓存命中（或维持不缓存但降频）。
- **`_isStablyPlaying()` 把"缓冲中"排除**：`player.state.buffering` 为 true 或持续缓冲超过阈值（如 5s）时视为不稳定，允许启动详情刷新与轮询。
- **快手加入 URL 刷新白名单**：`_shouldRefreshUrlsOnPlaybackRetry` 加入 `site.id == Constant.kKuaishou`，mediaError/mediaEnd 重试时 `refreshUrls: true`，从最新详情重新拉 URL；`_reloadPlayUrls` 失败保留现有"回退为重新打开当前线路"逻辑（`live_room_controller.dart:2602-2606`）。
- **主动缓冲恢复**：播放中检测到连续缓冲（如 `buffering=true` 持续 >5s，或窗口内第 2 次独立缓冲开始）时，触发一次受协调器控制的详情复核并刷新播放 URL，而不是等 mediaError。

### 7.3 冷却误触发防护（根因四，P1）

- 403 冷却加确认条件：同一端点连续 N 次（初值 2–3 次）403 才进入冷却；或严格区分"带登录 Cookie 的 403"与"匿名 403"，匿名 403 只分类不冷却。
- `looksLikeChallengePage` 维持"含 `window.__INITIAL_STATE__` 即不算挑战页"的保护（`:1163-1164`），并补一条脱敏分类日志，供真机确认误判是否真实发生。
- 冷却期间保留用户主动进房单探针（现有协调器已支持），不改动。

### 7.4 参数定标（P2）

轮询复核间隔、tracker 清零窗口/阈值、冷却确认次数全部由阶段 10 的真机观测数据定稿，不在本设计内写死。

## 8. 不建议的修补

| 方案 | 为什么不够 |
|---|---|
| 只把诊断阈值从 3 改回 2 | 8s 稳定清零仍在，间隔 >8s 的转圈依旧永远到不了阈值 |
| 只去掉 warmup 不动清零 | 间隔型转圈仍被 8s 清零卡死 |
| 无脑恢复 10s 全量轮询 | 重新引入《频率限制设计》要消除的高频完整详情抓取 |
| 只把快手加入 URL 刷新白名单 | 稳定播放期轮询已停、`detail.value` 陈旧，重试时刷新拿到的还是旧详情缓存或旧 URL |
| 全局关闭协调器冷却 | 退回"无法识别限流"状态，与三份方案的核心治理相悖 |
| 在 UI 上强制显示"网络检测中…" | 诊断不触发时无结果可显示，掩盖真实问题 |

## 9. 建议推进顺序

1. 修 `LiveRoomAutoQualityBufferTracker`：放宽 8s 稳定清零、warmup 仅限起播（R1/R3 同时覆盖）。
2. 快手"稳定播放"改低频复核 + `_isStablyPlaying` 排除缓冲态 + 快手加入 URL 刷新白名单（R2）。
3. 播放中连续缓冲触发主动 URL 刷新（R2 增强）。
4. 403/挑战页冷却加确认条件与分类日志（R4）。
5. 真机采集转圈间隔分布、URL 有效期、冷却日志，定稿所有参数。

第 1、2 步是必做项，缺一不可：只做 1 提示恢复但转圈依旧，只做 2 转圈停止但下次卡顿时提示还是不弹。

## 10. 验证方案

### 10.1 单元测试（fake clock，不依赖真实网络）

| 场景 | 验收条件 |
|---|---|
| `true,false,true,false,true` 每次间隔 10s | 放宽清零后应累计到阈值触发一次；旧参数下不触发（回归测试） |
| `true,true,true` 连续 | 只计 1 次边沿（既有语义保留） |
| warmup 内 `true` | 不计数（保留起播过滤） |
| mediaError 重开流（重试路径） | 不再 `reset` 诊断计数、不进入新 warmup |
| `_isStablyPlaying` 在 `buffering=true` 时 | 返回 false，允许轮询启动 |
| 快手 mediaError 重试 | `refreshUrls=true`；URL 刷新失败时回退旧线路 |
| 播放中连续缓冲 >5s | 触发一次低频详情复核并刷新播放 URL |

### 10.2 真机验收（iOS 快手为主）

- 连续观看 30 分钟，记录：每次 `buffering` 时间戳与间隔分布、播放 URL 请求时间线、诊断是否弹出、冷却是否触发（403/429/挑战页分类日志）。
- 修复前后对比：转圈次数、平均转圈间隔、诊断弹出次数、URL 刷新次数、从转圈到恢复的平均时长。
- 验收硬条件：转圈时左上角能弹出诊断提示；URL 过期后能自动换新 URL 而非反复旧 URL 重试；"看几分钟后开始转圈"现象消失或间隔显著拉长。

## 11. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 放宽 8s 清零后误报增多（一次独立卡顿被算成多次） | 中 | 边沿计数保留；阈值与窗口由真机间隔分布定稿 |
| warmup 收敛到起播后，重开流起播缓冲被计为故障 | 中 | 重试路径给极短 warmup（2s）或不计数首帧缓冲 |
| 低频复核间隔过短重新带来频率压力 | 中 | 复核走协调器 + 同房合并；间隔按 URL 实测有效期定稿 |
| 缓冲态判定与播放器状态上报不同步 | 低 | `_isStablyPlaying` 以 `state.buffering` + 计时双保险 |
| 冷却确认条件过严导致真限流识别变慢 | 低 | 429 维持立即冷却不变，仅 403/挑战页加确认 |
| iOS media_kit 与桌面 mpv 的 `playing/buffering` 语义差异 | 中 | 真机矩阵验收 iOS + Windows/Android |

## 14. 一句话总结

网络正常却周期转圈、提示又不弹，是 `96b7c74` 的两处副作用叠加：**诊断 tracker 的 8 秒稳定清零 + 8 秒 warmup 让间隔型转圈永远到不了触发阈值（提示与降画质双双失效），而 S2-T1 停轮询 + 快手不在 URL 刷新白名单又让过期播放 URL 失去任何刷新来源（转圈无法自愈）**。一起修：放宽诊断触发、恢复播放中低频 URL 复核并让快手重试刷新 URL，两个现象才能同时消失。
