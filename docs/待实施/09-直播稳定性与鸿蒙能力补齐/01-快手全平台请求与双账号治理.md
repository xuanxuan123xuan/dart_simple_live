# 快手全平台请求与双账号治理

> 状态：待实施
> 适用平台：Android、iOS、HarmonyOS、Windows、macOS、Linux
> 不包含：HarmonyOS AVPlayer 起播修复、多开同屏

## 1. 结论

“请求频繁”不能只靠延长外层任务间隔解决。需要同时移除异常请求来源、把限流下沉到每个真实 HTTP 请求、让关注状态完全匿名化，并在明确账号限流后按“主账号 -> 备用账号 -> 匿名模式”单向降级。

双账号是容灾能力，不是正常请求治理的替代品。完成本方案后，账号 Cookie 的主要用途应只剩用户主动进房和确实缺失的弹幕凭证。

## 2. 已核实现状

### 2.1 外层协调器没有覆盖全部物理请求

`simple_live_core/lib/src/common/kuaishou_request_coordinator.dart` 当前默认最小间隔为 300ms，并在 `getRoomDetail` 外层做串行、缓存和同房合并。

但一次 `getRoomDetail` 内部仍可能执行：

1. Cookie/房间页面预取。
2. 携带 Cookie 的房间页面补请求。
3. 匿名房间页面补请求。
4. DID 注册。
5. 弹幕缺凭证时的详情或 WebSocket 信息请求。

协调器限制的是外层任务，不是上述每个真实 HTTP 请求。

### 2.2 用户主动进房绕过最小间隔

`simple_live_core/lib/src/kuaishou_site.dart` 中 `userEnter` 当前可以设置 `bypassInterval`。它可以提高优先级，但不应绕过同设备/IP 的物理请求间隔。

### 2.3 关注状态消耗登录态请求

快手没有已接入的轻量状态接口，关注刷新当前调用完整 `getRoomDetail`。登录态已经明确返回未开播时，现有详情逻辑还可能再请求一次匿名页面，离线主播会放大请求量。

### 2.4 播放异常继续放大请求

HarmonyOS 卡在缓冲时，房间状态轮询和播放恢复可能分别重复获取完整详情。单个异常房间可在一分钟内产生多次详情任务。

播放器本地恢复和房间详情刷新必须解耦，具体由 [02-HarmonyOS直播起播与恢复稳定性](02-HarmonyOS直播起播与恢复稳定性.md) 实施。本方案负责确保播放器即使误触发恢复，也不能绕过全局请求保护。

### 2.5 当前冷却时间与实际限制不匹配

当前明确 429 只冷却数分钟，认证挑战/403 的冷却也较短。如果服务端实际按自然日限制账号，短冷却后的探针会继续加重限制。

## 3. 目标与非目标

### 3.1 目标

- 关注列表刷新不产生任何登录态快手请求。
- 每个真实快手 HTTP 请求都经过统一调度。
- 用户进房可以插队，但不能绕过全局间隔。
- 正常观看不因状态轮询持续消耗账号请求。
- 支持用户配置主、备两个账号 Cookie，且会话完全隔离。
- 明确账号限流后暂停该账号到次日 0 点。
- 两个账号都不可用时仍可匿名播放画面，但不获取弹幕。
- Cookie 失效和请求频繁使用不同状态与恢复规则。

### 3.2 非目标

- 不删除用户保存的 Cookie。
- 不把网络超时、DNS/TLS 错误或任意 403 判定为当日限流。
- 不在多个账号之间循环轮换。
- 不用登录态请求给匿名关注刷新兜底。
- 不猜测快手的精确日请求配额。
- 不包含多开同屏。

## 4. 请求架构

### 4.1 匿名与登录通道隔离

| 通道 | 用途 | Cookie | DID | 弹幕凭证 |
| --- | --- | --- | --- | --- |
| 匿名 | 关注状态、匿名详情、降级播放 | 永不携带 | 不执行 | 不获取 |
| 登录 | 主动进房、确需登录的弹幕凭证 | 当前账号槽位 | 每账号会话至多一次 | 按需获取 |

匿名请求使用独立、无 CookieManager、无自定义 Cookie 注入的 HTTP 会话。匿名和登录通道不得共享 CookieJar、响应缓存或错误分类状态。

### 4.2 全局物理请求调度器

所有快手真实 HTTP 请求都进入全局调度器：

- 固定单路串行。
- 相邻请求初始建议间隔 1.5 秒，并增加 0～500ms 抖动。
- 用户主动进房只提高队列优先级，不绕过最小间隔。
- 同通道、同端点、同房间在途请求 single-flight。
- 进入账号暂停状态时取消该账号尚未执行的任务。
- 切换备用账号不能补跑主账号积压的后台任务。

匿名与登录请求可以有不同优先级和缓存，但必须共享设备/IP 级出站间隔，避免切换 Cookie 后立即形成突发。

## 5. 关注列表匿名刷新

### 5.1 专用接口

新增 `getAnonymousLiveStatusState(roomId)`，关注列表不得再调用默认的 `getLiveStatusState -> getRoomDetail` 登录链路。

接口只做三件事：

1. 使用匿名会话请求公开房间页面。
2. 解析 `live`、`offline` 或 `unknown`。
3. 写入匿名状态缓存。

禁止获取弹幕凭证、注册 DID、更新登录 Cookie 会话，以及匿名失败后登录回退。

### 5.2 调度与缓存

- 固定单路串行刷新。
- 当前可见关注项优先，其他项分批排队。
- 已开播建议缓存 60 秒。
- 未开播建议缓存 3 分钟。
- 未知建议缓存 30 秒，避免界面重建立即重试。
- 同房请求合并。
- 离开关注页后取消尚未发出的低优先级刷新。

匿名请求也可能受到 IP 限制。失败时保留上一次状态并标记过期或未知，不得切回账号 Cookie。

### 5.3 结果复用

如果匿名状态解析已得到可用公开详情，可写入短期匿名详情缓存。用户随后进入该房间时优先复用 FLV 地址；正常模式仅在缺少弹幕凭证时补一次登录请求，匿名模式不启动弹幕。

## 6. 减少登录态重复请求

- 登录页面已明确返回 `live` 或 `offline` 时直接采用，不再匿名二次确认。
- 匿名回退只用于明确允许匿名播放的流程，不是详情请求的固定步骤。
- 弹幕参数已有连接信息时不再刷新详情或请求 WebSocket 信息。
- DID 上报改为每个账号应用会话最多一次。
- 状态轮询和播放恢复不得触发 DID 上报。
- 活跃播放会话不进行秒级房间详情轮询。
- 缓冲恢复优先重开当前 FLV；只有明确地址 HTTP 失效才刷新详情。

## 7. 双账号模型

### 7.1 会话隔离

每个槽位持有独立 `KuaishouAccountSession`：

```text
slot                    primary | secondary
cookie                  String
kww                     String
cookieExpiresAt         DateTime?
loggedInAt              DateTime?
lastValidatedAt         DateTime?
credentialState         unknown | valid | invalid
cooldownUntil           DateTime?
suspendedUntil          DateTime?
suspendedReason         String?
cookieJar               独立实例
httpSession             独立实例
didReportState          独立状态
requestCounters         独立计数
```

`KuaishouAccountPool` 只负责选择账号槽位和单向降级；设备/IP 级请求间隔仍由全局调度器控制。

### 7.2 账号与账号池状态

账号槽位状态：

| 状态 | 行为 |
| --- | --- |
| `available` | 可以处理登录态请求 |
| `cooldown` | 短期冷却，不处理后台任务 |
| `suspended` | 当日停止该账号全部请求 |
| `invalid` | Cookie 明确失效，等待重新登录 |

账号池模式：

| 模式 | 行为 |
| --- | --- |
| `primary` | 使用主账号 |
| `secondary` | 主账号不可用，使用备用账号 |
| `anonymous` | 两个账号均不可用或未配置 |

### 7.3 单向降级

```text
primary
  -> 主账号明确限流或失效
secondary
  -> 备用账号明确限流或失效
anonymous
```

- 主账号明确限流后暂停至次日 0 点并取消待执行任务。
- 触发限流的是用户当前操作时，可以用备用账号重试该操作一次。
- 不重放关注刷新、轮询、播放恢复等后台任务。
- 备用账号首次请求仍遵守全局间隔。
- 备用账号也被明确限制后进入匿名模式，不回切主账号。
- 当前已取得的 FLV 继续播放，切换账号不主动重建画面。

服务端限制可能同时关联账号、设备和出口 IP。备用账号第一次请求也被明确拒绝时，立即进入匿名模式，不能增加探测次数。

## 8. 限流与失效分类

### 8.1 当日暂停的硬证据

- 登录态请求返回明确 429。
- 正文明确包含“请求频繁”或“访问过于频繁”。
- 登录态返回可确认的频率挑战/安全验证页，且不是普通传输错误。

### 8.2 不应直接当日暂停

- 普通 403：先短冷却；只有同一 Cookie 会话、同一端点连续凭据拒绝才升级。
- DNS、连接超时、TLS、解析失败：按网络/响应错误处理。
- 播放器错误：只进入播放器恢复流程。
- 明确未登录、登录页或凭证无效：标记 Cookie `invalid`，不是频繁。

### 8.3 次日恢复

暂停截止时间按 `Asia/Shanghai` 的下一个自然日 00:00 计算。

- 到点惰性清除，不触发批量刷新。
- 两个暂停槽位恢复为可探测，账号池默认回到主账号。
- 次日第一个确需登录的用户操作作为主账号探针。
- Cookie `invalid` 不会在 00:00 恢复，必须重新登录。

## 9. Cookie 到期与重新登录

`cookieExpiresAt` 是预计到期时间，`suspendedUntil` 是请求频繁暂停时间，两者不能混用。

| Cookie 来源 | 到期时间能力 |
| --- | --- |
| Android/iOS/桌面 WebView 登录 | 通常可读取关键认证 Cookie 的 `expiresDate` |
| HarmonyOS WebView 登录 | 当前 `fetchCookieSync()` 只返回 `name=value`，通常取不到属性 |
| 手动粘贴 Cookie/Request Headers | 不含 `Expires/Max-Age`，通常取不到 |
| 内嵌标准 Token | 仅在可靠解析 `exp/expiresAt` 时使用；opaque token 返回未知 |

界面规则：

- 有预计到期时间：显示剩余时间，提前 24 小时提醒重新登录。
- 无预计到期时间：显示“到期时间未知”、登录时间和上次验证成功时间。
- 超过预计时间：显示“预计已到期”，仍以服务端实际响应确认。
- 明确失效：标记 `invalid` 并按账号池顺序降级。
- 403/429/挑战页不能标记为 Cookie 到期。
- 手动“检测账号”会消耗一次请求，不允许后台高频检测。

不得用固定天数伪造服务端到期时间。

## 10. 匿名模式

- 关注列表继续匿名刷新。
- 用户主动进房使用匿名公开详情和 FLV。
- 不连接快手弹幕。
- 不请求 WebSocket 凭证、Cookie 握手或 DID 注册。
- 不执行登录态轮询和后台重试。
- 匿名也被拒绝时停止重试并显示访问受限。

## 11. 设置与状态展示

- 设置页提供主账号、备用账号两个 Cookie 槽位。
- 校验两个槽位不是完全相同的 Cookie；能可靠取得 UID 时阻止同 UID 重复配置。
- 显示当前模式：主账号、备用账号或匿名模式。
- 每个账号显示：有效、已失效、到期时间未知、预计到期、请求频繁至某时。
- 更换某槽位 Cookie 只重置该槽位会话和状态。
- 日志只记录 `account_slot=primary|secondary|none`，不得记录 Cookie、UID、DID、播放 URL 或弹幕 Token。

## 13. 测试与验收

### 13.1 单元测试

- 匿名请求不含 Cookie，也不读取登录 CookieJar。
- 关注匿名失败后不登录回退。
- 三种直播状态缓存 TTL 正确。
- 每个真实请求遵守间隔，用户进房只改变优先级。
- 主、备 CookieJar/缓存/DID/凭证完全隔离。
- 429、频繁文案、挑战页、普通 403、网络错误和失效分类正确。
- 主账号只向备用账号切换一次，备用账号只向匿名降级。
- 上海时区次日 0 点计算覆盖跨月、跨年。
- `invalid` 不随 0 点恢复。
- Cookie 到期时间未知时不生成虚假日期。
- 重启后两个账号状态和当前模式正确恢复。

### 13.2 全平台验收

- 刷新快手关注列表时，登录态请求数为 0。
- 正常进房登录详情保持在一次量级，弹幕凭证只在缺失时追加。
- 正常观看 30 分钟不因轮询持续消耗登录详情。
- 主账号限流后，当前用户操作至多用备用账号重试一次。
- 备用账号限流后，两个账号在次日 0 点前均不再发请求。
- 匿名画面可用，弹幕明确停用。

## 14. 实施顺序

1. 先停止播放/关注导致的登录态请求放大。
2. 新增匿名关注状态专用接口。
3. 将协调器下沉到物理请求层。
4. 抽取单账号 `KuaishouAccountSession`，保持单账号行为兼容。
5. 增加备用槽位和账号池单向降级。
6. 增加持久化、配置迁移和状态 UI。
7. 最后启用“频繁到次日 0 点”的硬暂停。

每个阶段都应先上线计数日志，确认登录请求量下降后再开启下一阶段。
