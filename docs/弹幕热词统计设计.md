# 弹幕热词统计设计

> 状态：设计草案，**未实施**。所有结论基于对 dev 分支代码的只读核查。
> 关联：[[直播延迟优化设计.md]]（无冲突）、[[音量统一设计.md]]（无冲突）

Roadmap 原文：**进房实时统计弹幕高频词，看节奏/吃瓜；点击热词可一键加屏蔽词。**

---

## 1. 一句话结论

**结构上几乎已经做完了，唯一真正的新增成本是「中文分词」。**

项目里已有 `LiveRepeatedDanmuAggregator` —— 一个滑动时间窗 + TopN 的计数器，已投产于「重点动态」功能。热词统计与它的差异**只在 key 的粒度**：现有实现以「整条弹幕文本」为 key，热词要以「分词后的词」为 key。

所以这个功能的真实形态不是「新建统计系统」，而是「给已有的聚合器换一个 key 提取函数」。

## 3. 唯一的真实成本：中文分词

### 3.1 现状是零

已核实：**全仓 20 个 pubspec.yaml 检索 `jieba|segment|tokeniz|nlp|chinese|word|分词|lucene|hanlp|mecab|ik` —— 零命中。**

`Utils`（`app/utils.dart`）里也没有任何分词、n-gram、停用词能力。唯一相关的是两处文本归一化（`trim` + 空白折叠）：
- `live_room_controller.dart:729-731` `_normalizeDanmuFingerprintPart`
- `live_repeated_danmu_summary.dart:112-114` `_normalizeText`

### 3.2 三条路，成本与效果差别很大

| 方案 | 成本 | 效果 | 风险 |
|---|---|---|---|
| **B1. 不分词，只统计整句** | ~0（现有聚合器直接换个入口） | 只能抓「刷屏梗」，抓不到「词」 | 与现有「重点动态」功能高度重合，可能沦为重复功能 |
| **B2. n-gram（2/3 字滑窗）** | 低（几十行，无依赖） | 中文场景意外地可用；能抓出「下饭」「破防」这类词 | 产生大量无意义片段，**必须配停用词表 + 子串合并**，否则 TopN 全是噪声 |
| **B3. 引入分词库** | 中（新增依赖 + 词典 asset 体积） | 最准 | Dart 生态的中文分词库成熟度需实测；词典可能有数 MB 体积；纯 Dart 实现的性能在高频弹幕下未知 |

**倾向 B2。** 理由：弹幕文本极短（多为 2-10 字），n-gram 的噪声问题比长文本轻得多；且弹幕热词的本质是「重复出现的短片段」，与 n-gram 的产出形态天然吻合。B3 的词典对一个「看节奏/吃瓜」的轻量功能来说太重。

B2 的必要配套：
- **停用词表** —— 中文高频虚词（的/了/是/我/你…）+ 弹幕特有噪声（哈/啊/6/？）。这个表需要人工构造，是 B2 的主要工作量，不是分词算法本身。
- **子串合并** —— 「破防」和「破防了」会同时上榜，需要在 `_buildSummaries` 阶段做一次「若 A 是 B 的子串且 count 接近，只留 B」的折叠。

## 4. 性能：这是最需要注意的地方

### 4.1 现有链路已经有两处「每条弹幕全量重算」

**这不是热词功能引入的问题，是已存在的现状，但热词会把它放大。**

`live_room_controller.dart:1442-1443`，`_recordLiveEventFlow` 内：
```dart
_liveEventFlowAggregator.add(text);
_flushLiveEventFlow();     // ← 每条弹幕都全量 preview + 排序 + assignAll
```
3 秒的 periodic timer 是**额外兜底，不是节流**。

另一处：`_isKeywordShielded`（`:613-637`）对每条弹幕遍历全部屏蔽词，**且正则每次重新 `RegExp()` 编译，无缓存**。

还有：`messages.add()`（`:1753`）每条弹幕触发一次 Rx 通知 + 一次 `addPostFrameCallback`，**无批量刷新**。项目里有 `DelayedThrottle` 工具类（`app/custom_throttle.dart`），但未用于弹幕接收链路。

### 4.2 热词会把成本放大 N 倍

一条弹幕产生 1 个「整句 key」，但会产生 ~5-15 个「n-gram key」。如果沿用「每条弹幕全量 flush」的写法：

- Map 规模从「不同句子数」涨到「不同片段数」，量级上升约一个数量级
- 每条弹幕的 prune 成本、排序成本同步上升

**因此热词统计必须做节流 flush，不能照抄 `_recordLiveEventFlow` 的即时 flush。** 建议：只保留 periodic flush（现成的 3s timer 范式），埋点里只 `add` 不 `flush`。

### 4.3 缺口：没有速率上限

已核实：项目里**没有任何按速率降频/丢弃弹幕的逻辑**。去重是按内容，不是按速率。悬浮弹幕有丢弃（`_scheduleOverlayDanmaku` 的三重条件），但那是渲染层。

代码与注释里也**找不到任何弹幕「条/秒」量级的实测数字**，所以无法据此估算热词统计的实际负载。这是设计阶段的一个真实盲区 —— 大房间高峰期的弹幕速率是未知量。

## 5. 插入点：埋点该放在链路的哪一步

`onWSMessage`（`live_room_controller.dart:1735-1787`）的 chat 分支顺序：

```
1. :1736  _sanitizeLiveMessage(msg)
2. :1738  用户屏蔽 + 临时禁言 → return
3. :1743  _isKeywordShielded(msg) → return
4. :1747  _recordLiveEventFlow(msg)      ← 「重点动态」埋点在这
5. :1749  _isDuplicateDanmu(msg) → return
6. :1753  messages.add(msg)
7. :1757  上限裁剪（500）
8. :1761  chatScrollToBottom()
9. :1767  _scheduleOverlayDanmaku(msg)
```

**热词埋点应与 `_recordLiveEventFlow` 同位置（第 4 步）**，理由：

- 在**屏蔽之后**（第 3 步后）—— 已屏蔽的内容不该再进热词榜，否则用户屏蔽了还看它挂在榜上
- 在**去重之前**（第 5 步前）—— 刷屏是热词的核心信号，去重会把它抹掉。这也是现有「重点动态」的选择，逻辑一致

需要注意 `_sanitizeLiveMessage`（第 1 步）的行为**未核实** —— 若它会改写 message 文本，热词统计到的是改写后的内容。

## 6. 数据模型的一个硬约束

**`LiveMessage` 没有时间戳字段。** 已核实（`simple_live_core/lib/src/model/live_message.dart:17-65`，全部 7 个字段：type / userName / message / data / color / imageUrls / spans）。

所以「实时统计」的时间基准只能是 app 收到消息的时刻。`LiveRepeatedDanmuAggregator.add()` 用的就是 `now ?? DateTime.now()`，即 add 时刻取时间 —— 热词沿用同样方式即可，但要清楚这意味着**统计窗口反映的是「客户端接收时间」，不是「弹幕发送时间」**。弹幕延迟补偿（`danmuDelayMs` / `danmuDelayBySite`）会让这两者产生偏差。

## 7. 建议范围与推进顺序

**第一步（最小可用）：**
1. 用 n-gram 提取 key，复用 `LiveRepeatedDanmuAggregator`（或克隆一个 `LiveHotWordAggregator`，避免与「重点动态」参数互相干扰）
2. 埋点放第 4 步，**只 add 不 flush**
3. 只保留 periodic flush（3s 范式）
4. 新增一个 Tab + 面板，`ListTile` 加 `onTap` → `addShieldList` + 强制开开关
5. 停用词表先做一个小规模版本（几十个词），上线后按实际噪声迭代

**第二步（按需）：**
- 子串合并折叠
- 设置项（窗口/阈值/条数），照抄 `kLiveEventFlow*` 四参数范式
- 「点击热词」的第二个动作：除了屏蔽，也可以是「筛选出含该词的弹幕」

**明确不做的：**
- 引入分词库（B3）—— 除非 n-gram 实测噪声无法接受
- 落盘持久化 —— 热词是会话内的实时信号，跨会话统计属于「观看统计」的范围
