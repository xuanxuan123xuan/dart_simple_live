# 竖屏弹幕列表 + 全屏方向跟随视频方向 —— 设计与实施方向

> 总设计师视角。只写方向、位置、可能情况与风险，不写具体实现代码。
> 状态：**仅设计，代码未改动。**
> 对应 Roadmap 两项：「竖屏直播弹幕」（下称 **A**）、「全屏方向跟随视频方向」（下称 **B**）。

---

## 0. 为什么这两项合成一份文档

它们共用同一个基础设施：**视频实际方向的探测结果 `isVertical`**。

分开写会把同一套探测机制的分析做两遍，且容易得出互相矛盾的结论（比如 A 假设方向可靠、B 假设方向需要兜底）。合并后只维护一份关于「方向信号何时可信」的判断。

但**两者的成本相差一个量级**，排期上不应捆绑：

| | 性质 | 核心工作量 |
|---|---|---|
| **B** 全屏方向跟随 | 改默认值 + 补齐已知不对称 | 判定逻辑**已经写好了**，只是默认值反着 |
| **A** 竖屏弹幕列表 | 新 UI 形态 + 定位约束 | 数据源与滚动逻辑可复用，定位与避让要新写 |

**建议 B 先做、单独发**，A 按 README 现有标注（「大更新，不急」）另行排期。

## 1. 共用基础：方向探测现状（已核实）

`isVertical` 定义在 [player_controller.dart:150](simple_live_app/lib/modules/live_room/player/player_controller.dart:150)，是 `PlayerMixin` 里的 `RxBool`，被 `LiveRoomController` 混入。**三条播放后端已统一收口到这一个信号**，A 和 B 都不需要新建探测机制。

| 后端 | 探测方式 | 中途变化 | 拿不到时 |
|---|---|---|---|
| media_kit（Android/iOS/桌面） | `player.stream.width` / `stream.height` 订阅（[:1761-1795](simple_live_app/lib/modules/live_room/player/player_controller.dart:1761)） | ✅ 流式，切清晰度/线路自动更新 | 兜底 `?? 16` / `?? 9` → 判为横屏 |
| OHOS video_player | `VideoPlayerValue.size`（[:169-183](simple_live_app/lib/modules/live_room/player/player_controller.dart:169)） | ⚠️ 仅 `initialized` 事件带宽高，靠 `revision` 强制重建取新值 | 切房时显式重置为 false |
| TV app | 无此能力 | — | 相关代码全是注释 |

### 1.1 这里有一处已核实的不对称，A 和 B 都会踩

换房间时 `isVertical` 的重置**只有 OHOS 分支做了**：

[live_room_controller.dart:2155-2160](simple_live_app/lib/modules/live_room/live_room_controller.dart:2155) 在 OHOS 分支显式 `isVertical.value = false`，注释写明「A previous room/line may have been a portrait stream」。

**media_kit 分支没有对应重置。** 后果：从竖屏房间切到横屏房间的瞬间，`isVertical` 仍是上一个房间的 `true`，直到新的 width/height stream event 到达。这个窗口期内：

- 对 B：进全屏会误判为竖屏流而不转横屏
- 对 A：弹幕形态会按上一个房间的方向渲染

窗口长度取决于 mpv 首个 width event 的到达时间，**未实测**。这是 A/B 共同的前置修复项。

### 1.2 站点元数据完全不带宽高（已核实，零命中）

`LivePlayQuality`（[live_play_quality.dart:3-16](simple_live_core/lib/src/model/live_play_quality.dart:3)）只有 `quality` / `data` / `sort`；`LivePlayUrl` 只有 `urls`。五个站点的清晰度解析全部只取画质档位名与编号，**无一取宽高**。

core 库里 `width|height|resolution` 的全部命中都是无关项：抖音/快手请求里伪造的 `screen_width=1920` 反爬指纹、protobuf 里弹幕表情图片的尺寸、字符串格式化的 `padRight(width)`。

**结论：方向判定必须依赖播放后实测，不存在「播放前预判竖屏」的路径。** 这直接决定 A 和 B 都必须容忍一个「方向未知」的初始状态，不能在打开播放器时就确定布局。

## 2. B：全屏方向跟随视频方向

### 2.1 现状 —— 逻辑已经写好了，默认值反着

[player_controller.dart:624-635](simple_live_app/lib/modules/live_room/player/player_controller.dart:624) 的 Android/iOS 分支：

```
if (!isVertical.value || fullScreenForceLandscape.value) {
  await setLandscapeOrientation();
}
```

语义已经完全正确：横屏流永远转横屏；竖屏流只有开关打开才转横屏。

`fullScreenForceLandscape` 的默认值是 `true`，两处：
- 声明 [app_settings_controller.dart:2132](simple_live_app/lib/app/controller/app_settings_controller.dart:2132) `true.obs`
- 持久化读取 fallback [:413-416](simple_live_app/lib/app/controller/app_settings_controller.dart:413)

设置项、UI 开关（[player_controls.dart:1186-1196](simple_live_app/lib/modules/live_room/player/player_controls.dart:1186)，标题「全屏自动横屏」）、持久化都已就位。

**OHOS 分支（[:581-624](simple_live_app/lib/modules/live_room/player/player_controller.dart:581)）根本不读这个开关**，硬编码 `if (!isVertical.value)` —— 即 OHOS 上竖屏流全屏**已经**保持竖屏了，已符合 B 的目标行为。

### 2.2 改动方向

核心改动只有一处：**两个 `true` 改 `false`**。

但如果只改默认值，会连带暴露三个已存在的缺口。它们现在被「默认强制横屏」掩盖着 —— 一旦竖屏全屏成为默认路径，这些就都会被用户碰到：

| 缺口 | 位置 | 掩盖原因 | 暴露后的表现 |
|---|---|---|---|
| media_kit 换房不重置 `isVertical` | 见 1.1 | 强制横屏时方向判定结果不影响行为 | 切房后首次进全屏方向可能错 |
| `exitFull` OHOS 硬编码恢复 `portraitUp` 单一方向 | [player_controller.dart:733-735](simple_live_app/lib/modules/live_room/player/player_controller.dart:733) | Android/iOS 走 `DeviceOrientation.values`（[:1074](simple_live_app/lib/modules/live_room/player/player_controller.dart:1074)），两条路径本就不对称 | OHOS 退出全屏被强制竖屏，横屏持握时体验断裂 |
| `buildPhoneUI` 播放器区域硬编码 `AspectRatio(16/9)` | [live_room_page.dart:414-417](simple_live_app/lib/modules/live_room/live_room_page.dart:414) | 全屏时不走这个布局 | 竖屏流**非全屏**时是 letterbox 上下黑边 |

第三项是 B 的**范围边界问题，需要你拍板**：README 那行只说「竖屏直播全屏保持竖屏」，字面上不含非全屏。但用户装上新版本后，最先看到的其实是非全屏那个 16:9 letterbox —— 因为它一直都在，且是进房第一眼。

三个选项：

1. **严格按 README 只做全屏**（改动最小，但用户会觉得「没修全」）
2. **顺带让非全屏播放器区域也跟随方向**（改 `buildPhoneUI` 的 AspectRatio，但会影响下方 Tab 区域的可用高度，是布局连锁改动）
3. **只做全屏，非全屏 letterbox 单独立项**

倾向 **3** —— 非全屏跟随方向会挤压 Tab 区域，那是独立的布局决策，不该塞进 B 这个小改动里。

另有一处死代码可顺带清理：`setPortraitOrientation()`（[:1055-1063](simple_live_app/lib/modules/live_room/player/player_controller.dart:1055)）定义了但**全仓零调用者**。

### 2.3 B 的风险

**低，但有一个真实的平台约束不能忽略。**

现有开关的代码注释已经写明了它为什么默认开：

> iPad 竖屏状态栏由系统强制显示，只有横屏才能可靠隐藏；关闭则保持当前方向

以及 UI 副标题：

> 竖屏进全屏时自动转横屏，状态栏才能隐藏；关闭则保持当前方向（竖屏全屏状态栏隐藏不了）

也就是说 **B 的目标行为与「全屏隐藏状态栏」在 iPad 上是互斥的**，这是 iOS 平台行为，不是本项目的 bug。改默认值等于选择「保持方向」而放弃「iPad 竖屏全屏隐藏状态栏」。

这个取舍需要你确认。可选的缓解是**按平台分默认值**（iPad 保持 `true`，其他平台 `false`），代价是行为不一致、解释成本上升。

`restoreFullScreenSystemUi()`（[:658-687](simple_live_app/lib/modules/live_room/player/player_controller.dart:658)）里 iOS 按 `[250,500,900,2000,3000]`ms 反复重设 `SystemUiMode.manual` —— 这串重试本身就是 iOS 状态栏难以稳定隐藏的证据。竖屏全屏下它大概率仍然无效，**建议实测确认，不要假设**。

## 3. A：竖屏直播弹幕列表

### 3.1 关键发现 —— 这个形态已经存在两份实现

README 把 A 标为「大更新」。实际上**滚动列表 + 自动滚底 + 上滑回看**这套核心逻辑，仓库里已经有两份可用实现：

**实现一：多开页 `_ChatPanel`**（[multi_room_page.dart:745-903](simple_live_app/lib/modules/multi_room/multi_room_page.dart:745)）—— 源码注释就写着「竖向弹幕列表」。

**实现二：直播间 `buildChatList`**（[live_room_page.dart:1370-1403](simple_live_app/lib/modules/live_room/live_room_page.dart:1370)）+ controller 侧逻辑 —— **这份更完整**：

- `disableAutoScroll` 是 **Rx**（[live_room_controller.dart:469](simple_live_app/lib/modules/live_room/live_room_controller.dart:469)），能驱动 UI；多开那份 `_followBottom` 是裸 bool，改了不 setState
- 有「最新」浮动按钮（`Visibility` + `forceChatScrollToBottom`）
- `scrollListener` 判定用 `position.extentAfter <= 24`（[:606-611](simple_live_app/lib/modules/live_room/live_room_controller.dart:606)），并区分 `userScrollDirection`
- 列表长度有界（500 硬上限，[:1757](simple_live_app/lib/modules/live_room/live_room_controller.dart:1757)），注释明确提到「避免 disableAutoScroll 时内存无上限」

**A 应当复用实现二的 controller 逻辑** —— 它挂在同一个 `LiveRoomController` 上，A 要在同一页面做叠加列表，直接读同一个 `controller.messages`，不需要新的数据通路。

逐条对照 README 的需求：

| README 需求 | 现状 | 缺口 |
|---|---|---|
| 从下往上 | ✅ 已有 | — |
| 背景透明 | ✅ 多开用 `withAlpha(120)` | 需确定直播间用什么值 |
| 长文本自动换行 | ✅ `ChatMessageItem` 复用 | 内部是否有 maxLines **未核实** |
| 上滑可回看历史 | ✅ 两份都有 | — |
| ≤ 半屏 | ❌ 现有列表都是 `Expanded` 撑满 | **要新写定位约束** |
| 左下角 | ❌ 现有是独立面板 / Tab 内容 | **要新写定位** |
| 底部避让控制栏 | ❌ 无先例 | **要新写**，且缺常量（见 3.3） |
| 弹幕模式跟随视频方向 | ❌ `isVertical` 目前只影响全屏方向 | **要新写模式切换** |

即：**数据与滚动全部现成，定位、避让、模式切换要新写。** 这比「大更新」的预期要小，但比「改默认值」大得多。

### 3.2 叠加位置

播放器 Stack 有三个，`buildDanmuView` 已经证明 `Positioned.fill` 叠加可行：

- [player_controls.dart:69-98](simple_live_app/lib/modules/live_room/player/player_controls.dart:69) `buildFullControls`（全屏）
- [player_controls.dart:144-158](simple_live_app/lib/modules/live_room/player/player_controls.dart:144) `buildControls`（非全屏）
- [live_room_page.dart:691-761](simple_live_app/lib/modules/live_room/live_room_page.dart:691) `_buildOhosMediaPlayer`（OHOS 自建 Stack，调同一个 `buildDanmuView`）

**注意竖屏非全屏的可用空间约束**：[buildPhoneUI](simple_live_app/lib/modules/live_room/live_room_page.dart:413) 是 `Column`，播放器固定 `AspectRatio(16/9)`，下方是 `buildUserProfile` + `buildMessageArea`（TabBar 容器）+ `buildBottomActions`。

所以 A 的「左下角」只能落在那个 16:9 播放器区域内 —— **竖屏流在里面本身就是 letterbox，画面上下有黑边**。弹幕列表叠在黑边上还是画面上，是需要明确的设计决策（叠黑边不遮挡画面，但视觉上像是「列表在画面外」）。

### 3.3 底部避让：缺常量，只有散落字面量

控制栏高度目前**没有任何命名常量**，全是 `AnimatedPositioned` 的负偏移字面量：

| 位置 | 值 | 出处 |
|---|---|---|
| 非全屏底栏 | 48 | [player_controls.dart:745](simple_live_app/lib/modules/live_room/player/player_controls.dart:745) `bottom: ... : -48` |
| 全屏底栏 | 80 + 安全区 | [player_controls.dart:606](simple_live_app/lib/modules/live_room/player/player_controls.dart:606) `-(80 + padding.bottom)` |
| OHOS 顶栏 | 48 + 安全区 | [live_room_page.dart:768](simple_live_app/lib/modules/live_room/live_room_page.dart:768)（唯一显式 `height`） |
| OHOS 底栏 | 全屏 80 / 非全屏 48 | [live_room_page.dart:745-747](simple_live_app/lib/modules/live_room/live_room_page.dart:745) |
| 多开顶栏 | 56 + 安全区 | [multi_room_page.dart:135](simple_live_app/lib/modules/multi_room/multi_room_page.dart:135) |

**A 做底部避让必须先把这些抽成常量**，否则会变成第六处同类字面量。这是 A 的一项前置整理工作，本身不产生用户可见变化。

避让范式有三个可照抄的先例：

1. **统一安全区解析器** `_fullScreenControlPadding()`（[player_controls.dart:41-58](simple_live_app/lib/modules/live_room/player/player_controls.dart:41)）—— 已被 `buildFullControls` 与 `buildDanmuView` 复用，含 OHOS 用 `viewPadding`、iOS 横屏 top 兜底 8pt 的特判
2. **多开页整体 Padding**（[multi_room_page.dart:51-56](simple_live_app/lib/modules/multi_room/multi_room_page.dart:51)）—— 用 `MediaQuery.viewPaddingOf(context).top`，注释说明是为了「避免第一行格子（及其弹幕）与状态栏重叠」
3. **平板横屏固定 inset**（[player_controls.dart:920-926](simple_live_app/lib/modules/live_room/player/player_controls.dart:920)）—— `tabletLandscapeFullscreen ? 32.0 : 0.0` 的条件式偏移

先例 2 和 3 都用 **`viewPadding` 而非 `padding`**，原因是全屏隐藏系统栏时 `padding` 归零但 `viewPadding` 保留物理刘海高度。A 必须沿用这个选择。

### 3.4 弹幕库可自由改

`canvas_danmaku` 已是本地 fork（[pubspec.yaml:119-120](simple_live_app/pubspec.yaml:119) 的 `dependency_overrides` 指向 `../third_party/canvas_danmaku`）。如果 A 的列表形态需要复用弹幕的富文本/表情渲染，可以直接改 fork，不受上游限制。

顺带一个已核实的既有缺陷：**`danmuStrokeWidth`（描边宽度）配置项定义了但从未生效** —— `buildDanmuView` 构造 `DanmakuOption` 时没传它（[player_controls.dart:960-990](simple_live_app/lib/modules/live_room/player/player_controls.dart:960)），`initDanmakuController` 里那段带 strokeWidth 的 `updateOption` 在 [player_controller.dart:399-409](simple_live_app/lib/modules/live_room/player/player_controller.dart:399) 整段被注释掉了。设置页也没有对应条目。

即：有一个设置字段是死的。A 动弹幕渲染时可顺手接上或删掉，但**这是独立缺陷，不属于 A 的范围**。

### 3.5 A 的风险

**中等，主要在「两套弹幕形态并存」的状态管理上。**

| 风险 | 说明 |
|---|---|
| 形态切换时机 | `isVertical` 变化 → 滚动弹幕与列表弹幕互换。切换瞬间已渲染的弹幕如何处置（清空？保留？）没有先例 |
| 换房窗口期 | 见 1.1，media_kit 不重置 `isVertical`，切房后形态可能短暂错误 |
| 与现有 Tab 聊天重复 | 竖屏下方 Tab 里本来就有「聊天」列表。播放器上再叠一个列表，同一份 `messages` 同时渲染两处 —— 是否要联动、滚动位置是否独立，需明确 |
| 遮挡画面 | 竖屏流本身就窄，左下角列表会遮挡画面内容。半屏高度上限缓解了这点，但仍需可关闭 |
| 性能 | `messages` 每条弹幕单独 `add()` 触发 Rx 通知（无批量刷新），同一份数据多一个 ListView 消费者，高弹幕量房间的开销**未实测** |
| TV app 无 `isVertical` | TV 侧相关代码全是注释，A 若要覆盖 TV 等于从探测层开始新建 |

## 5. 建议推进顺序

**B 先走，独立发布：**

1. 补齐 media_kit 换房重置 `isVertical`（1.1）—— 这是 B 正确性的前置，不是可选项
2. 统一 `exitFull` 的方向恢复（OHOS 对齐 Android/iOS）
3. 改两处默认值为 `false`
4. **实测 iPad 竖屏全屏的状态栏行为**，据结果决定是否按平台分默认值
5. 更新 UI 开关副标题文案（现有文案是站在「默认开」立场写的）
6. 可选：清理零调用的 `setPortraitOrientation()`

非全屏 letterbox（2.2 第三项）建议**不进 B**，单独立项。

**A 另行排期，内部顺序：**

1. 抽控制栏高度常量（3.3）—— 纯整理，无用户可见变化，可先行合并
2. 核实 `ChatMessageItem` 的换行/maxLines 行为
3. 明确设计决策：列表叠黑边还是画面、与下方 Tab 聊天是否联动、形态切换时已渲染弹幕如何处置
4. 基于 `buildChatList` 的 controller 逻辑做叠加列表（复用 `messages` 与 `disableAutoScroll`）
5. 接 `isVertical` 做形态切换
6. 实测高弹幕量房间的性能

**A 依赖 B 的第 1 步**（换房重置），所以 B 不做完 A 的方向切换会不稳。这是两者唯一的硬顺序约束。

## 6. 验证方案

**B：**

- 竖屏流进全屏保持竖屏（抖音/快手竖屏直播间）
- 横屏流进全屏仍转横屏（不能回归）
- 竖屏房间 → 横屏房间切换后立即进全屏，方向正确（验证 1.1 的修复）
- OHOS 退出全屏后横屏持握不被强制转竖屏
- iPad 竖屏全屏的状态栏实际表现（这项是决策依据，不是通过/失败判定）

## 8. 一句话结论

**B 不是新功能，是把一个已经写好的判定分支的默认值翻过来** —— 真正的工作在补齐它暴露出的三处既有不对称，以及确认 iPad 状态栏那个平台级取舍。

**A 比 README 标注的「大更新」要小** —— 数据源、滚动逻辑、安全区范式全部现成且有两份可参照实现；新写的部分集中在定位约束、底部避让、形态切换三处。但它依赖 B 的换房重置修复，且引入「两套弹幕形态并存」的状态管理，不宜与 B 捆绑发布。
