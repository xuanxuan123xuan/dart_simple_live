# 快手直播间冷启动加载失败设计

> 状态：问题已定位到代码链路，**未实施修复**。平台侧限流/风控现象仍需通过脱敏请求日志确认。
> 分支范围：dev
> 撰写日期：2026-08-06
> 观测到的现象：关注页或主页能显示快手正在直播的房间，但点击后长时间停留在“正在读取直播间信息”，播放器黑屏并持续转圈；刚打开 App 时更明显，等待一段时间或先观看其他直播后成功率提高。
> 关联：[[直播延迟优化设计.md]]（播放器延迟问题发生在房间详情成功之后，本问题的主要阻塞点更早）

---

## 1. 一句话结论

问题不是快手房间卡片的 roomId 或路由错误，而是**快手进入直播间时必须先抓取并解析网页详情，冷启动期间关注状态刷新又会并发抓取同一站点的网页详情**。快手站点对象没有共享请求会话、没有请求合并、没有按平台限速，且详情抓取失败后会顺序尝试多个网络请求；最终在直播间控制器中又被特殊处理成“不要显示错误，继续轮询”，所以用户看到的是黑屏转圈，而不是明确失败。

---

## 2. 现象与进入链路（已核实）

### 2.1 主页和关注页只负责展示，不负责拿播放地址

- 主页卡片点击直接调用 `AppNavigator.toLiveRoomDetail(site: site, roomId: item.roomId)`（`simple_live_app/lib/widgets/live_room_card.dart:11-18`）。
- 主页快手列表来自 `KuaishouSite.getRecommendRooms()`（`simple_live_core/lib/src/kuaishou_site.dart:334-367`），只把作者 ID、标题、封面和人数转换成 `LiveRoomItem`。
- 关注页点击最终调用 `AppNavigator.toLiveRoomDetail`（`simple_live_app/lib/modules/follow_user/follow_user_controller.dart:528-538`）。快手不会经过抖音专用的进入前 ID 校正逻辑。

因此列表显示“正在直播”只证明列表接口返回了可展示数据，**不证明进入房间所需的网页详情和播放 URL 已经可取**。

### 2.2 直播间首次加载的前置步骤是读取网页详情

`LiveRoomController.onInit()` 无条件调用 `loadData()`（`simple_live_app/lib/modules/live_room/live_room_controller.dart:590-622`）。

`loadData()` 的第一条关键网络链路是：

1. 添加系统消息“正在读取直播间信息”（`:1923`）。
2. 等待 `site.liveSite.getRoomDetail(roomId: roomId)`（`:1924-1927`）。
3. 只有详情返回后，才会根据直播状态调用 `_bootstrapPlaybackIfNeeded()`（`:1984-1994`）。
4. `_bootstrapPlaybackIfNeeded()` 再调用 `getPlayQualites()`，随后才会读取播放 URL、打开播放器（`:1432-1445`、`:2038-2080`）。

所以黑屏发生在播放器之前时，播放器参数、线路排序和 mpv/AVPlayer 还没有机会生效。

## 3. 快手详情请求的真实成本（已核实）

### 3.1 每次 `getRoomDetail` 都从网页重新建立 Cookie 上下文

`KuaishouSite.getRoomDetail()`（`simple_live_core/lib/src/kuaishou_site.dart:573-610`）每次调用都会：

1. 调用 `_getCookie(url)`（`:575-576`）。
2. `_getCookie()` 新建一个 `Dio` 和一个新的 `CookieJar`（`:943-947`）。
3. 请求 `https://live.kuaishou.com/u/<roomId>`，超时时间只有外层 `4s`（`:948-956`）。
4. 将本次响应的 Cookie 写回共享字段 `cookieObj` 和 `cookie`（`:957-968`）。

这不是一个复用的浏览会话：每个房间、每次状态刷新都会创建新的 CookieJar，多个并发调用还会同时写同一个 `KuaishouSite.cookie` 和 `cookieObj`。

### 3.2 解析失败后会顺序追加最多两次网页请求

网页内容必须包含并成功解析：

- `window.__INITIAL_STATE__`（`:646-655`）
- `jsonObj["liveroom"]`（`:656-658`）
- 非空 `liveroom["playList"]`（`:660-664`）

如果第一次网页预取解析失败：

- 当当前 Cookie 非空时，再用 Cookie 请求一次网页（`:582-587`）。
- 只要第一次结果不是明确 `live`，还会再发一次匿名网页请求（`:590-596`）。

`_loadRoomDetail()` 使用 `HttpClient.instance.getText()`，而 `HttpClient` 的连接、发送和接收超时均为 `20s`（`simple_live_core/lib/src/common/http_client.dart:29-36`、`:54-84`）。异常被 `_loadRoomDetail()` 吞掉并转换成 `null`（`kuaishou_site.dart:624-638`）。

因此一次冷启动详情读取可能走出以下时序：

| 阶段 | 请求 | 代码行为 | 失败时的代价 |
|---|---|---|---|
| 预取 | 网页请求 + 新 CookieJar | 外层 `4s` 超时 | 进入后续分支 |
| Cookie 重试 | 带 Cookie 的网页请求 | 最多使用 `HttpClient` 的 `20s` 超时 | 继续匿名请求 |
| 匿名重试 | 不带 Cookie 的网页请求 | 同样最多 `20s` | 详情最终失败 |

这解释了“看起来一直转圈”：详情链路没有总截止时间，页面会等待上述 Future 完成，而不是在一个较短的总预算内失败。

### 3.3 详情解析成功后才有播放地址

`_parseRoomDetail()` 从选中的直播条目提取 `liveStream["playUrls"]` 或 `selected["playUrls"]`（`:677-685`、`:749-753`），并将其放入 `LiveRoomDetail.data`。`getPlayQualites()` 只是在详情已成功返回后递归提取这些 URL（`:852-930`）。

所以“列表看到直播但播放器没有画面”并不矛盾：列表接口和详情网页是两套接口，后者失败时播放地址根本尚未进入 App。

## 4. 冷启动为什么更容易触发（已核实 + 待实测部分）

### 4.1 App 启动后会立即初始化快手站点和关注服务

服务初始化顺序中，`KuaishouAccountService` 和 `FollowService` 会在本地存储、数据库和设置初始化后立即注册（`simple_live_app/lib/main.dart:569-586`）。快手账号服务会把持久化 Cookie 写入 `KuaishouSite.customCookie`（`simple_live_app/lib/services/kuaishou_account_service.dart:17-41`），但不会建立可复用的网络会话。

### 4.2 关注状态刷新把快手完整详情当成“轻量状态请求”

关注刷新 worker 调用统一接口 `site.liveSite.getLiveStatusState(roomId: item.roomId)`（`simple_live_app/lib/services/follow_service.dart:344-362`）。

快手的实现不是轻量状态接口，而是直接调用完整 `getRoomDetail()`（`simple_live_core/lib/src/kuaishou_site.dart:835-843`），也就是每一个关注中的快手主播都会触发网页预取、解析和可能的重试。

代码注释明确认为状态请求“轻量且不再等待房间元数据”（`follow_service.dart:220-224`），但快手实现与该假设不符，这是当前架构中最关键的不对称。

### 4.3 默认并发最多四个 worker，没有快手专属并发上限

- 自动并发数在默认模式下最多为 `4`（`follow_service.dart:206-224`）。
- worker 按这个并发数同时运行（`:1184-1188`）。
- 只有抖音有单独的 limiter；快手没有类似的站点级限制（`:354-356`、`:373-375` 只处理抖音）。

因此冷启动时，关注刷新可能与用户点击的房间详情请求同时访问 `live.kuaishou.com`。这些请求还会共享一个可变的 `cookie`/`cookieObj`，但每个请求使用独立的 `CookieJar`，容易形成以下竞态：

```text
关注刷新 worker A -> 快手房间 A -> 新 CookieJar -> 写共享 cookie
关注刷新 worker B -> 快手房间 B -> 新 CookieJar -> 写共享 cookie
用户点击房间 C   -> getRoomDetail(C) -> 读取/写入同一组共享 cookie
```

是否已经被快手返回 403/429、挑战页或空壳 HTML，需要真实请求日志确认；但**并发完整网页抓取 + 共享可变 Cookie 状态**已经是代码层面的确定问题。

### 4.4 “看一会其他直播后恢复”符合会话热身特征

成功打开任意快手房间后，站点对象已经得到一组响应 Cookie，网络连接和 DNS/TLS 也可能已建立；后续详情请求更可能命中可解析的页面。这个现象与冷启动阶段的首轮 Cookie/网页请求失败或被平台暂时拒绝相吻合，但目前没有脱敏日志证明具体是哪个响应码或哪种挑战页面。

## 5. 为什么用户只看到黑屏转圈（已核实）

### 5.1 快手详情失败被特殊吞错

`loadData()` 的 catch 对快手单独处理（`simple_live_app/lib/modules/live_room/live_room_controller.dart:2005-2020`）：

- `roomLiveState` 重置为 `unknown`
- `loadError` 保持 `false`
- 启动在线状态轮询

其他平台会把 `loadError` 设为 `true` 并展示错误页；快手则故意不展示错误。因此即使 `getRoomDetail()` 最终抛出“快手直播间详情解析失败”，页面也不会进入“直播间加载失败”界面。

### 5.2 重试不是立即的

快手失败后依赖 `_restartOnlineRefreshTimer()` 再次调用详情接口；轮询请求本身还有 `8s` 超时（`live_room_controller.dart:1370-1382`），首次重试延时按当前显示状态通常为 `10s` 或 `45s`（`:1361-1367`）。

这正好对应用户观察到的“必须等一会”：首次详情请求可能已经失败，但 UI 不提示；下一次后台轮询成功后，才重新进入播放地址和播放器初始化。

### 5.3 播放地址暂时为空也会继续等待

如果详情成功但 `getPlayQualites()` 提取不到 URL，快手在已判定直播时会设置 `waitingForPlaybackUrl = true`，不显示错误（`:2051-2056`）。这属于第二个等待态，必须和“详情网页请求失败”通过日志区分。

## 6. 根因分层

| 层 | 根因 | 证据状态 | 影响 |
|---|---|---|---|
| L1 请求模型 | 快手状态查询复用完整网页详情抓取，没有独立轻量状态路径 | 已核实 | 关注刷新和进房请求成本过高 |
| L2 并发 | 冷启动关注刷新最多四路并发，快手没有站点级限速/单飞 | 已核实 | 与用户点击请求竞争同一站点和共享 Cookie |
| L3 会话 | `_getCookie` 每次新建 `Dio + CookieJar`，结果写入共享可变 Cookie 字段 | 已核实 | 会话不复用，并发写状态存在竞态 |
| L4 超时 | 预取 `4s` 后可能串行追加两个 `20s` 网页请求，没有总截止时间 | 已核实 | 首次进入可能长时间停留在加载态 |
| L5 UI/错误 | 快手加载异常保持 `loadError=false`，改用延迟轮询恢复 | 已核实 | 用户看到黑屏转圈，无法判断是失败还是等待 |
| L6 平台响应 | 快手可能返回挑战页、空壳 HTML、403/429 或暂时不可解析响应 | 待日志确认 | 解释冷启动和热身后的成功率差异 |

**当前最可信的根因组合是 L1-L5 共同作用；L6 是需要实测确认的外部触发条件，而不是目前可以直接断言的唯一根因。**

## 7. 现成的部分（已核实）

### 7.1 直播状态已经支持三态

`LiveStatusState` 有 `live`、`offline`、`unknown` 三种状态（`simple_live_core/lib/src/model/live_room_detail.dart:3-7`），快手也已经通过 `getLiveStatusState()` 返回 `unknown` 而不是把请求失败误报为下播（`kuaishou_site.dart:835-843`）。

这可以作为修复后的状态机基础：请求失败应保持 `unknown` 并展示可重试状态，不应继续伪装成普通加载。

### 7.2 直播间已有请求代次保护

`LiveRoomController` 已有 `_loadGeneration`、`_playbackRequestRevision` 和 `_isCurrentLoad()`/`_isCurrentPlaybackRequest()`，能够阻止旧房间或旧线路请求回写新房间（`live_room_controller.dart:2034-2036` 及播放链路）。

因此本问题不需要重新设计整套房间切换竞态；需要补的是快手站点内部请求的单飞、会话和截止时间。

### 7.3 失败后已有轮询恢复入口

`_refreshRoomStatus()` 会在轮询成功后重新调用 `_bootstrapPlaybackIfNeeded()`（`live_room_controller.dart:1370-1395`）。这可以保留作为后台恢复，但不能再作为唯一的用户可见反馈。

## 8. 修复方向

### 8.1 P0：先消除冷启动请求竞争

1. **快手详情请求加站点级单飞/队列**：同一 `KuaishouSite` 同时只允许一个网页详情引导请求，至少先把 `_getCookie` 和 Cookie 合并写入串行化。
2. **状态刷新对快手使用更低并发**：在 `FollowService` 中按 `siteId` 分组限速，快手状态请求先按 1 路串行或严格间隔执行，不能沿用通用最多 4 路并发。
3. **进入房间请求具备优先级**：用户点击后，后台关注刷新应暂停、让出快手请求额度；不能让进入房间请求排在冷启动全量刷新之后。

这一阶段不需要改变快手接口，只减少同时打网页详情的数量，验证成本最低。

### 8.2 P0：复用同一个 Cookie 会话

把 `_getCookie()` 中临时创建的 `Dio` 和 `CookieJar` 提升为 `KuaishouSite` 的长期会话：

- `CookieManager` 只安装一次。
- 自定义 Cookie 在会话初始化时导入。
- 详情请求和必要的 API 请求使用同一 CookieJar。
- Cookie 更新通过一个明确的同步入口完成，不允许多个请求直接覆盖 `cookie`/`cookieObj`。

这一步的目的不是“保存更多 Cookie”，而是让网页预取、详情重试和播放前请求看到同一套会话状态。

### 8.3 P1：给详情链路增加总时间预算

当前每个子请求有超时，但整个 `getRoomDetail()` 没有总超时。建议：

- 设定一个总预算，例如 `8s`，预算耗尽后立即返回可识别的 `CoreError`。
- 子请求只能消费剩余预算，不能每次重新获得完整 `20s`。
- 记录每一阶段耗时：预取、Cookie 重试、匿名重试、解析。
- 不在详情方法内部无限增加重试次数。

预算不是为了强行提高成功率，而是防止用户在一个不可恢复的请求上等待几十秒。

### 8.4 P1：把“详情失败”和“播放地址暂未就绪”分开

现有 `waitingForPlaybackUrl` 只适合“已经确认直播，但暂时没有可用播放 URL”。详情网页请求失败应使用独立状态，例如：

- `roomDetailLoading`
- `roomDetailRetryableError`
- `playbackUrlWaiting`

快手详情失败时显示明确错误和“重试”入口；后台轮询可以继续，但不应把页面永久留在普通 CircularProgressIndicator。

### 8.5 P2：寻找快手轻量直播状态接口

`getLiveStatusState()` 不应长期调用完整 `getRoomDetail()`。应通过浏览器网络面板或快手官方网页请求确认是否存在按 roomId 查询直播状态/直播流的 JSON 接口，然后：

- 关注刷新只请求状态字段。
- 用户进入房间时再请求完整详情和播放 URL。
- 状态接口失败只返回 `unknown`，不触发网页详情重试风暴。

不能在没有抓包证据前直接编造接口地址；如果不存在可用轻量接口，至少要复用短 TTL 的详情缓存。

### 8.6 P2：增加短 TTL 详情缓存和单飞缓存

对同一 `siteId + roomId` 的成功详情保存短时间内存缓存，例如 `15-30s`：

- 关注状态刷新刚成功取得的详情可直接供进房使用。
- 同一房间同时被列表预览、状态刷新和用户点击请求时，只保留一个 Future。
- 播放 URL 失败时不缓存失败结果，避免把暂时故障固化。

缓存只能减少重复请求，不能替代平台限速和会话复用。

## 9. 不建议的修复

- **只把轮询间隔从 10s 改短**：会进一步增加网页详情请求，可能放大限流。
- **只在 `loadData()` 里多重试几次**：当前已经存在串行重试，继续增加会让黑屏等待更久。
- **只修改播放器初始化或 mpv 参数**：当前多数失败发生在 `getRoomDetail()` 返回前，播放器尚未打开。
- **把所有快手请求都改成匿名请求**：当前实现已经在详情阶段追加匿名请求，问题是请求模型和会话管理，不是单纯 Cookie 是否存在。
- **把所有 `unknown` 都当成 `offline`**：会把临时风控/网络失败误报成未开播，且掩盖真实根因。

## 10. 验证方案

### 10.1 必须新增的脱敏日志

在 `KuaishouSite.getRoomDetail()` 和 `_loadRoomDetail()` 增加以下字段，禁止记录完整 Cookie、播放 URL token 或身份信息：

- `requestId`、`roomId`、调用来源（关注状态/主页进入/关注页进入/房间轮询）
- 当前请求并发计数和等待队列长度
- 预取、Cookie 重试、匿名重试各自耗时
- HTTP 状态码、Dio 错误类型
- 响应是否包含 `window.__INITIAL_STATE__`
- `liveroom`、`playList`、可播放 URL 数量
- 最终状态：`live` / `offline` / `unknown` / `parse_error`

### 10.2 冷启动复现矩阵

| 场景 | 操作 | 需要比较的指标 |
|---|---|---|
| A | 冷启动，关注刷新开启，立即点击快手房间 | 详情请求并发数、首个响应状态、总耗时 |
| B | 冷启动，关闭进入关注页自动刷新，立即点击同一房间 | 是否仍出现详情解析失败 |
| C | 先进入其他平台直播，再进入快手 | Cookie 是否已存在、请求耗时是否下降 |
| D | 先成功进入一个快手房间，再切换第二个快手房间 | 会话复用后是否稳定 |
| E | 同时保存多个快手关注，冷启动后进入关注页 | 快手请求是否串行、是否出现 403/429/挑战页 |

### 10.3 成功标准

- 冷启动点击快手房间时，用户可见详情阶段总耗时有明确上限，不再无限转圈。
- 关注刷新不会与用户进入房间同时发起多路快手网页详情请求。
- 相同房间的并发请求合并为一个 Future。
- 详情失败能显示可重试错误；后台恢复成功后能自动进入播放流程。
- 日志能够区分“网页请求失败”“HTML 解析失败”“没有播放 URL”和“播放器打开失败”。

## 11. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 快手确实要求浏览器挑战或动态参数 | 高 | 先用脱敏日志确认响应内容，再决定是否需要 WebView/动态参数方案 |
| 全局串行快手请求降低关注页刷新速度 | 中 | 仅对快手限速，其他平台保持现有并发；增加短 TTL 状态缓存 |
| Cookie 会话复用导致旧 Cookie 污染新账号 | 中 | `setCookie`/`clearCookie` 时显式清空 CookieJar 并重新初始化 |
| 总预算过短导致弱网下误报失败 | 中 | 记录分阶段耗时，提供手动重试；不要通过无限延长页面加载解决 |
| 详情缓存使用了已过期播放 URL | 中 | 缓存短 TTL；播放器打开失败时只刷新 URL，不把房间直接判为下播 |
| 快手 `unknown` 处理改变现有自动恢复行为 | 中 | 保留后台轮询，但将 UI 状态与直播状态分开，覆盖冷启动和切房测试 |

---

## 12. 待核实项

1. 冷启动失败时快手实际返回的 HTTP 状态码和 HTML 内容是否为 403、429、挑战页或空壳页面。
2. `getRoomDetail()` 在失败样本中实际走了几次请求，各阶段分别耗时多少。
3. 关注页自动刷新是否在用户点击前已经启动，以及其中同时命中的快手关注数量。
4. `KuaishouSite.cookie` 与 `cookieObj` 的并发覆盖是否会造成请求头不一致。
5. 快手网页是否存在可按 roomId 获取直播状态/播放信息的轻量 JSON 接口。
6. 首页列表接口返回的数据中是否已经包含可安全缓存的 `liveStreamId` 或播放 URL。
7. 不同平台和不同客户端（Windows、Android、OHOS）是否都复现；当前代码分析覆盖主 app，未做真机矩阵验证。
8. 快手直播网页响应是否因 User-Agent、Referer、`Kww` 或自定义 Cookie 缺失而进入不同页面分支。

---

## 13. 一句话总结

快手列表能显示直播，只说明列表接口正常；进入房间时 App 又重新抓取网页详情。冷启动的关注状态刷新会以最多四路并发重复抓取快手网页，而每次请求都新建 Cookie 会话并可能串行等待最多两个 `20s` 重试；失败后又被 UI 隐藏成后台轮询，所以最终表现为“读取直播间信息”黑屏转圈。**第一优先级是快手请求单飞/限速与 Cookie 会话复用，第二优先级是总超时和错误呈现，最后才是继续寻找播放器层面的原因。**
