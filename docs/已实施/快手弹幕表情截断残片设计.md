# 快手弹幕表情截断残片设计

> 状态：**已实施，相关自动化测试已通过**；上游截断阈值（按字符还是字节、具体数值）尚未通过真实抓包标定。
> 分支范围：dev
> 撰写日期：2026-08-22
> 实施日期：2026-08-22
> 观测到的现象：快手长弹幕（尤其带多个 `[表情]` 的）会在末尾留下 `[`、`[奸` 之类的残缺文本；前面的表情都正常显示成图片，只有最后一个变成字面乱码。
> 关联：[快手直播请求频率限制设计](快手直播请求频率限制设计.md)（同属快手平台侧限制，但与请求调度无关）

---

## 0. 实施结果（2026-08-22）

- 快手弹幕解码新增尾部残片清理：末尾未闭合的 `[` 连同其后内容一并丢弃，残片长度上限 8 字符。
- 残片为整条内容时整条弹幕丢弃（不再产出空消息）。
- `message`、`spans`、`imageUrls` 全部基于清理后的文本派生，聊天列表与悬浮弹幕层显示一致。
- 修复两处兜底渲染路径的下标配对缺陷：`imageUrls` 被去重后，重复表情不再从第二个开始退化成字面文字。
- Core 33 项、canvas_danmaku 16 项、App 8 项测试通过。

---

## 1. 一句话结论

不是"整条弹幕被砍短"，而是**上游把文本截断在表情 token 中间**：`[奸笑]` 被切成 `[奸`，缺少右括号，匹配不上 `_kuaishouEmojiPattern`，于是以字面文字形式留在屏幕末尾。

截断发生在我们上游（快手服务端或发送方客户端），客户端无法避免，只能在解码时清理残片。

---

## 2. 排查过程与证据

用合成 protobuf 帧对解码层和渲染层做了实测，两层都**没有**任何长度上限：

```
解码层：RAW_LEN=104  OUT_LEN=104  SPANS=21   IMAGE_SPANS=20
        HUGE_RAW=1000 HUGE_OUT=1000 HUGE_SPANS=201
渲染层：n=5   width=325   boxes=5   lines=1  tailKept=true
        n=100 width=2700  boxes=100 lines=1  tailKept=true
```

进出字节一致，100 个表情仍是单行、尾部文字保留。逐项排除：

- `_kuaishouEmojiPattern` 的 `{1,64}` 上限：真实 token 最长 6 字，远未触及。
- 段落布局宽度：`_singleLineLayoutWidth = 1000000`，等于无限制。
- 表情占位符：每个 `[表情]` 塌缩成一个正方形占位框，**token 字符数不影响排版**。
- 聊天列表：`softWrap: true`，无 `maxLines`。
- `_normalizeMessageText`：只有一个 `trim()`。
- 传输层：`IOWebSocketChannel` 自行重组分片。

复现残片症状（喂入不完整 token）：

```
[奸笑][奸笑][奸笑][奸笑   → imageSpans=3  textSpans=["[奸笑"]
[奸笑][奸笑][奸笑][       → imageSpans=3  textSpans=["["]
20 个表情 + [奸           → imageSpans=20 textSpans=["[奸"]
```

按字节截断时切点可能落在汉字 UTF-8 三字节序列中间，`utf8.decode(allowMalformed: true)` 会留下 U+FFFD：

```
drop=2 → textSpans=["[奸�"]
drop=5 → textSpans=["[�"]
```

确认截断不是我们造成的：`readBytes` 长度不足会抛 `FormatException`，gzip / AES 路径遇到不完整数据整条解码失败。都不可能产出"前面完好、尾部半截"的结果。

---

## 3. 判据选择

`[奸笑]` 是 4 字符 / **8 字节**，表情越多越早撞上游长度上限，也越容易恰好切在 token 中间。

### 3.1 为什么放弃"已知表情名前缀"校验

初版只在残片能匹配已知 token 前缀时才剥除。实测词库数据后否掉：

- 两张词库 + 别名共 273 个 token，名字长度分布 1 字 ×25、2 字 ×156、3 字 ×64、4 字 ×25、5 字 ×1、6 字 ×2。
- 其中 **210 个不同单字**会触发剥除，且都是中文高频字：`一 上 不 你 我 好 想 快 爱 笑 哈 哦 大 天 有 点 生 白 火 钱` …
- 另有 25 个 token 的完整名字就是单字（`[汗] [赞] [色] [钱] [火] [哦]` …），`[汗` 这种残片**无法判断**原本是 `[汗]` 被切还是用户手打。

即"词库刷得越全，能匹配的前缀越多，误伤越大"。而且它有反向盲区：快手新上线、本地词库尚未收录的表情，残片永远过不了前缀校验，会漏到界面上。

### 3.2 最终判据

**无条件剥除 + 残片长度上限**，有意接受误判：

1. `open = lastIndexOf('[')`，无 `[` 则原样返回。
2. `open` 之后存在 `]`（括号闭合）则原样返回 —— 只处理末尾未闭合的 `[`。
3. 残片 = `substring(open + 1)`，去掉尾部 U+FFFD。
4. 残片长度 > 8 则原样返回。
5. 否则返回 `substring(0, open)`。

**根本的歧义**：`...[我` 这个字符串，截断产生的和用户手打的**字节完全一致**。区分它们所需的信息在上游就已丢失，没有算法能做到，只能选择错误率和让哪一侧的错误更便宜。

### 3.3 上限 8 的作用

真实表情名最长 6 字，所以合法残片一定很短。上限用来**兜住误判的破坏力**：`substring(0, open)` 会删到结尾，没有上限时误判会吞掉不受限长度的尾巴。

```
主播这个操作[笑死我了哈哈哈哈哈   残片 9 字 > 8 → 整句保留
```

无上限时这句会连 `[` 一起丢掉 10 个字符。取 8 而非 6 是给未来更长的表情名留余量。

U+FFFD 是铁证（用户键盘打不出来），先剥掉再判长度。

## 4. imageUrls 去重导致的下标错配

`_decodeCommentFeed` 对 `imageUrls` 做了 `.toSet()`，20 个相同 `[奸笑]` 塌成 1 个 URL（`IMAGE_SPANS=20` 但 `IMAGES=1`）。六个站点都是这个写法，属有意为之——该列表是预加载提示，不承担定位职责。

所有渲染端优先用 `spans`，所以正常路径不受影响。但两处兜底渲染（`Utils.contentParts`、`ChatMessageText._buildFallbackContentSpans`）是**按下标**配对 token 与 URL 且 URL 用完即 `break`：一旦 `spans` 为 null，重复表情的弹幕会第一个显示成图、其余全变字面文字。

改为：token 数 ≤ URL 数时保持原有下标配对；否则按**首次出现顺序**给不同 token 分配 URL，同一 token 的重复出现共用同一个 URL，正好反转上游的 `.toSet()`。

## 5. 表情映射表的更新方式（重要）

两张表性质不同，容易误解：

| 表 | 来源 | 更新方式 | 数量 |
| --- | --- | --- | --- |
| 网页表 | `live.kuaishou.com/live_api/emoji/panel` | 运行时拉取，**进程内仅一次** | 222 |
| 移动端表 | `apissl.kuaishou.com/rest/n/emotion/package/list/v2` | **手工抓包 + 跑脚本 + 发版** | 258 |

查表顺序：`_dynamicKuaishouEmoji` → `kuaishouMobileEmojiAssets` → `kuaishouEmojiAssets`。运行时刷新只覆盖第一层。

`_maybeRefreshEmoji` 由 static `_emojiRefreshStarted` 把关，全进程只放行一次，仅 cookie 变化（登录）再刷一次，**没有周期性刷新**。另有启动竞态：刷新是 `unawaited` 发出的，同时弹幕已在连，前几秒到的弹幕在旧表上匹配。刷新失败仅 `CoreLog.d` 记一行，静默保留内置表。

### 5.1 移动端接口无法在运行时拉取

实测（2026-08-22）：

```
裸请求      → {"result":40,"error_msg":"服务器繁忙，请稍后再试。"}
带 app 参数 → {"result":50,"error_msg":"签名验证失败"}
```

"服务器繁忙"是障眼法，加上 `appver/client_key/os` 后露出真实原因：需要快手 Android 客户端签名（`__NS_sig3` 一类），算法在 native 层，仓库无任何快手签名实现。参照抖音签名移植进来是 10787 行，快手 native 签名只会更难，且随客户端版本失效。

这也是 `tool/generate_kuaishou_mobile_emoji.dart` 只接受 `--input response.json`、不自己发请求的原因。


**线上接口一个新表情都没多，反而比 08-12 的快照少 15 个。**那 51 个"移动端独有"表情（`[尊嘟假嘟] [憨笑哪吒] [猪猪] [打call] [都市丽人] [进度99]` …）panel 永不返回，但移动端快照里全都有，三层兜底可以命中。

### 5.3 更新移动端快照的步骤

需要真机/模拟器抓包，拿到 `emotion/package/list/v2` 的响应 JSON 后：

```bash
dart run tool/generate_kuaishou_mobile_emoji.dart \
  --input response.json \
  --output lib/src/danmaku/kuaishou_mobile_emoji_assets.dart \
  --client-version 14.7.10.49551 \
  --source https://apissl.kuaishou.com/rest/n/emotion/package/list/v2 \
  --generated-at 2026-08-12T14:38:01+08:00 \
  --expected-count 258
```

脚本会校验 `[都市丽人] [猪猪] [尊嘟假嘟] [憨笑哪吒]` 四个样本必须存在，且总数须等于 `--expected-count`（数量变化时要同步改这个参数和 `test/kuaishou_danmaku_test.dart` 里的断言）。同一 token 多处出现时先到先得。

**不建议**用 CI（GitHub Actions 的 Ubuntu runner 已支持 KVM 加速跑安卓模拟器）自动抓取：APK 获取、root 镜像装系统级证书做 MITM、Frida 绕证书固定与反调试、模拟器/root 检测、设备注册拿合法 `did`，每一环都会随客户端更新而断，维护成本远超手工更新。且当前数据新鲜度已优于线上接口。

## 6. 已知边界

- **上游截断阈值未标定**：按字符还是字节、具体数值都不确定，合成 protobuf 测不出来。抓到一条真实被截断的弹幕（dump field 3 原始字节）即可定标，届时可用"是否接近上限"作为更精确的判据，进一步压低误判。
- **有意接受的误判**：用户自己打出的、结尾带未闭合 `[` 且残片 ≤8 字的短文本（如 `你猜[`）会被删掉。破坏范围由上限兜住。
- **兜底路径的固有退化**：去重模式下，不同 token 数超过 URL 数时，多出来的仍会退化成字面文字（`[a][b][c]` 只有 1 个 URL → 1 图 + `[b][c]` 文字）。确实没有 URL 可用，与旧行为一致。本次修复只解决 token **重复**的情况，也正是去重造成的那种。
- 残片清理只作用于快手。抖音/斗鱼/虎牙用的是同一套方括号正则，如需同等处理要另抽公共函数。
