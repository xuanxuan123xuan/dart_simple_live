# 快手直播请求频率限制设计

> 状态：**核心治理已实施，相关自动化测试已通过**；部分集成验收、真实平台预算与冷却参数仍需补充定标。
> 分支范围：dev
> 撰写日期：2026-08-06
> 实施日期：2026-08-07
> 观测到的现象：在多个快手直播间之间来回切换，或多开选择两个及以上快手直播间后，会触发快手请求频率限制；用户观察到受限后当天无法继续观看快手直播。
> 关联：[直播延迟优化设计](直播延迟优化设计.md)（多开加载链路有交集，但与播放延迟无直接关系）、[跨平台聚合搜索设计](跨平台聚合搜索设计.md)（同属平台风控问题，但接口和流量来源不同）

---

## 0. 实施结果（2026-08-07）

- 新增快手进程级请求协调器：敏感请求串行执行，默认最小间隔 300ms 并带随机抖动；同 key 从排队开始即合并。
- 优先级顺序为用户进房、播放恢复、弹幕凭证、当前房间状态、关注后台刷新；多开使用独立来源并遵守最小间隔。
- 冷却窗口只允许一个用户主动探针；429 默认冷却 5 分钟，带 Cookie 的 403/安全验证页默认冷却 2 分钟。
- 稳定播放期间停止快手 10 秒全量详情轮询；未知状态指数退避至 300 秒，明确离线使用 45 秒低频复核。
- 关注刷新增加快手单路 gate；弹幕详情、websocketinfo 和 DID 上报纳入协调器。DID 5 分钟去重，弹幕凭证重试限制为最多 10 次/60 秒并线性退避。
- Cookie 会话、缓存和在途请求受 session epoch 保护；账号切换后旧请求不会污染新会话。
- 已通过协调器、站点、弹幕和网络诊断相关 Core 测试。跨进程实例无法共享预算，仍属于已知边界。

## 1. 一句话结论

这不是“多开同时播放两条流”本身触发的单点问题，根因是：**项目把快手的完整直播间页面抓取同时当作进房、直播状态轮询和关注刷新接口使用，却没有快手专用的全局请求调度、最小间隔、同房合并、缓存、限流识别或熔断。**

其中最严重的一条已核实：手机/桌面单直播间在成功播放后，仍每 `10s` 调一次完整的 `getRoomDetail`；一次成功调用至少包含一次房间 HTML GET，并通常附带一次 DID 日志 POST。理论下限就是每小时约 `360` 次房间详情抓取，若 DID 存在则总 HTTP 请求约 `720` 次。解析失败或进入风控响应后，一次轮询还可能放大为 `2–3` 次房间页面 GET，且仍以 `10s` 周期继续重试。

快速切房和多开只是把这个长期高频问题提前暴露：快速切房的旧请求只会被 generation 丢弃结果，**不会取消网络请求**；多开和关注刷新又会从其他入口继续调用同一个快手站点实例。受限之后，弹幕凭证的 `5s` 自动重试还可能继续追加详情页与 websocketinfo 请求，形成“越失败越请求、越请求越难恢复”的正反馈。

## 2. 根因摘要

| 层 | 已核实问题 | 结果 |
|---|---|---|
| L1 请求模型 | `KuaishouSite.getRoomDetail` 是完整网页抓取，不是轻量状态接口 | 单次调用成本高，失败时最多连续抓取三次同一房间页面 |
| L2 状态轮询 | 单直播间无论已成功播放还是未知状态，都每 `10s` 调完整 `getRoomDetail` | 单房间稳定观看也会持续制造高频请求 |
| L3 多入口调度 | 进房、切房、多开、关注状态、关注详情补齐共用该入口，但没有快手全局限流器 | 各业务只保护自己，无法控制进程级总频率 |
| L4 取消与合并 | 快速切房只有 generation 校验，没有取消令牌、同房 in-flight 合并或短时缓存 | 过时请求照样到达快手服务器 |
| L5 失败处理 | 快手网络异常和 HTTP 状态被内部吞掉并退化为通用解析失败 | 上层无法识别“已限流”，无法退避或熔断 |
| L6 重试放大 | 状态轮询和弹幕凭证各有独立重试；多开层还有第二套弹幕重连 | 受限后仍持续请求，延长恢复时间 |
| L7 会话管理 | 每次详情请求新建 `Dio` 和 `CookieJar`，再回写共享可变 Cookie 字段 | 会话复用不足；并发调用还存在 Cookie 覆盖竞态 |

**主因优先级：L2 > L3/L4 > L5/L6 > L7。** 只把多开改成串行不能解决问题，因为单直播间 `10s` 全量轮询本身已经足够高频，关注刷新也不经过多开队列。

## 3. 单次 `getRoomDetail` 实际会发出多少请求

### 3.1 第一跳必定是完整房间页面

`simple_live_core/lib/src/kuaishou_site.dart:573-576`：

1. 把 roomId 转成公开房间 URL。
2. 调 `_getCookie(url)`。
3. `_getCookie` 在 `:943-969` **每次新建一个 `Dio` 和一个内存 `CookieJar`**，然后 GET 完整房间页面。

它不是只取“是否开播”的小接口。页面返回后再从 `window.__INITIAL_STATE__` 解析直播状态、播放地址和弹幕字段（`:641-759`）。

### 3.2 解析不理想时会连续补抓

`getRoomDetail` 的分支（`:578-597`）：

| 条件 | 新增请求 |
|---|---|
| 首次页面解析成功且状态为 live | 不补抓 |
| 首次解析失败且当前有 Cookie | 再带 Cookie GET 一次同一房间页面 |
| 最终结果不是 live（含 null / offline / unknown） | 再匿名 GET 一次同一房间页面 |

因此一次 `getRoomDetail` 的房间页面 GET 数量是：

- **正常 live：最少 1 次**
- **解析降级：2 次**
- **首次失败 + Cookie 补抓仍非 live/失败：最多 3 次**

风控页面通常会缺少正常的 `__INITIAL_STATE__` 或直播字段。当前代码会把它当作“解析失败/未知状态”，恰好进入更多补抓分支。服务端越不愿返回正常内容，客户端单轮请求数越高。

### 3.3 每次成功详情还会异步上报 DID

`kuaishou_site.dart:603-608` 在每次成功返回详情前都会 `unawaited(_registerDid(...))`；`:1015-1031` 向 `log-sdk.ksapisrv.com/rest/wd/common/log/collect/misc2` POST 一次。

这个上报没有“仅首次进房”、最小间隔或同一 DID 去重。状态轮询拿到详情也会重复上报。

所以正常 live 的一次完整调用通常不是 1 个 HTTP 请求，而是：

```
1 × 房间页面 GET + 1 × DID 日志 POST
```

DID 日志域名是否与房间页面共用同一套服务端频率预算，代码无法证明；但它是确定存在的额外流量，且不应由状态轮询每 `10s` 触发。

## 4. 最大的持续流量来源：单直播间每 10 秒抓完整详情

### 4.1 轮询周期与调用目标

`simple_live_app/lib/modules/live_room/live_room_controller.dart:1358-1367`：

- 普通状态：`10s`
- 已确认离线并显示遮罩：`45s`

定时器进入 `_refreshRoomStatus` 后，在 `:1378-1382` 直接调用：

```dart
site.liveSite.getRoomDetail(roomId: roomId)
```

这里没有调用一个轻量状态端点，也没有针对快手降低频率。成功进房后 `loadData` 在 `:1984-1993` 无条件启动这套状态轮询，所以**正在稳定播放并不会停止轮询**。

### 4.2 理论请求量

按成功 live、每次 1 个页面 GET 计算：

| 观看时长 | `getRoomDetail` 轮询次数 | 房间页面 GET 下限 | 若每次都有 DID POST，则 HTTP 总量约 |
|---|---:|---:|---:|
| 10 分钟 | 60 | 60 | 120 |
| 1 小时 | 360 | 360 | 720 |
| 4 小时 | 1440 | 1440 | 2880 |

这还**不含**首次进房、切换房间、关注刷新、弹幕凭证、表情资源和播放 CDN 请求。

上述数字是根据定时器与代码分支算出的理论下限，不是抓包实测。快手真实阈值、计算维度（IP / Cookie / DID / 账号）和封禁时长均未在本地实测，不能把用户观察到的“一天”写成平台固定规则。

### 4.3 进入限流后不会自然降速

`loadData` 的 catch 在 `live_room_controller.dart:2011-2016` 对快手做了特殊处理：

- 不显示普通 load error
- 把状态保持为 unknown
- 清空离线确认次数
- 重新启动状态定时器

unknown 状态不满足 `showOfflineOverlay`，因此继续走 `10s`，而不是 `45s`。

`_refreshRoomStatus` 自身也在 `:1396-1403` 捕获失败后再次启动定时器。**没有指数退避、Retry-After、连续失败上限或熔断。** 一旦服务端开始拒绝，客户端仍会每 `10s` 发起一轮，而每轮可能因解析失败扩成 `2–3` 次页面 GET。

这是“触发后当天一直看不了”的重要客户端侧放大因素：服务端限制持续多久尚未核实，但当前客户端没有给它安静恢复的窗口。

## 5. 为什么来回切房会快速触发

### 5.1 每次切房都会重新走完整加载链

`live_room_controller.dart:3913-3971` 的 `resetRoom` 会停止旧弹幕和播放器，然后在 `:3959-3960` 调 `loadData()`；`loadData` 在 `:1924-1927` 重新调用 `getRoomDetail`。

### 5.2 generation 只防旧结果落地，不取消旧请求

`loadData()` 的签名是 `void loadData() async`（`:1900`），`resetRoom` 调用时无法 await，也没有向 core 传取消令牌。

`_loadGeneration` / `_isCurrentLoad`（`:1901`、`:1932-1934`、`:2034-2036`）只能做到：旧房间请求返回后不再写当前 UI。它**不能让已经发出的 HTTP 请求从网络上消失**。

因此快速切换 A → B → C 时，可能出现：

```
A getRoomDetail ──────────────> 返回后丢弃
      B getRoomDetail ────────> 返回后丢弃
            C getRoomDetail ──> 当前结果
```

对 UI 来说只有 C 有效；对快手服务器来说 A/B/C 全部是有效请求。若旧请求进入解析降级，每个还可能各自补抓 1–2 次。

### 5.3 同房间也没有请求合并和短时缓存

`KuaishouSite` 是 `Sites.allSites` 中的进程级单实例（`simple_live_app/lib/app/sites.dart:5-37`），具备做全局协调的天然落点；但当前 `getRoomDetail` 没有：

- `(roomId -> in-flight Future)` 合并
- 短 TTL 的详情缓存
- 上次成功状态缓存
- 全局请求队列
- 最小请求间隔

所以当前房间状态轮询、关注刷新或其他页面在同一时刻请求同一个 roomId，也会各发一套完整请求。

## 6. 为什么多开两个以上会触发

### 6.1 手机/桌面多开：页面内串行，但没有平台级间隔

每个 `MultiRoomPlayerController` 在 `multi_room_player_controller.dart:278-293` 的 `onInit` 中 `unawaited(load())`，每格加载都在 `:492-527` 调一次完整 `getRoomDetail`。

手机/桌面多开有一个已核实的缓解：`MultiRoomController` 在 `multi_room_controller.dart:117` 创建页面级共享 `PlayerMutationQueue`，每格在 `player_mutation_queue.dart:18-39` 中串行执行整个 load。因此同一多开页面里的格子通常不是同时打房间详情。

但这仍不能解决快手限制：

- 串行任务之间**没有最小时间间隔和抖动**，仍会背靠背抓多个完整页面
- 队列是“播放器变更队列”，不是快手请求队列
- 单直播间状态轮询、关注刷新、TV 端和其他页面不经过它
- 每格成功后都会再启动独立弹幕连接与可能的凭证补抓

因此“已有串行队列”不能当作快手限流方案。

### 6.2 TV 多开：确实会并发抓取

TV 端 `simple_live_tv_app/lib/modules/multi_room/multi_room_controller.dart:43-49` 为每格独立创建 controller；每个 controller 在 `multi_room_player_controller.dart:56-62` 直接 `unawaited(load())`，并在 `:126-150` 调完整 `getRoomDetail`。

TV 端没有手机/桌面这份共享 `PlayerMutationQueue`，所以多个格子首次构建时会并发请求。core 的 `KuaishouSite` 又是共享实例，这同时带来请求突发和共享 Cookie 字段竞态。

### 6.3 Cookie 会话不是可并发的共享会话

`KuaishouSite._getCookie` 每次新建独立 `Dio + CookieJar`，请求结束后把结果写回实例字段 `cookie` / `cookieObj`（`:943-967`）。多个调用并发时是“各自用临时 CookieJar 请求，完成后覆盖共享字段”，没有互斥和版本校验。

这不一定是频率限制的直接判定条件，但会让 DID/Cookie 会话不稳定，尤其是首次匿名并发进多个房间时。它应与全局请求串行化一起修，不应单独作为主方案。

## 7. 另外两条隐藏流量来源

### 7.1 关注状态刷新也等于完整进房请求

`KuaishouSite.getLiveStatusState`（`kuaishou_site.dart:835-847`）没有轻量实现，而是直接：

```dart
final detail = await getRoomDetail(roomId: roomId);
```

手机/桌面关注服务在 `simple_live_app/lib/services/follow_service.dart:344-362` 调用该方法。通用状态刷新默认自动并发最多 4，手动可配到 8（`:208-225`、`:1008-1011`、`:1184-1188`）；只有抖音经过 `DouyinFollowRefreshLimiter`，快手被放在普通任务队列中。

关注定时刷新默认间隔为 10 分钟（`app_settings_controller.dart:337-338`、`follow_service.dart:171-182`）。它不是单直播间流量的最大头，但会与进房/多开叠加，并可能一次并发刷新多个快手关注房间。

手动详情补齐阶段对非抖音使用最多 2 个 worker（`follow_service.dart:872-891`），同样没有快手间隔。

TV 关注服务也只为抖音建立专用 limiter；快手 `getLiveStatusState` 仍进入通用并发 worker。说明这个缺口横跨两个 app，不能只在手机多开 UI 上打补丁。

### 7.2 弹幕凭证缺失会每 5 秒继续请求

房间 HTML 没带完整 `liveStreamId + token + websocketUrls` 时：

1. `_resolveDanmakuCredentials`（`kuaishou_site.dart:793-832`）可能再抓一次房间详情。
2. 再请求 `/live_api/liveroom/websocketinfo`。
3. `_getWebsocketInfoWithRetry`（`:762-790`）失败后等待 `500ms` 再请求一次。
4. 仍拿不到时，`KuaishouDanmaku` 每 `5s` 调 credential resolver（`kuaishou_danmaku.dart:93-102`、`:161-203`）。

也就是说，一轮凭证解析最多追加：

```
1 × 房间页面 GET + 2 × websocketinfo GET
```

而且当前没有总次数上限。

手机/桌面多开又在 `multi_room_player_controller.dart:809-863` 对 `onClose` 建了一套 `3s / 6s / 12s ...` 外层弹幕重连。快手内部用 `onClose` 文案通知“凭证正在自动重试”时，外层也会把它当成连接关闭并安排重连，两套重试没有统一状态机。

这不是正常播放时的主流量；但风控/不完整响应正好更容易缺凭证，所以它是**受限后的重要放大器**。

## 8. 为什么当前无法识别并停止限流

`KuaishouSite` 的关键网络方法都吞掉了原始错误：

- `_getCookie`（`:943-969`）catch 后返回 null
- `_loadRoomDetail`（`:624-638`）catch 后返回 null
- `_parseRoomDetail`（`:641-759`）catch 后返回 null
- `_getWebsocketInfo`（`:972-1010`）catch 后返回 empty

最后 `getRoomDetail` 只抛一个通用的“快手直播间详情解析失败，请稍后重试”（`:599-600`）。HTTP `403` / `429`、验证码/挑战页、空页面、HTML 结构变化和普通网络错误在上层看起来几乎一样。

后果：

- 无法读取 `Retry-After`
- 无法按 403/429 进入长冷却
- 无法区分“主播离线”和“服务端不给正常数据”
- 无法记录第一次触发限流的端点与上下文
- 状态轮询只能把它当 unknown，并继续 `10s` 重试

**先保留错误类型和响应指纹，是实现退避/熔断的前置条件。**

## 9. 设计方向

### 9.1 第一优先级：停止稳定播放中的 10 秒全量详情轮询

这是收益最大、最集中的改动。

建议把“直播状态确认”按当前播放状态拆开：

| 当前状态 | 建议行为 |
|---|---|
| 正在稳定播放 | 不再每 `10s` 抓详情；依赖播放状态，或把快手状态复核降到分钟级 |
| 已知离线 | 使用低频轮询，并增加随机抖动 |
| unknown / 初次加载失败 | 指数退避，不固定 `10s` 永久重试 |
| 播放地址暂未就绪 | 使用有上限的短期重试，成功或达到上限后退出 |

不要只把 `10s` 改成 `30s`。那只是把问题延后 3 倍，仍保留全量页面轮询和失败正反馈。

### 9.2 第二优先级：给快手建立进程级请求协调器

协调器应放在 core 的快手站点层或其专用 service，而不是某个页面 controller，因为所有入口最终都经过同一个 `KuaishouSite`。

最小职责：

1. **全局串行或极低并发**：房间 HTML、状态查询、websocketinfo 等风控敏感请求进入同一预算。
2. **最小间隔 + jitter**：避免多开格子和关注刷新背靠背形成固定节奏。
3. **优先级**：用户主动进房 > 播放恢复 > 弹幕凭证 > 当前房间状态 > 关注后台刷新。
4. **同房 in-flight 合并**：同一个 roomId 同时请求时复用同一个 Future。
5. **短 TTL 缓存**：状态/详情在短窗口内复用；播放地址缓存时必须考虑 URL 有效期，不能无限缓存。
6. **全局冷却**：识别限流后，暂停所有快手后台任务，只允许受控的用户主动探测。

多开自己的 `PlayerMutationQueue` 可以保留，但它不再承担平台风控职责。

### 9.3 第三优先级：拆开“状态”和“详情”契约

`getLiveStatusState` 不应永久委托完整 `getRoomDetail`。有两条路线：

**路线 A：找到快手轻量状态端点（推荐先调研）**

- 只返回 live/offline/unknown
- 不刷新 Cookie、不解析播放地址、不注册 DID
- 仍经过快手协调器

**路线 B：没有稳定轻量端点时，使用详情缓存 + 低频复核**

- 当前播放会话直接视为 live，不额外抓页面
- 关注状态使用缓存和严格队列
- unknown 不等于 offline，不触发匿名补抓风暴

不能为了“轻量”重新使用一个更容易触发风控的私有接口；端点选择必须先抓包实测。

### 9.4 第四优先级：限流识别、指数退避和熔断

至少保留以下信号：

- HTTP status code
- `Retry-After`
- 响应 Content-Type
- 响应长度
- 是否存在 `window.__INITIAL_STATE__`
- 是否出现验证码/访问频繁/安全验证类页面特征（只记录分类，不写入完整响应和 Cookie）

建议状态机：

| 事件 | 行为 |
|---|---|
| 单次网络失败 | 短退避后有限重试 |
| 连续解析到异常页面 | 进入分钟级冷却 |
| 明确 403/429/频率提示 | 打开全局熔断，暂停关注刷新、状态轮询和弹幕凭证重试 |
| 冷却结束 | 只放行一个探测请求；成功后逐步恢复 |
| 用户主动进房 | 可提示当前处于冷却；不能同时唤醒所有后台任务 |

具体冷却时长不能凭空写死为“一天”，应根据实测响应头和恢复曲线决定，并允许指数增长和上限。

### 9.5 第五优先级：收敛 Cookie/DID 与弹幕重试

- 为 `KuaishouSite` 复用持久的会话级 `Dio + CookieJar`，不要每次详情请求新建。
- Cookie 更新放在协调器保护下，避免并发覆盖。
- `_registerDid` 只在会话/DID 首次需要时发送，至少做时间窗口去重；状态轮询绝不能重复注册。
- 快手弹幕内部凭证重试与多开外层重连合并成一个状态机。
- 凭证重试增加总次数/总时长上限，并服从全局熔断。
- 播放画面已经可用时，弹幕失败不应继续高频打详情接口。

## 10. 不建议的局部修补

| 方案 | 为什么不够 |
|---|---|
| 多开最多只允许一个快手房间 | 牺牲功能，但单直播间 `10s` 轮询和关注刷新仍存在 |
| 只把多开并发改串行 | 手机/桌面已经基本串行；缺的是全局间隔、跨入口预算和熔断 |
| 只把轮询从 10s 改成 30s | 仍是完整网页抓取，仍会无限重试 |
| 只增加随机 User-Agent | 不能减少请求量，还会让同一 Cookie/DID 的客户端指纹不稳定 |
| 限流后自动快速换 Cookie/DID | 可能被视为规避风控，风险更高，也会破坏登录状态 |
| 每个页面各做一个 limiter | 关注、单开、多开、TV 仍互相看不见，无法控制进程总量 |
| 解析失败时继续匿名补抓 | 当前已经这样做，正是失败放大的组成部分 |

## 11. 建议推进顺序

1. **先加只读请求观测**：端点分类、调用来源、roomId 哈希/脱敏标识、状态码、耗时、是否命中缓存/合并/熔断；严禁记录 Cookie、token 和完整播放 URL。
2. 停止快手稳定播放状态下的 `10s getRoomDetail`，把 unknown/失败改为指数退避。
3. 在 core 增加快手全局协调器：优先级、最小间隔、同房 in-flight 合并、短缓存。
4. 让关注刷新和两个 app 的多开全部经过协调器；快手后台关注刷新固定低并发，不能沿用通用 4–8 worker。
5. 保留 HTTP/响应分类，接入全局冷却与单探针恢复。
6. 复用 CookieJar，限制 DID 注册频率。
7. 合并弹幕两套重试，并让其服从熔断。
8. 最后再调具体间隔和缓存 TTL；这些参数必须由抓包和受控实测决定。

## 12. 验证方案

### 12.1 先建立当前版本基线

在不改变请求行为的前提下，记录以下场景的请求时间线：

1. 单个快手房间稳定观看 30 分钟
2. A/B/C 三个快手房间每 5 秒切一次，共 20 次
3. 手机/桌面多开 2 路、4 路
4. TV 多开 2 路、4 路
5. 同时触发关注刷新与进房
6. 模拟详情页面缺 `__INITIAL_STATE__`
7. 模拟 websocketinfo 返回空数据
8. 模拟 HTTP 403 / 429 / Retry-After

每个场景至少统计：

- 房间页面 GET 次数
- websocketinfo GET 次数
- DID POST 次数
- 最大并发数
- 任意相邻快手敏感请求的最小间隔
- 过时切房请求是否真正取消
- 限流后进入冷却所需请求数

### 12.2 修复后的硬验收条件

| 场景 | 验收条件 |
|---|---|
| 稳定播放 30 分钟 | 不再每 10 秒抓完整详情；请求数不随播放时长线性高速增长 |
| 快速切房 | 过时排队任务可取消；已发请求不补抓；最终房间优先完成 |
| 多开 4 个快手房间 | 快手敏感请求服从全局并发与最小间隔，TV 与手机/桌面行为一致 |
| 关注刷新叠加进房 | 用户进房优先，后台刷新让路且不形成并发突发 |
| 403/429 | 立即停止后台状态、关注与弹幕凭证请求；冷却期只允许单探针 |
| 弹幕凭证长期为空 | 重试有次数/时长上限，不影响已经成功的画面播放 |
| 同 roomId 多入口请求 | 只产生一条 in-flight 网络链路，其余调用复用结果 |

### 12.3 单元测试缺口

现有 `simple_live_core/test/kuaishou_site_test.dart` 主要覆盖标题、直播状态解析、清晰度和 URL 提取；`kuaishou_danmaku_test.dart:141-208` 覆盖凭证自动重试与 stop 取消。

当前缺少：

- `getRoomDetail` 各分支的精确请求次数测试
- 同房请求合并测试
- 多房全局最小间隔测试
- 优先级与后台让路测试
- 403/429/异常 HTML 的错误分类测试
- 熔断、冷却、单探针恢复测试
- 快速切房取消测试
- 单开/多开/关注同时请求的集成测试
- DID 注册去重测试

这些测试应使用可注入 fake transport 和 fake clock，不能依赖真实快手网络，否则测试本身也会制造风控风险。

## 13. 待核实项

1. **快手实际限流响应**：HTTP 状态码、响应头、页面内容特征目前没有用户日志或抓包证据。
2. **限流维度**：按公网 IP、Cookie、DID、账号、设备指纹还是组合计算，代码无法判断。
3. **恢复时长**：用户观察为“一天内无法观看”，尚未做分时探测，不能确认是否固定到自然日、滚动 24 小时或动态惩罚。
4. **阈值**：单房稳定观看、多房突发、websocketinfo 和 DID 日志是否共用预算未知。
5. **轻量状态端点**：仓库中没有快手专用轻量状态实现；是否存在稳定可用端点需要抓取官方 Web 行为核实。
6. **房间页面播放 URL 有效期**：决定详情缓存 TTL，不能在未核实前长时间复用。
7. **CookieJar 复用效果**：需确认快手响应 Cookie 的更新语义，以及多房是否允许共享同一 Web 会话。
8. **手机/桌面多开与单直播间能否同时存活**：页面路由通常会关闭旧页面，但桌面多窗口/副实例可能并存，未实测。
9. **跨进程限制**：当前设计的进程内协调器无法协调桌面多个进程；若多个实例共享同一公网 IP，仍可能合并触发平台阈值。
10. **TV 端账号 Cookie 注入时序**：已确认共用 core `KuaishouSite`，但 TV 登录态初始化与多开首次构建的先后未完整追踪。

## 14. 一句话总结

快手被限流的根因不是“用户切得太快”，而是项目没有把快手请求当作一种需要全局预算的稀缺资源：**一个正在正常播放的单房间就会每小时调用约 360 次完整详情，切房、多开、关注和弹幕再从不同入口叠加；一旦失败，固定轮询和凭证重试还会继续加压。**

正确方向是先移除稳定播放中的 `10s` 全量详情轮询，再在 core 建立快手进程级协调、合并、缓存、优先级、错误分类和熔断。只限制多开数量或把某一个页面改成串行，都无法从根上解决“一天内看不了快手直播”的问题。
