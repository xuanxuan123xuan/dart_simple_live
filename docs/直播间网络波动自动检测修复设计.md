# 直播间网络波动自动检测修复设计

> 状态：**核心修复已实施，相关自动化测试已通过**；跨会话异步与弱网真机验收仍待补充，本文根因分析保留为实施前基线。
> 分支范围：dev
> 撰写日期：2026-08-06
> 实施日期：2026-08-07
> 问题现象：直播间发生缓冲转圈后会自动检测网络；原地切换直播间时计数不会按新房间重置，网络正常时也可能提示丢包率过高，观测值经常固定为 `2/3`。
> 关联：[直播延迟优化设计](直播延迟优化设计.md)（共用播放器缓冲事件，但本文只处理网络诊断状态与诊断口径）

---

## 0. 实施结果（2026-08-07）

- `PlayerController` 已建立房间级诊断 generation；换房会清理计数、冷却、提示和 Timer，旧 Future/Timer 不得写入新房间。
- 自动诊断与自动降画质使用独立 tracker，均按 `false -> true` 边沿计数；诊断阈值为 30 秒内 3 次，起播 warmup 和稳定清零均为 8 秒。
- warmup 在 `player.open()` 前启动，覆盖播放器打开期间产生的起播 buffering 事件。
- 自动和手动诊断均优先探测当前实际播放 URL 的真实 host/port，再与外部目标分层比较。
- UI 已统一使用“TCP 连接失败 x/y”“目标不可达”等真实语义，不再把建连失败冒充丢包率；没有播放端点数据时不再推断本地网络异常。
- 已通过 Core 网络诊断测试及 Flutter 3.41 定向分析；弱网、代理和长时播放仍需真机验收。

## 1. 一句话结论

这是三个概念混在一起造成的复合问题，不是单一的“历史数据残留”：

1. **自动网络诊断的缓冲计数确实跨直播间残留。** `resetRoom()` 复用同一个 `PlayerController`，只停止播放器并加载新房间，没有清空 `_bufferingCount`、冷却时间、提示文本、提示定时器和正在运行的诊断任务。
2. **缓冲次数本身可能多算。** 自动诊断对每个间隔超过 `300ms` 的 `buffering=true` 都加一，没有按 `false -> true` 状态边沿计数；而同一文件的自动降画质逻辑已经明确承认播放器可能重复发送相同值。
3. **固定 `2/3` 不是缓存出来的旧结果。** 自动诊断硬编码每个目标只测 3 次，并把“连接公共 DNS 的 TCP 443 端口失败”直接叫作“丢包”。这只能得到以三分之一为步长的结果，而且目标端口拒绝、运营商拦截、代理策略和服务端限速都会被误判为本地网络丢包。

修复不能只补一行 `_bufferingCount = 0`。需要同时建立**房间级诊断会话边界**、改成**缓冲开始边沿计数**，并纠正“TCP 建连失败率 = 丢包率”的错误诊断口径。

## 2. 先区分三套“次数”，当前 UI 和代码口径并不一致

当前代码里有三套数字都与“转圈/检测”有关，很容易被理解成同一套计数：

| 计数 | 位置 | 当前阈值/样本数 | 用途 | 是否跨换房残留 |
|---|---|---:|---|---|
| 自动降画质缓冲开始次数 | `live_room_controller.dart:250-323, 638-675` | 30 秒内 3 次 | 自动降一档清晰度 | `getPlayUrl()` 时会延迟重置，但 `resetRoom()` 当下没有显式重置 |
| 自动网络诊断缓冲计数 | `player_controller.dart:1904-1910, 1985-2007` | **2 次** | 左上角显示网络诊断 | **会残留，且触发后也不归零** |
| 网络探测采样数 | `player_controller.dart:2019-2022` | 每目标 3 次 | 计算所谓“丢包率” | 每次新建局部结果，不会残留 |

因此，用户描述的“3 次转圈自动检测”与当前自动网络诊断实现并不完全一致：

- 真正的**网络诊断触发阈值是 2 次**，见 `player_controller.dart:1985, 1998`。
- 真正使用“3 次”的一处是自动降画质，另一处是每个网络目标的探测样本数。

后续修复和文案必须把三者拆开，否则即使代码改对，用户仍无法判断 `2/3` 指“两个直播间的转圈”、三个样本中的两个失败，还是三个目标中的两个不可达。

## 3. 当前自动网络诊断调用链（已核实）

### 3.1 订阅只在 Controller 初始化时建立一次

非 OHOS 路径在 `PlayerController.onInit()` 中调用 `initStream()`：

1. `player_controller.dart:1884-1888`：初始化播放器流订阅。
2. `player_controller.dart:1986`：监听 `player.stream.buffering`。
3. `player_controller.dart:1997`：收到符合条件的 `true` 后执行 `_bufferingCount += 1`。
4. `player_controller.dart:1998-2006`：计数达到 2、提示为空且不在 30 秒冷却期时启动 `_runAutoNetworkDiagnose()`。
5. `player_controller.dart:2019-2022`：对三个固定目标并发执行，每个目标采样 3 次。
6. `player_controller.dart:2027-2033`：把汇总结论写入 `networkHint`，8 秒后清空。
7. `live_room_page.dart:1080-1101`：直播画面左上角直接展示 `networkHint`。

该订阅直到整个直播间 Controller 关闭才在 `disposeStream()` 中取消（`player_controller.dart:2036-2048`）。普通的原地换房不会调用 `disposeStream()`。

### 3.2 原地换房复用同一个 PlayerController

`LiveRoomController.resetRoom()`（`live_room_controller.dart:3913-3975`）的行为是：

1. 替换 `rxSite` / `rxRoomId`。
2. 增加 `_loadGeneration`，使旧的房间加载请求失效。
3. 清空弹幕、SC、贡献榜等房间会话状态。
4. 调用 `player.stop()`。
5. 调用 `loadData()` 加载新房间。

这里**没有销毁或重建 `LiveRoomController` / `PlayerController`**，也没有任何自动网络诊断重置调用。

`resetRoom()` 已经显式清理了大量房间级状态，但漏掉了下面这些同样属于房间会话的字段：

| 字段 | 当前作用 | 残留后果 |
|---|---|---|
| `_bufferingCount` | 累计自动诊断触发次数 | A 房间的计数直接带入 B 房间 |
| `_lastBufferingTime` | 300ms 重复事件抑制 | 换房瞬间的新事件可能被旧时间戳吞掉 |
| `_lastAutoDiagnoseAt` | 30 秒诊断冷却 | B 房间可能因 A 房间刚诊断过而无法诊断 |
| `_autoDiagnoseRunning` | 阻止并发诊断 | A 房间任务未结束时，B 房间不能启动新诊断 |
| `networkHint` | 当前左上角提示 | A 房间的结果会继续显示在 B 房间 |
| `_networkHintTimer` | 8 秒后清空提示 | A 房间旧 Timer 可在 B 房间执行并修改 UI |

这就是“切换直播间后计数没有重置”的直接根因。

## 4. 根因一：自动诊断计数没有房间会话边界

### 4.1 `_bufferingCount` 在 Controller 生命周期内单调增加

全仓核查 `_bufferingCount`：

- 初始化仅一处：`player_controller.dart:1906`，赋值为 0。
- 增加仅一处：`player_controller.dart:1997`。
- **没有任何归零代码。**

这意味着它不仅不会在换房时重置，**触发一次网络诊断后也不会重置**。

例如：

1. A 房间缓冲两次，`_bufferingCount = 2`，触发诊断。
2. 提示 8 秒后消失，但 `_bufferingCount` 仍为 2。
3. 30 秒冷却结束后，A 房间或任何后续房间只要再收到一次 `buffering=true`，计数变成 3，会再次诊断。
4. 之后计数继续变成 4、5、6，不再具有“最近发生了几次缓冲”的含义。

当前实现实际表达的是“这个 Controller 自创建以来是否曾缓冲至少两次”，不是“当前直播间最近是否连续缓冲两次”。

### 4.2 房间加载 generation 没有覆盖网络诊断

直播间数据加载已经用 `_loadGeneration` / `_playbackRequestRevision` 防止旧房间异步结果覆盖新房间（例如 `live_room_controller.dart:1901, 1932-1934, 2122-2129`）。

自动网络诊断没有同等保护：

- `_runAutoNetworkDiagnose()` 不接收 room generation。
- `await NetworkDiagnoseService.diagnose(...)` 返回后只检查 `isPlayerClosing`（`player_controller.dart:2024`）。
- 原地换房时 `isPlayerClosing` 为 false。

因此，A 房间启动的诊断完全可能在切到 B 房间后完成，并把 A 房间触发的结果写到 B 房间画面上。这属于**异步结果串房**，不能靠清空计数单独解决。

## 5. 根因二：自动诊断没有按“真实转圈开始”计数

`player_controller.dart:1986-1997` 当前只处理 `buffering=true`：

- `false` 直接 return，不记录当前是否处于缓冲。
- 两个 `true` 只要间隔超过 300ms，就会被当作两次缓冲。

但同一份代码的 `LiveRoomAutoQualityBufferTracker` 已明确写出播放器事件的真实特性：

> A stream may emit the same buffering value more than once. Count only transitions into buffering.

对应实现位于 `live_room_controller.dart:281-295`：通过 `_isBuffering` 只计算 `false -> true` 的边沿，连续重复的 `true` 不增加次数。

自动网络诊断没有使用这套已经存在的防重复语义，只加了 300ms 时间去抖。若一次持续转圈期间播放器每隔一段时间重复广播 `true`，一次转圈就可能满足两次触发阈值。

因此“网络没有问题但很快触发检测”不一定是用户真的经历了多次独立网络波动，可能只是同一段缓冲状态被重复计数。

## 6. 根因三：“丢包率”实际上不是丢包率

### 6.1 当前测量的是 TCP 端口连接失败率

`NetworkDiagnoseService.diagnoseHost()`（`network_diagnose_service.dart:49-79`）每次执行：

```dart
final socket = await Socket.connect(host, 443, timeout: timeout);
await socket.close();
```

任何异常都执行 `lost += 1`。这里没有发送或统计网络数据包，也没有 ICMP ping、TCP 重传计数或播放器传输统计。

因此当前所谓 `lost` 实际包含：

- 目标根本没有监听 TCP 443；
- 目标主动拒绝连接；
- 公共 DNS 对短时间重复建连做限速；
- 运营商、路由器、防火墙或代理屏蔽某个目标 IP；
- IPv4 路由到该目标异常；
- 2 秒内没有完成 TCP 握手；
- 本机真正断网。

只有最后一类能直接支持“本地网络异常”。把所有异常统一显示为“丢包”是指标命名和归因错误。

### 6.2 默认目标与实际直播链路无关

默认目标（`network_diagnose_service.dart:42-47`）是：

| 目标 | 注释中的身份 | 自动探测端口 |
|---|---|---:|
| `223.5.5.5` | 阿里 DNS | 443 |
| `114.114.114.114` | 114 DNS | 443 |
| `8.8.8.8` | Google DNS | 443 |

它们被称为 DNS，但诊断没有连接标准 DNS 端口 53，而是统一连接 443。某个公共 DNS IP 能解析域名，不代表它承诺接受来自所有网络的 TCP 443 连接。

自动诊断也没有加入当前直播页面 host 或当前播放 URL 的真实 `(host, port)`。所以它最多判断“到三台固定 IP 的 443 端口是否容易建连”，无法直接判断当前直播 CDN 是否丢包或卡顿。

手动诊断面板会额外加入直播间页面域名（`live_room_page.dart:2335-2342`），但仍使用固定 443，也不是实际播放线路端点。

### 6.3 为什么结果会稳定为 `2/3`

自动诊断在 `player_controller.dart:2019-2022` 明确传入 `samples: 3`。丢包计算是 `lost / samples * 100`（`network_diagnose_service.dart:24-25`）。

所以单目标结果只能是：

| 失败数 | 显示比例 | 百分比 |
|---:|---:|---:|
| 0 | `0/3` | 0% |
| 1 | `1/3` | 33% |
| 2 | `2/3` | 67% |
| 3 | `3/3` | 100% |

如果“固定 `2/3`”指三个默认目标中固定有两个不可达，汇总同样会得到 `(100% + 100% + 0%) / 3 = 67%`。

两种解释都来自**固定目标 + 固定三次采样**，不是历史数据残留。

### 6.4 汇总阈值会放大小样本误差

`summarize()`（`network_diagnose_service.dart:167-192`）对所有目标的失败百分比做等权平均，只要 `avgLoss > 20` 就提示“丢包率偏高”。

在每目标只有 3 个样本时：

- 任一目标出现一次连接失败，就是该目标 33%。
- 三个目标中只要一个完全不接受 443、另外两个全部成功，整体仍是 33%。
- 33% 已超过 20% 阈值，于是直接归因为“网络不稳定”。

现有单元测试验证了给定 `lost/samples` 时的数学分支，但没有验证默认公网目标是否适合作为 TCP 443 探测对象，也没有覆盖“单个目标服务不可达但本地网络正常”的归因场景。

## 7. 设计方向

### 7.1 建立明确的房间级诊断会话（必须做）

在 `PlayerController` 提供一个单点重置入口，例如 `resetAutoNetworkDiagnosisSession()`，由 `LiveRoomController.resetRoom()` 在停止旧播放前调用。

该入口应一次性处理：

1. 缓冲计数归零。
2. 缓冲边沿状态归零。
3. 上次缓冲时间清空。
4. 诊断冷却时间清空，使新房间不继承旧房间冷却。
5. 取消旧提示 Timer。
6. 清空旧 `networkHint`。
7. 增加诊断 generation，使旧异步任务返回后只能丢弃结果。

**不能只把 `_autoDiagnoseRunning` 强行设为 false。** 旧 Future 仍在执行，这样会允许新旧两个任务并发，旧任务依然可能覆盖新结果。正确做法是 generation/token 校验：每次重置递增版本，任务完成后只有版本仍匹配才能写 UI。

### 7.2 自动降画质的 3 次计数也应在换房入口立即重置

`getPlayUrl()` 当前会调用 `_autoQualityBufferTracker.beginWarmup()`（`live_room_controller.dart:2195-2197`），一般能在新播放地址开始加载时重置 3 次缓冲计数。

但它不是严格的换房边界：

- `resetRoom()` 到 `getPlayUrl()` 之间还要异步读取房间详情和清晰度。
- 离线房间、读取失败或播放地址未就绪时可能根本走不到 `getPlayUrl()`。
- `_lastAutoQualityDownAt` 的 10 秒冷却不会被 `beginWarmup()` 清空。

建议在 `resetRoom()` 同一位置立即执行：

- `_autoQualityBufferTracker.reset()`；
- `_lastAutoQualityDownAt = null`；
- 新流真正打开时继续保留 `beginWarmup()`，过滤起播阶段的正常 buffering。

这样“换房清会话”和“每次重开流进入 warmup”是两层不同语义，不互相替代。

### 7.3 只按 `false -> true` 统计独立缓冲开始

自动网络诊断应采用与 `LiveRoomAutoQualityBufferTracker` 相同的状态边沿语义：

- 首次收到 `true`：记一次缓冲开始。
- 持续收到重复 `true`：不计数。
- 收到 `false`：结束本次缓冲，允许下一次 `true` 计为新事件。

可复用现有 tracker 的算法，但不建议让自动降画质和自动诊断共享同一个可变实例：两个功能的阈值、冷却、触发后重置策略不同，共享实例会互相消费状态。可以抽取同构类，各持有独立 tracker。

### 7.4 明确触发阈值和时间窗口

当前自动网络诊断是“Controller 生命周期累计 2 次”，没有统计窗口。建议改为：

| 参数 | 建议初值 | 理由 |
|---|---:|---|
| 独立缓冲开始次数 | 3 次 | 与用户认知及当前自动降画质阈值一致，降低起播偶发缓冲误触发 |
| 统计窗口 | 30 秒 | 只把短时间密集缓冲视为网络波动 |
| 起播 warmup | 8 秒 | 新流打开时的正常预缓冲不应计入故障 |
| 稳定清零 | 连续稳定 8 秒 | 网络恢复后不携带早先事件 |
| 自动诊断冷却 | 30 秒 | 防止持续故障反复探测 |

若产品仍希望保持“2 次就诊断”，也必须保留房间重置、状态边沿和时间窗口；阈值只是灵敏度选择，不是本问题的根因修复。

### 7.5 把“丢包率”改成与实际测量一致的指标

纯 Dart `Socket.connect` 可以继续作为低成本信号，但文案必须改成：

- “TCP 连接失败 `2/3`”，而不是“丢包率 67%”；
- “部分探测目标不可达”，而不是直接断言“本地网络不稳定”。

推荐把诊断拆成两层：

1. **实际播放端点信号**：优先探测当前播放 URL 的真实 `(host, port)`，复用 `findFastestLine()` 已有的 scheme/port 解析方式。它与当前卡顿链路最相关。
2. **外部连通性对照**：再探测少量明确提供 HTTPS 服务的域名/端口，用于区分“直播 CDN 单点异常”和“外网普遍异常”。单个固定目标失败不能独立判定本地网络坏。

若没有系统级 ICMP、平台网络统计或播放器重传指标，就不要继续使用“丢包率”这个名词。TCP 建连失败率与真实传输丢包率不是同一指标。

### 7.6 汇总采用可达性分层，而不是直接平均百分比

建议汇总顺序：

1. 当前播放端点可连接，且至少一个外部对照可连接：不能判定本地断网；提示“当前线路发生缓冲，可尝试切线/降画质”。
2. 当前播放端点失败，但外部对照成功：优先判断平台/CDN/线路问题。
3. 当前播放端点和多个独立外部对照均失败：才提示本地网络、代理或防火墙异常。
4. 只有少量连接失败：展示“探测结果不稳定”，不要用 3 个样本计算出看似精确的 67% 丢包率。

这比当前对三个不相关目标的百分比做算术平均更符合诊断目的。

## 9. 平台与多开范围

### 9.1 当前自动网络提示只覆盖非 OHOS 单直播间

`PlayerController.onInit()` 在 OHOS 分支提前 return（`player_controller.dart:1869-1882`），不会调用 `initStream()`，因此本问题所述 `_bufferingCount` 自动诊断链路不在 OHOS 上运行。

TV app 也没有复用这套 `networkHint` 自动提示。

### 9.2 多开有自己的缓冲统计，但没有这套自动网络诊断

`MultiRoomPlayerController` 有独立的 `_bufferingCount`（`multi_room_player_controller.dart:193-197`），并且按 `false -> true` 边沿累计（`:313-333`）。它用于多开遥测和自适应画质，不会调用 `NetworkDiagnoseService`，也不会显示单直播间的 `networkHint`。

因此本文修复范围应先限定为**手机/桌面普通直播间的 media_kit 路径**。若未来要给多开增加网络诊断，必须按每个格子的 room key 独立管理会话，不能复用一个全局计数器。

## 10. 验证方案

### 10.1 缓冲计数单元测试

1. 连续输入 `true, true, true`，只计一次缓冲开始。
2. 输入 `true, false, true`，计两次。
3. 计到阈值后触发一次并重置窗口，不因下一条重复 `true` 立即再触发。
4. 连续稳定超过 8 秒后，旧计数清零。
5. 超过 30 秒窗口后，旧计数清零。
6. warmup 内的 `true` 不计入故障。

### 10.2 换房会话测试

1. A 房间累计阈值前一档，切到 B 房间；B 的第一次真实转圈不能触发诊断。
2. A 房间刚诊断，30 秒内切 B；B 不应继承 A 的冷却时间。
3. A 房间提示仍在显示时切 B；B 画面不应显示 A 的提示。
4. A 房间诊断 Future 未完成时切 B；A 结果返回后不得写入 B 的 `networkHint`。
5. A 房间旧 8 秒 Timer 到期时，不得清空 B 房间后来产生的新提示。
6. 快速 A -> B -> C 连切时，只允许最新 generation 写 UI。

### 10.3 诊断口径测试

用本地假 TCP server 构造确定性场景：

1. 播放端点成功，三个对照目标中两个失败：不得显示“本地网络丢包率过高”。
2. 播放端点失败，对照目标成功：提示线路/CDN 问题。
3. 播放端点与多个对照目标全部失败：提示本地网络/代理/防火墙问题。
4. 三次采样失败两次：显示“连接失败 2/3”，不能显示“丢包率 67%”。
5. 一个目标完全不可达时，不应因简单平均超过 20% 就直接判定整个网络不稳定。

### 10.4 真实环境验收

至少覆盖：

- 稳定 WiFi 下切换 5 个直播间；
- 稳定 WiFi 下反复切清晰度和线路；
- 开启/关闭系统代理；
- 屏蔽 `8.8.8.8` 但保持普通网页和直播可用；
- 主动断网、弱网和恢复网络；
- Windows、Android、macOS/Linux 各自的 media_kit 路径；
- 直播 CDN 卡顿但普通网络正常的样本。

验收日志至少记录 room generation、缓冲边沿、窗口内计数、触发原因、探测 endpoint、连接成功/失败类型和结果是否因 generation 过期而丢弃。日志不得记录带 token 的完整直播 URL。

## 11. 建议推进顺序

1. 先为自动诊断状态抽出房间级 reset，并加 generation 防串房。
2. 把自动诊断改为 `false -> true` 边沿计数，补窗口、稳定清零和 warmup。
3. 在 `resetRoom()` 同时重置自动网络诊断与自动降画质会话。
4. 修改网络指标模型，把 `lost/lossRate` 更名或分离为 TCP connection failure，不再冒充丢包。
5. 改成“实际播放端点 + 外部对照”的分层诊断。
6. 更新左上角提示与手动网络诊断面板文案。
7. 最后做真实网络矩阵验收，按实测决定自动诊断阈值保持 2 还是改为 3。

前 3 步解决状态残留与误计数；第 4-6 步解决固定 `2/3` 和错误归因。只做其中一半都会留下用户可见问题。

## 12. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 换房时直接把 running 设 false，造成新旧诊断并发 | 高 | 使用 generation 丢弃旧结果，不把布尔值当取消机制 |
| 自动诊断和自动降画质共享同一个 tracker，触发后互相重置 | 高 | 只复用算法/类型，各自持有独立状态 |
| 阈值从 2 改 3 后诊断过迟 | 中 | 真实环境对比误报率与触发时延，再定最终值 |
| 探测当前播放端点增加 CDN 建连 | 中 | 低频、短超时、复用冷却；不发送媒体请求，不高频重试 |
| 固定公网对照目标在部分地区不可达 | 高 | 多目标分层，单目标失败不归因本地网络；目标必须明确支持对应端口 |
| 文案继续使用“丢包”导致错误排障 | 高 | 无真实丢包数据时统一称“连接失败/目标不可达” |
| 起播 buffering 被当成故障 | 中 | 新流打开后设置 warmup，不计正常预缓冲 |
| 旧 Timer 清理新提示 | 中 | Timer 回调同样绑定诊断 generation |

## 13. 待核实项

1. 用户看到的“固定 `2/3`”具体来自日志、左上角汇总，还是手动诊断面板；三处表达的含义可能不同。
2. media_kit 在 Windows、Android、macOS/Linux 上是否都会在同一段缓冲内重复发送 `buffering=true`；代码注释已确认“可能重复”，但各平台频率未实测。
3. 三个默认 IP 在用户当前运营商下的 TCP 443 实际可达性；代码没有任何运行时日志记录异常类型。
4. 自动诊断最终阈值应保持 2 次还是与自动降画质统一为 3 次；本文倾向 3 次独立缓冲开始，但需要产品口径确认。
5. 当前播放 URL 在播放器已连接后再做一次独立 TCP 探测，是否会触发部分平台/CDN 的连接频率限制。
6. 系统代理模式下 Dart `Socket.connect(IP, 443)` 是否绕过代理，从而稳定失败；需要按各平台代理实现实测。
7. OHOS 是否需要等价的自动网络诊断。当前代码路径明确没有启用，本文不扩大范围。
8. TV app 和多开是否要增加同类提示。当前两者均不使用单直播间这套自动诊断状态。

## 14. 与其他设计的关系

- **[直播延迟优化设计](直播延迟优化设计.md)**：缓冲、客户端缓存和端到端延迟是不同信号。本文只修复缓冲事件计数与网络诊断归因，不改变低延迟档、追帧环、选流或选线策略。
- **自动降画质**：与自动网络诊断共享播放器 buffering 数据源，但应保持独立阈值和独立状态，避免一个功能触发后破坏另一个功能的统计窗口。
- **后台线路测速**：`NetworkDiagnoseService.findFastestLine()` 已按播放 URL 的真实 endpoint/port 探测，可复用端点解析方法；不能直接复用其“最快线路”结论作为网络健康结论。
- **多开自适应画质**：已经使用缓冲状态边沿，说明边沿计数是项目内现成范式；本文不改变多开逻辑。

## 15. 一句话总结

换房残留是真的，但固定 `2/3` 不是旧数据：**前者是 PlayerController 复用时漏清房间级诊断状态，后者是把三次 TCP 443 建连失败错误命名为丢包率。** 同时修复会话边界、缓冲边沿计数和诊断指标口径，才能让自动提示既不串房，也不在网络正常时给出看似精确但实际错误的“67% 丢包”。
