# Pure Live 功能借鉴评估

## 1. 评估范围

本文对比当前 Simple Live 与 [liuchuancong/pure_live](https://github.com/liuchuancong/pure_live) 的公开功能，目的是筛选值得借鉴的产品能力和实现思路，不建议直接复制页面或控制器代码。

Pure Live 当前 `master` 分支的项目定位是 Flutter 多平台直播聚合播放器，支持 Bilibili、虎牙、斗鱼、快手、抖音、网易 CC、Twitch、SOOP，以及自定义 M3U/M3U8 直播源。本文评估基于 2026-08-18 读取到的仓库状态。

## 2. 当前项目已经具备的能力

Simple Live 当前已经具备或正在建设以下能力，因此不需要从 Pure Live 直接迁移：

- 五个平台直播：虎牙、斗鱼、Bilibili、抖音、快手。
- 跨平台聚合搜索、单平台分页、关注和标签分组。
- 弹幕接收、弹幕屏蔽词、多开同屏和多路播放器控制。
- mpv 播放、线路选择、自动选线、延迟优化和网络波动诊断。
- 桌面端小窗/画中画、远程同步、WebDAV 和配置导入导出。
- 抖音、Bilibili、快手等平台的 Cookie 或网页登录能力。

因此，平台数量、基础搜索、基础弹幕和多开不是本次借鉴的重点。

## 3. 值得优先借鉴的功能

| 优先级 | 功能 | 价值 | 难度 | 建议 |
|---|---|---:|---:|---|
| P0 | M3U/M3U8 自定义直播源 | 很高 | 中 | 首先实施 |
| P0 | IPTV 分组、频道管理和 EPG | 很高 | 中高 | 与自定义源配套 |
| P1 | Android 播放器内核切换 | 很高 | 高 | 先手动切换，后自动兜底 |
| P1 | 弹幕高级样式和参数 | 高 | 中 | 增量补齐现有播放器 |
| P1 | 独立小窗弹幕队列 | 高 | 中高 | 与现有画中画结合 |
| P2 | DLNA 投屏 | 中高 | 中 | TV/桌面端优先 |
| P2 | ASMR 纯音频和后台播放 | 中高 | 中 | 可与定时关闭一起设计 |
| P2 | 直播录制和本地回放 | 高 | 高 | 单独立项 |
| P2 | Twitch 接入 | 中 | 中高 | 参考已有 Twitch 构思文档 |
| P3 | 动态刷新率适配 | 中 | 中 | Android 专项优化 |

## 4. 重点功能分析

### 4.1 自定义直播源和 IPTV

Pure Live 的 IPTV 模块支持本地或网络直播源导入，并提供分组、频道、收藏、EPG 和自动同步能力。这个方向与 Simple Live 的现有能力互补度最高，可以把应用从“五个平台观看器”扩展为“平台直播 + 任意直播源”。

建议拆成以下数据模型：

```text
Playlist
  ├─ Source: local / network
  ├─ Group
  ├─ Channel
  └─ EpgBinding
```

建议分阶段实施：

1. 第一阶段：M3U/M3U8 导入、解析、分组和频道播放。
2. 第二阶段：本地文件、网络源定时同步和频道收藏。
3. 第三阶段：XMLTV/JSON EPG 导入、自动匹配和节目单展示。

第一阶段不需要引入账号体系，也不影响现有五个平台接口。

### 4.2 播放器内核切换

Pure Live 在 Android 上提供 IJKPlayer、ExoPlayer 和 MPV 切换，用于应对黑屏、硬解兼容、特定编码失败和卡顿问题。

Simple Live 当前已经深度使用 `media_kit/mpv`，鸿蒙也有独立播放器实现，因此不建议直接照搬播放器层。建议借鉴其“播放策略”而不是代码：

```text
默认播放器失败
    -> 提示或尝试备用内核
    -> 记录平台/线路/设备的成功内核
    -> 下次优先使用成功配置
```

落地顺序建议是：先支持 Android 手动切换，再增加单房间自动兜底，最后评估是否需要按平台和线路记忆内核。

### 4.3 弹幕高级控制

Pure Live 提供的可借鉴参数包括：

- 字号、透明度和描边。
- 滚动速度、显示区域和最大弹幕数量。
- 弹幕刷新 FPS。
- 使用平台原色或统一颜色。
- 用户屏蔽、关键词屏蔽。
- 弹幕点击和长按操作。

Simple Live 已有弹幕屏蔽词和多开弹幕基础，适合按以下顺序增量实现：

1. 补齐字号、透明度、速度、区域和颜色设置。
2. 将主播放器和小窗弹幕队列、样式、生命周期彻底隔离。
3. 增加点击/长按后的复制、屏蔽用户等操作。
4. 结合竖屏弹幕设计，按窗口尺寸动态调整字号、最大数量和显示区域。

### 4.4 录制、投屏和纯音频

- **录制**：用户价值明显，但需要处理 FFmpeg 或平台原生录制、磁盘空间、权限、断线续录、文件命名和回放列表，建议单独设计，不要混入播放器控制器。
- **DLNA**：对 TV、平板和桌面端有实际价值，建议先验证设备发现、鉴权和 HLS/FLV 兼容性，再决定是否进入主版本。
- **ASMR/纯音频**：可以复用后台音频、媒体通知和定时关闭能力，适合做成播放器模式，而不是单独的直播平台功能。

## 5. 不建议直接迁移的内容

### 5.1 Firebase 用户同步

Simple Live 已有远程同步、WebDAV、配置导入导出和本地数据管理。再引入 Firebase 会增加账号、隐私、服务配置和维护成本，当前没有明显收益。

### 5.2 本地互动经济系统

Pure Live 的本地用户、体验币、礼物目录、等级和礼物动画偏向互动社区。Simple Live 当前定位是不提供账号付费、写操作或官方活动参与功能，这部分与产品边界不一致，不建议引入。

### 5.3 大段复制 UI 或基础设施

不要直接复制 Pure Live 的页面、控制器、GetX 基础设施或资源目录。应优先参考功能边界、数据模型和异常处理方式，在 Simple Live 现有的 Core/App 分层中重新实现。

## 6. 推荐实施顺序

1. M3U/M3U8 自定义源、分组、收藏和基础播放。
2. 弹幕高级样式与独立小窗弹幕队列。
3. Android 播放器内核手动切换。
4. EPG 导入、匹配和节目单。
5. DLNA 投屏。
6. 直播录制与本地回放。
7. Twitch 平台接入。
8. ASMR 纯音频、后台保活和定时关闭整合。

其中第 1、2 项最适合近期实施，既能明显提升用户价值，也不会破坏现有五平台、多开和鸿蒙播放器架构。

## 7. 许可证与合规

Pure Live 当前仓库许可证为 **AGPL-3.0**，Simple Live 当前仓库为 **GPL-3.0**。迁移时应遵循以下原则：

- 借鉴产品思路、交互方式和抽象数据字段，不等于复制代码。
- 直接使用 Pure Live 的源码、图片、协议实现或其他资源时，必须保留版权和许可证信息，并评估 AGPL 对派生作品和网络服务修改的义务。
- 优先采用独立实现，避免整段复制页面、控制器和工具类。
- 平台表情、图标、礼物素材仍需单独确认其来源和授权范围。

## 8. 结论

Pure Live 最值得 Simple Live 借鉴的是 **自定义直播源/IPTV、播放器容错、弹幕高级控制** 三个方向。它们分别补足内容来源、播放稳定性和观看体验，且与 Simple Live 现有架构有较好的结合点。账号互动、Firebase 同步和大量 UI 基础设施不建议迁移。
