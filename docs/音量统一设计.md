# 音量统一设计

> 状态：设计草案，未动任何代码
> 分支范围：dev
> 撰写日期：2026-08-04
> 需求原话：各平台基准音量不同，要在本 App 内调成一样；在上一个直播间设的音量，切到另一个平台也得保持（**不调整系统音量的前提下**）

---

## 1. 需求拆解：这是两个独立问题

原始描述里含两个技术上几乎无关的子需求，必须分开设计，否则会互相拖累：

| 子问题 | 本质 | 难度 |
|---|---|---|
| **A. 音量记忆跨房间/跨平台保持** | 状态管理 + 生命周期 | 低，且现状已接近可用 |
| **B. 跨平台基准响度归一化** | 音频信号处理 | 高，且**受平台能力硬限制，无法全平台一致** |

A 是「把已有机制的漏洞补上」，B 是「新增一套能力，且部分平台做不到」。

**建议把 A 与 B 作为两个独立特性排期**，A 先行。理由见第 7 节。

> **与 README Roadmap 的差异**：README 现有条目「音量统一 | 多开时各格音量归一化，任一格调音量同步到全部」描述的是**多开同屏各格同步**，与本文档的 A/B 都不是同一件事。三者是并列的独立需求，需确认 Roadmap 那一行是否要改写或拆分。本文档不覆盖多开各格同步。

## 2. 平台能力矩阵（决定 B 的天花板，已核实）

| 后端 | 适用平台 | 音量上限 | 音频滤镜注入 |
|---|---|---|---|
| media_kit (libmpv) | Windows / Linux / macOS / Android 主路径 | `volume` **无 clamp**，`setVolume` 直接透传 libmpv（`real.dart:781-797`），实际受 libmpv `volume-max` 约束，而 media_kit **从不设置该属性** | ✅ `af` 可注入，未被过滤 |
| media_kit iOS | iOS | 同上 | ❌ **不可能** —— `applyToPlayer` 无条件 `return`（`mpv_options_service.dart:124-128`） |
| OHOS AVPlayer | HarmonyOS | **硬性 1.0**（`PlayConstants.ets:27-28`） | ❌ 零命中，只有线性标量 |
| Android ExoPlayer (`video_player`) | OHOS 之外若走此路 | **硬 clamp 1.0**（`VideoPlayer.java:274-277`） | ❌ 默认 Builder，无 `AudioProcessor` 接入点 |

**结论：B 只能在 media_kit 非 iOS 平台实现。** iOS / OHOS 上只能退化为「静态增益」，且因为上限被夹到 1.0，**连向上放大都做不到** —— 只能向下衰减。

这不是工程量问题，是接口不存在。设计必须接受平台间行为不一致，并在 UI 上诚实表达。

## 3. 现状（已核实）

### 3.1 音量已经持久化了

- 存储 key `kPlayerVolume = "PlayerVolume"`（`local_storage_service.dart:94`，Hive）
- `Rx<double> playerVolume = 100.0.obs` + `setPlayerVolume` 写盘（`app_settings_controller.dart:2195-2202`），启动默认 `100.0`
- 统一入口 `setSessionPlayerVolume(double volume, {bool persist = false})`（`player_controller.dart:1011-1039`）
- 落盘只发生在 `persist: true`，**仅两处**：滑条（`live_room_controller.dart:2686`）和 Windows/Linux/OHOS 手势（`player_controller.dart:1624`）

所以子需求 A 的骨架已经在了，缺的是几个具体环节。

### 3.2 A 的真实缺口：`resetRoom` 不重新施加音量

Player 实例是**复用**的，切房间有两条路径，行为不一致：

| 路径 | 是否重建 Player | 是否恢复音量 |
|---|---|---|
| 路由重新进入 `kLiveRoomDetail`（`app_pages.dart:132-143`，每次 `put` 新 controller） | 是 | ✅ `onInit` 里 `player.setVolume(...)`（`player_controller.dart:1701`） |
| `resetRoom()` **原地换房**（`live_room_controller.dart:3663-3724`） | 否 | ❌ **全程没有再调 `setVolume`** |

`resetRoom` 里 `await player.stop()`（`:3705`）后 `loadData()`（`:3709`）重新 `player.open(...)`，但没有重新施加音量。

**关键**：`resetRoom` 被**跨平台切换共用**（`:2426, 3014, 3163, 3248, 3276, 3437, 3541` 全部调它，含跨站点的 `Sites.allSites[target.siteId]`）—— 正好命中你说的「切到另一个平台」场景。

对比：多开路径在每次 `_openCurrentUrl` 之后**显式**重新 `await player.setVolume(...)`（`multi_room_player_controller.dart:554`）。直播间路径缺这一步。

**为什么现在看起来「大部分能用」**：mpv 的 `volume` 属性跨 `stop()`/`open()` 在同一实例上保持，所以桌面/Android 侧内存值会延续，问题被掩盖。但 OHOS 走完全不同的路径 —— `initialVolume` 是**构造时传参**（`ohos_video_player.dart:87, 100, 178`；`live_room_page.dart:708`），widget 重建时若不带上当前值就会回落到默认。**OHOS 是 A 最可能实际暴露的平台，需重点验证。**

### 3.3 A 的第二个缺口：移动端手势调的是系统音量

`_realSetVolume` 按平台分叉（`player_controller.dart:1621-1629`）：

```dart
if (Platform.isWindows || Platform.isLinux || Utils.isOhos) {
  await setSessionPlayerVolume(volume.toDouble(), persist: true);
  return;
}
// 手势只调系统音量，播放器内部音量由独立设置控制。
await VolumeController.instance.setVolume(volume / 100);
```

**Android / iOS 的垂直手势调的是系统音量**（`volume_controller: ^3.4.0`，override 钉 3.4.1），不落盘、不碰 `playerVolume`。而这两个平台**又不显示音量滑条按钮**（`player_controls.dart:668` 的 `if (!Platform.isAndroid && !Platform.isIOS && !Utils.isOhos)`），只剩静音按钮能动播放器音量。

**这直接违背你「不调整系统音量」的前提** —— 在手机上目前唯一的音量交互就是改系统音量。A 若要在移动端成立，必须先决定是否把移动端手势切到播放器内部音量。这是个**行为变更**，会影响现有用户肌肉记忆，需要单独取舍（见第 6 节风险）。

### 3.4 顺带发现的两个既有缺陷

| 位置 | 问题 |
|---|---|
| `player_controller.dart:221-222` | `_volumeBeforeMute = 100.0` 是**硬编码初值**，不是「静音前的实际音量」。若在未调音量的会话里直接静音再取消，会跳到 100 而非原值 |
| `live_room_controller.dart:3684` 附近 | `resetRoom` 里 `tempMutedUsers.clear()` 了，但 `mutedState` / `_volumeBeforeMute` **没有重置** —— 换房后静音状态与实际音量可能不一致 |

注：`toggleMute()` 全程 `persist` 默认 false，静音状态本身不落盘。这大概是有意的（静音不该跨会话），但需确认。

## 4. 子需求 A 设计：音量记忆跨房间/跨平台保持

### 4.1 改动方向

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| A1 | `resetRoom` 后重新施加音量 | `live_room_controller.dart:3663-3724`（`loadData()` 之后） | 照多开的做法（`multi_room_player_controller.dart:554`）补一次 `setSessionPlayerVolume`。**这是 A 的核心修复** |
| A2 | OHOS widget 重建时带上当前音量 | `ohos_video_player.dart:87, 100, 178`、`live_room_page.dart:708` | `initialVolume` 传 `playerVolume/100` 的**当前值**而非默认值；确认 `ohosVolume`（`player_controller.dart:145`）与 `playerVolume` 的同步方向 |
| A3 | 统一收口到单一入口 | `setSessionPlayerVolume`（`player_controller.dart:1011-1039`） | 所有音量写入必须走它。目前已是唯一入口，需确认没有绕过它直接调 `player.setVolume` 的地方 |
| A4 | 移动端手势改调播放器音量（**行为变更，需决策**） | `player_controller.dart:1621-1629` | 见 3.3。若不做，A 在 Android/iOS 上不成立 |
| A5 | 修 `_volumeBeforeMute` 硬编码初值 | `player_controller.dart:221-222` | 初值改为读当前实际音量 |
| A6 | `resetRoom` 重置静音态 | `live_room_controller.dart:3684` 附近 | 与 `tempMutedUsers.clear()` 并列处理 |

### 4.2 A 的成本与风险

- A1 / A2 / A5 / A6：**成本很低**，都是补一行到几行的事，风险低
- A3：需要一次全量核查，成本低
- A4：**成本低但风险中** —— 是用户可感知的行为变更

### 4.3 A4 的取舍（需要你拍板）

移动端手势当前调系统音量。改成调播放器音量的**代价**：

- 用户在 App 里把音量调到很小后退出，**系统音量不变**，其他 App 不受影响（这是想要的）
- 但用户若习惯了「在播放器上滑就是调系统音量」，会觉得音量键与手势不再一致
- 播放器音量与系统音量**串联相乘**，两者都小时会过于安静，用户可能困惑「明明滑到最大还是很轻」

**折中选项**：保留手势调系统音量，**同时在移动端也放出音量滑条按钮**（去掉 `player_controls.dart:668` 的平台限制），让播放器音量可独立调节与记忆。这样两套音量各有入口、互不抢占，A 也能成立。**推荐这个方案**，因为它不破坏既有肌肉记忆。

## 5. 子需求 B 设计：跨平台基准响度归一化

### 5.1 先摆一个可能推翻需求前提的判断

**「平台间基准音量不同」这个归因可能不准确。**

直播音频的响度主要由**主播自己的麦克风增益、OBS 推流电平、声卡设置**决定，平台只做转码通常不改响度。因此：

**同一平台内不同主播的响度差，很可能大于平台之间的平均响度差。**

这直接影响方案选择：

- 如果差异主因是**平台**，那么「每平台一个固定增益偏移」的查表法就够了，成本极低
- 如果差异主因是**主播**，查表法几乎无效，必须上**动态响度归一化**，成本和风险都高一个量级

**这个判断必须先用实测澄清，不能靠猜。** 见 5.2。

### 5.2 阶段 B0：先测量，不实现（强制前置）

**方法**：mpv 侧可读 `af-metadata` 或挂 `ebur128` 滤镜读取 LUFS 测量值，采集样本。

**采样设计**：五个平台 × 每平台至少 5 个不同主播 × 各测 60s 稳态响度。

**产出**：一张 LUFS 分布表，回答两个问题：

1. 平台间**均值**差多少 dB？
2. 平台**内**方差有多大？与平台间差异比较，谁更大？

**分支决策**：

| 测量结果 | 判定 | 走哪条 |
|---|---|---|
| 平台间均值差显著（>3dB）且平台内方差小 | 平台主导 | B1 静态查表（便宜） |
| 平台内方差 ≥ 平台间差异 | 主播主导 | B2 动态归一化（贵，且有延迟代价） |
| 两者都显著 | 叠加 | B1 打底 + B2 兜住个体差异 |

**成本**：中（要搭采集手段 + 人工跑样本）。**但这是唯一能避免做错方向的办法。**

### 5.3 方案 B1：静态每平台增益偏移

**做法**：配一张 `siteId → gain(dB)` 表，切平台时按表施加增益。

**实现路径**：不需要音频滤镜 —— 直接在 `setSessionPlayerVolume` 施加时叠加一个平台系数即可，**因此全平台可用**（含 iOS / OHOS）。

**改动位置**

| 位置 | 改动 |
|---|---|
| 新增常量表（建议 `simple_live_core` 或 app 侧 constant） | `siteId → gain` |
| `setSessionPlayerVolume`（`player_controller.dart:1011-1039`） | 施加时乘平台系数；**注意持久化的应当是「用户意图音量」而非「施加后的实际值」**，否则切平台会反复叠加漂移 |

**这是整个 B1 最容易写错的地方**：必须严格区分「用户设定值」与「实际下发值」两个量，只持久化前者。

**上限问题**：若某平台需要**放大**，`volume` 要超过 100。media_kit 从不设置 `volume-max`（已核实全包零命中），需自行注入 `volume-max`（走 `mpv_options_service` 的透传路径，见 5.5）。**但 iOS / OHOS / ExoPlayer 三条路上限硬性为 1.0，无法放大。**

**因此 B1 的基准点必须选「最响的平台」，其余平台一律向下衰减** —— 这是唯一能全平台一致的做法。代价是整体音量变小，与你「不调系统音量」的诉求部分冲突（见 6.1）。

### 5.4 方案 B2：动态响度归一化（仅 media_kit 非 iOS）

**候选滤镜**

| 滤镜 | 特性 | 直播适用性 |
|---|---|---|
| `dynaudnorm` | 实时动态归一化，高斯平滑窗口 | ✅ 较适合，可做到低前瞻 |
| `loudnorm` | 基于 EBU R128，双阶段测量 | ❌ 需前瞻窗口，延迟代价大 |
| `replaygain` | 依赖文件元数据 | ❌ **直播流无元数据，完全不可用** |

**结论：只有 `dynaudnorm` 可选。**

**注入路径**：`mpv_options_service.dart` 的 `applyToPlayer`（`:123-142`）用 `NativePlayer.setProperty` 下发，**无属性白名单**，只剔除 `vo` / `hwdec`（`:133-134`）。所以 `af` 可以注入。

### 5.5 B2 的三个硬坑（都已核实，必须在设计阶段处理）

**坑 1：`af` 是整串覆盖，不是 append**

- media_kit 自己在 `pitch == true` 时会整串覆盖 `af`（`real.dart:827-830`，写的是 `scaletempo`）。本仓库 `pitch` 默认 false 且两个 app 都没传，所以**当前不冲突**，但这是个埋着的雷 —— 一旦有人开 `pitch`，滤镜链会被冲掉
- 更现实的冲突：用户自定义 `mpvAdvancedOptions`（`:82`）和导入的 `mpv.conf`（`:87`）**优先级高于** profile，且 conf 最高（`:88`）。用户若自己写了 `af`，会与本功能互相覆盖
- **设计要求**：必须定义 `af` 的合成策略（读取现有值并拼接，而非盲写），且在用户已自定义 `af` 时明确让谁赢

**坑 2：注入失败是静默的**

`applyToPlayer` 的 `try/catch` 把异常吞掉只记一条 `Log.d`（`:139-141`）。这意味着**滤镜没生效时用户和开发者都不会收到任何反馈**。设计需要一条可观测手段（读回属性确认，而非假设写入成功）。

**坑 3：与低延迟优化直接冲突**

`dynaudnorm` 有平滑窗口，本质在**加音频缓冲**；而 `docs/直播延迟优化设计.md` 的低延迟档恰好要把 `audio-buffer` 压到 0、并可能套用 `profile=low-latency`。

**两者必须协商，不能各写一份。** 可选处理：

- 归一化档与低延迟档做**互斥或分级**（选低延迟激进档时自动降级归一化）
- 或把 `dynaudnorm` 窗口压到最小，接受归一化精度下降
- 明确优先级：**延迟优先**（直播场景延迟更影响体感）

**这是两份设计文档之间唯一的强耦合点，任何一边施工前都要看另一边。**

### 5.6 B 的平台降级矩阵

| 平台 | 能做到什么 |
|---|---|
| Windows / Linux / macOS / Android(media_kit) | B1 + B2 全量 |
| iOS | **仅 B1，且不能放大**（`applyToPlayer` 无条件 return） |
| OHOS | **仅 B1，且不能放大**（上限硬 1.0，无滤镜） |
| TV app | 机制同主 app（`mpv_options_service.dart:81-95`，无 iOS 分支），但跑 media_kit **1.1.11**（老版，不在本地 cache，`setVolume` 是否同样无 clamp **未验证**） |

**UI 必须诚实表达这个差异** —— 在做不到的平台上不要显示「已归一化」之类的承诺。

## 6. 风险登记

### 6.1 「向下归一化」与需求的内在冲突

你的诉求是「不调系统音量」。但 B 的全平台一致方案只能**向下衰减**到最安静的基准（因为 iOS/OHOS 上限硬为 1.0）。结果是**整个 App 整体变安静**，用户很可能反而去调大系统音量 —— 与诉求相反。

**这是需求内部的真实矛盾，不是实现问题。** 三条出路：

1. 接受平台不一致：能放大的平台就放大（media_kit 非 iOS），不能的只衰减
2. 全平台统一向下衰减，接受整体变安静
3. 只做 A（音量记忆），B 降级为「可选开关，默认关」

**倾向 1 或 3。**方案 2 表面「一致」，实际体验最差。

### 6.2 其余风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 增益叠加漂移（持久化了施加后的值） | 高，切平台数次后音量失控 | 严格区分「用户意图值」与「实际下发值」，只持久化前者（见 5.3） |
| 放大导致削波失真 | 中 | 放大必须配限幅；不要裸调 `volume` 超 100 |
| `af` 与用户自定义/导入 conf 互相覆盖 | 中 | 定义合成策略并文档化（见坑 1） |
| `dynaudnorm` 加缓冲抬高延迟 | 中 | 与延迟设计协商，延迟优先（见坑 2、坑 3） |
| 移动端手势语义变更（A4） | 中 | 采用 4.3 折中方案：手势不动，另放滑条 |
| TV app media_kit 1.1.11 行为未验证 | 中 | 结论不可从主 app 平移，需单独验证 |
| 归一化在纯音乐/ASMR 类直播上听感变差 | 低 | 提供关闭开关 |

## 7. 建议推进顺序

```
A（音量记忆）—— 先做，独立可交付
  ├─ A1 resetRoom 补施加音量   ← A 的核心，成本最低收益最直接
  ├─ A2 OHOS initialVolume 带当前值
  ├─ A5/A6 修既有缺陷
  ├─ A3 入口收口核查
  └─ A4 决策：采纳 4.3 折中（移动端放出滑条）
        ↓
B0 响度实测        ← 强制前置，回答「平台主导还是主播主导」
        ↓
   ├─ 平台主导 → B1 静态查表（全平台可用）
   └─ 主播主导 → B2 dynaudnorm（仅 media_kit 非 iOS）
        ↓
   与 docs/直播延迟优化设计.md 协商 audio-buffer 冲突
```

**为什么 A 必须先做且能独立交付**：它是你需求里「切平台也得保持」那一半的**完整答案**，成本极低，且不依赖任何 B 的结论。

**为什么 B0 不能跳**：5.1 的归因判断若错了，B1 会做完全无效的工作。

## 8. 验证方案

**A 的验证（可确定性验证）**

| 场景 | 预期 |
|---|---|
| 房间内调音量 → `resetRoom` 换同平台房间 | 音量保持 |
| 房间内调音量 → 换**不同平台**房间（走 `resetRoom`） | 音量保持 ← **当前缺陷所在** |
| 调音量 → 退出 App → 重进 | 音量保持（读 `kPlayerVolume`）|
| OHOS 上同上三项 | 音量保持 ← **最可能暴露问题的平台** |
| 静音 → 换房 → 取消静音 | 回到静音前音量，不是 100 |

**B 的验证（只能相对比较）**

需要客观测量，不能靠耳朵：挂 `ebur128` 读 LUFS，比较归一化前后**跨平台 LUFS 标准差是否下降**。同时必须监测削波（`clipping` / true peak）。

**平台矩阵**：Windows / Android / iOS / OHOS / TV 各自播放器路径不同，结论不可平移，需分别验证。

## 9. 待核实项

- **平台间响度差异是否真实存在、量级多大** —— 整个 B 的前提，尚无任何实测数据（这正是 B0 要做的）
- libmpv `volume-max` 的**确切默认值**（引自 mpv 文档记忆，未在本机二进制核实）；media_kit 从不设置该属性已核实
- TV app 的 media_kit **1.1.11 不在本地 pub cache**，其 `setVolume` 是否同样无 clamp、`af` 的 pitch 覆盖逻辑是否相同，**均未验证**
- 主 app **无 `pubspec.lock`**（仅 TV app 有），实际解析版本无法从 lock 确认；`pubspec.yaml:88` 声明 `^1.2.2`，本地 cache 匹配 1.2.6，本文档结论基于 1.2.6
- Android 主路径究竟走 media_kit 还是 `video_player` —— 直接决定 Android 属于「能做 B2」还是「上限 1.0」，**这是平台能力矩阵里唯一没坐实的格子**
- `toggleMute` 不落盘是否为有意设计
- `ohosVolume`（`player_controller.dart:145`，0..1）与 `playerVolume`（0..100）的同步方向与唯一真源
- `dynaudnorm` 在低延迟档下的**实际**缓冲代价（需实测，不能靠文档推断）

## 10. 一句话结论

**A 该马上做** —— 「切平台音量保持」的缺口就在 `resetRoom` 少一次重新施加音量（`live_room_controller.dart:3663-3724`），多开路径早就做对了（`multi_room_player_controller.dart:554`），照抄即可，成本几行。

**B 要先测再做，且注定不能全平台一致** —— iOS / OHOS / ExoPlayer 三条路音量上限硬为 1.0 且无滤镜接口，真正的响度归一化只在 media_kit 非 iOS 平台可行。更要紧的是：**「平台基准音量不同」这个归因本身需要先用 LUFS 实测证实**，否则可能做出一个对真实差异（主播个体差异）无效的功能。
