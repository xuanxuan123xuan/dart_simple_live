# 观看统计设计

> 状态：设计草案，**未实施**。所有结论基于对 dev 分支代码的只读核查。
> 关联：[[弹幕热词统计设计.md]]（性质相反，不共享基础设施）

Roadmap 原文：**本地静默统计观看时长/平台分布/常看主播（hive 存储，不打扰使用）。**

---

## 1. 一句话结论

**存储层完全现成，难点全在「什么时候算作在看」这一个问题上。**

Hive、`BasePageController` 分页、页面接入范式、配置导入导出、周期性静默任务 —— 全部有成熟先例可抄。但「观看时长」需要一个**退房/停止观看的钩子**，而这个钩子在当前架构里**不存在**。

## 2. 现成的部分（已核实）

### 2.1 存储层

`hive: 2.2.3` + `hive_flutter: 1.1.0`（`simple_live_app/pubspec.yaml:20-21`），`Hive.initFlutter` 在 `main.dart:128`。

**typeId 占用情况（app 端）：1 = FollowUser，2 = History，3 = FollowUserTag。新模型从 4 起安全**（0 未使用但按 Hive 惯例建议避开）。

Adapter 注册点 `main.dart:556-558`，在所有 `openBox` 之前：
```dart
Hive.registerAdapter(FollowUserAdapter());
Hive.registerAdapter(HistoryAdapter());
Hive.registerAdapter(FollowUserTagAdapter());
```

已开 6 个 box：`History` / `FollowUser` / `FollowUserTag`（`db_service.dart:17-19`）+ `LocalStorage` / `DanmuShield` / `DanmuShieldPreset`（`local_storage_service.dart:158-160`）。

服务初始化顺序（`main.dart:555-590`）：registerAdapter → `LocalStorageService` → `DBService` → `CurrentRoomService` → `PlaybackDisplayCoordinator`(permanent) → `AppSettingsController` → 账号服务 → `FollowService` → …

**两种存储范式都有先例：**
- **TypeAdapter 模式** —— `History` / `FollowUser` / `FollowUserTag`，需 `hive_generator` 代码生成
- **JSON-in-Hive 模式** —— `kRoomQualityMemory`（`live_room_controller.dart:376-436`）把一整个 JSON Map 存进单个 key，用 siteId 做二级 key；`DanmuShieldPreset`（`models/danmu_shield_preset.dart`）只有 `toJson()`，反序列化手写

后者对「统计聚合数据」可能更合适 —— 统计数据通常是少量聚合记录，不需要按 key 独立读写。

### 2.2 现有 History 模型 —— 可 join 但不能复用

`simple_live_app/lib/models/db/history.dart`：
```dart
@HiveType(typeId: 2)
class History {
  @HiveField(0) String id;        // "${siteId}_${roomId}"
  @HiveField(1) String roomId;
  @HiveField(2) String siteId;
  @HiveField(3) String userName;
  @HiveField(4) String face;
  @HiveField(5) DateTime updateTime;
}
```

**关键事实：没有任何时长字段，`updateTime` 语义是「最后一次进入该房间的时刻」。**

写入点全仓**仅一处**：`live_room_controller.dart:1893` 的 `addHistory()`，位于 `loadData()` 内部、房间详情拉取成功之后。函数体 `:2470-2489`。即**进房写入，退房不写**。

因为 key 是 `siteId_roomId`，同一房间反复观看只覆盖一条 —— 所以 History box 的条目数上限天然等于「看过的不同房间数」，**没有任何裁剪逻辑**（全仓搜 length/limit/trim/prune 零命中），清理只能靠用户手动（`history_controller.dart:27` 的 `clear()` / `:32` 的 `delete`）。

**结论：History 不能直接扩展成观看统计**（语义是「最近访问」，且同房间会覆盖，历史观看次数不可恢复）。但它与 `FollowUser` 共用 `siteId_roomId` id 规则，**统计数据可按同一规则 join**，取主播名/头像不需要重复存。

## 3. 核心难点：「什么时候算作在看」

这是整个功能唯一真正需要设计的东西。

### 3.1 退房钩子不存在

**`resetRoom()` 完全绕过 onInit / onClose。**

`live_room_controller.dart:3663` `Future<void> resetRoom(Site site, String roomId)` —— 原地改 `rxSite.value` / `rxRoomId.value`、`_roomDisposed = false`、`_loadGeneration += 1`、停旧弹幕与播放，然后 `loadData()`。**不重建 controller。**

7 个调用点（同文件）：`:2426`（播放失败自动切换）、`:3014`（历史弹窗选中）、`:3163`（推荐/关注列表选中）、`:3248`、`:3276`、`:3437`、`:3541`。

后果：
- **进房事件是完整的** —— `addHistory` 挂在 `loadData()` 里，所以换房也能覆盖到。这是现有 History 能正常工作的原因。
- **退房事件在 `resetRoom` 路径下没有任何钩子。** 用户从 A 房切到 B 房，A 房的「观看结束」时刻无处捕获。

另外 `resetRoom` 内部有 `_roomSwitching` + `_pendingRoomSite/_pendingRoomId` 的合并循环 —— **快速连切时中间房间会被折叠掉**，只有最后一个真正 `loadData`。所以「进房」事件本身在快速切换下也不是每房必发。

### 3.2 `onClose` 不可靠

`onClose()` 是 `async` 且内部 `await player.stop()` / `await liveDanmaku.stop()`。**GetX 不会等 `onClose` 的 Future** —— 在 `onClose` 里放异步写盘存在不被完成的风险。

（另有一个已废弃的 `_legacyOnClose()` :3946，标了 `// ignore: unused_element`，不在调用链上。）

### 3.3 可用的信号（都已核实存在）

| 信号 | 位置 | 说明 |
|---|---|---|
| 前后台切换 | `live_room_controller.dart:3737` `didChangeAppLifecycleState` | **语义最贴近「是否真在看」**。已维护 `isBackground`(:472)、`_backgroundedAt`、`_wasPlayingBeforeBackground`、`_positionBeforeBackground` |
| 服务级前后台 | `playback_display_coordinator.dart:215` | 常驻服务（`permanent: true`），维护 `_appActive`。**不随房间销毁，是挂持久化的更安全位置** |
| 播放中 | `player.state.playing`（非鸿蒙，用法见 `:3749`）/ `ohosPlaying`（`player_controller.dart:142`） | |
| 缓冲中 | `player.stream.buffering` | 卡顿时是否计入时长的判断依据 |
| 静音 | `mutedState`（`player_controller.dart:221`） | 「静音挂机」是否算在看 |
| 后台播放允许 | `_allowBackgroundPlayback`（设置 `kAllowBackgroundPlayback`） | 开启时后台仍在听，应计入 |

**不要误用 `startLiveDurationTimer()`（`:3915`）** —— 它算的是**主播开播时长**（`detail.value.showTime` 到现在），`liveDuration`(:483) 仅用于 UI 展示。

### 3.4 三个可选口径

| 口径 | 实现方式 | 优点 | 缺点 |
|---|---|---|---|
| **C1. 心跳累加** | periodic timer（如 30s）+ 条件判断（前台 && playing），每 tick 累加固定增量 | **不需要退房钩子** —— 天然绕开 3.1 的全部问题；崩溃/强杀最多丢一个 tick | 精度受 tick 粒度限制；tick 频率与耗电权衡 |
| **C2. 进出配对** | 进房记 start，退房记 end，相减 | 精确 | 需要退房钩子（不存在）；`onClose` 不可靠；崩溃丢整段 |
| **C3. 混合** | C1 为主，退房时补最后一段零头 | 精确且健壮 | 复杂度最高 |

**倾向 C1。** 理由：它把「退房钩子不存在」这个架构事实从障碍变成了无关项。心跳模式下 `resetRoom` 的绕过、`onClose` 的不可靠、快速连切的房间折叠**全都不影响正确性** —— 只要 tick 时读的是「当前房间」即可（`CurrentRoomService` 已经在维护这个状态，`onInit` 里 `setRoom`，`onClose` 里 `clearRoom`）。

代价是精度：30s tick 意味着单次观看的误差上限 30s。对「平台分布」「常看主播」这类聚合统计，这个精度完全够用。

### 3.5 落盘频率

C1 下有两层选择：每个 tick 都写盘（简单、崩溃几乎不丢），或内存累加 + 低频 flush（省 IO）。

考虑到 Hive 是本地文件且写入量极小（一条聚合记录），**倾向每 tick 直接写**，避免引入第二套 flush 时序问题。这也符合「不打扰」——用户感知不到。

## 4. 数据模型草案方向

不写具体代码，只说结构决策：

**按「日 × 站点 × 房间」聚合，而非按会话记录。** 理由：
- 会话级明细会无界增长（`History` 无裁剪的问题会重演，且更严重 —— History 上限是「不同房间数」，会话明细上限是「观看次数」）
- 三个 Roadmap 目标（时长 / 平台分布 / 常看主播）都是聚合查询，不需要明细
- 日粒度足够支撑「最近 7 天/30 天」这类视图，也天然给出了裁剪维度（按日期删旧数据）

**主播名/头像不重复存** —— 按 `siteId_roomId` join `History` 或 `FollowUser`。代价是被清理过历史的房间会丢展示信息，可接受（退化为显示 roomId）。

**必须设计裁剪策略。** 这是 History 的既有教训：无裁剪 + 无上限 + 只能手动清。按日聚合的话，保留 N 天（如 90 天）滚动删除是最简单的做法。

## 5. 展示层

### 5.1 没有图表库

已核实：**全部 21 个 pubspec.yaml 检索 `fl_chart|syncfusion|charts_flutter|graphic|echarts|charts` —— 零命中。**

项目里也**没有任何真正的统计/图表页**。最接近的展示形态：
- `history_page.dart`（120 行，纯 `ListTile` + `Dismissible` 列表）
- `other_settings_page.dart:272-273` 日志文件列表，用 `Utils.parseFileSize` 展示大小

现成的格式化工具：`Utils.parseFileSize`、`Utils.parseTime`（`history_page.dart:91` 在用）。

### 5.2 建议：先不引图表库

第一版用列表 + 进度条形态（平台分布用横向占比条，常看主播用带时长的排行列表）。理由：
- 引图表库是一次不可逆的依赖决策，包体积成本明确，收益取决于用户是否真会看
- 列表形态与项目现有 UI 语言（`ListTile` + `remixicon`）一致，实现成本接近零
- 若后续确认有需求再引，届时数据结构已经稳定

**统计数据的形状不应被展示形态绑定** —— 按日聚合的数据既能画图也能列表，先做列表不会挡住后续加图表。

## 6. 隐私

已核实：**项目没有隐私政策页、没有隐私开关、没有任何数据上报开关。**

搜 `privacy|隐私|telemetry|统计` 的结果全是无关项：`telemetry` 命中来自多开自适应画质的性能遥测（本地内存态）；「统计」只命中两处 UI 文案「动态统计跨度」。唯一沾边的是「开启日志记录」（`other_settings_page.dart:237`）和 `Utils.showStatement` 免责声明弹窗。

Roadmap 写的是「本地静默统计」，**数据不出设备，所以不需要隐私政策**。但建议：
- 提供一个总开关（默认开或关都可以讨论，但开关本身应该有）
- 提供「清空统计数据」入口 —— 与 History 的手动清理对齐

这两条不是合规要求，是「不打扰」原则的自然延伸：用户应该能关掉一个自己不想要的后台统计。

## 7. 建议推进顺序

1. **先定口径**（C1 心跳 / tick 频率 / 什么条件算在看）—— 这个决定之后所有代码都是机械劳动
2. 数据模型 + Hive adapter（typeId 从 4 起）+ 裁剪策略
3. 心跳埋点。挂在 `PlaybackDisplayCoordinator`（常驻服务）比挂在 `LiveRoomController`（随房销毁）更稳
4. 展示页（照抄 history 页范式：route_path → app_pages → app_navigation → controller extends BasePageController → page extends GetView → mine_page 加入口）
5. 总开关 + 清空入口
6. **最后再考虑**是否进配置导入导出（要动 schemaVersion 和两条同步链路，是独立的一摊事）

## 10. 一句话总结

存储、页面、周期任务、导入导出全部有现成范式可抄，**唯一需要真正做决定的是「怎么算在看」**。选心跳累加（C1）能一次性绕开退房钩子缺失、`onClose` 不可靠、快速连切房间折叠这三个架构障碍，代价只是时长精度 —— 而这个精度对聚合统计无影响。
